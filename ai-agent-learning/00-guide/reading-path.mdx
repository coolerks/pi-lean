# 阅读指南

这套教材不是 API 目录，而是一条从 HTTP 请求走到 Agent Harness 的工程学习路径。每章都回答一个问题：**这件事在一次真实 Agent 请求中发生在哪里，谁负责它，失败时怎么办？**

## 学习目标

完成学习后，你应该可以：

- 看懂 `system`、`user`、`assistant`、`tool` 消息和 Provider 的请求体。
- 解释模型输出的 `tool_call` 为什么不是 Java 方法调用。
- 从一个 `ScriptedModel` 写出有限步数的 Tool Calling Loop。
- 用 Session、Compaction、Steering、Retry 和 Permission 把循环变成可运行的 Harness。
- 沿着 Pi 的 `AgentSession → Agent → agent-loop.ts → Provider` 调用链定位源码。
- 用 Go 的 `context.Context` 和 Java 的 cancellation/`Future` 表达取消。

## 前置知识

你需要能读懂 Java 类、interface、集合、异常、HTTP 和 JSON；不要求先会 TypeScript、React 或某个 Agent Framework。Go 部分会解释 module、struct、interface、goroutine 和 channel，但不会把本教材变成 Go 语法课。

如果你不熟悉 TypeScript，先记住五个映射：

| Pi/TypeScript | Java 类比 | Go 类比 | 在 Agent 中的作用 |
| --- | --- | --- | --- |
| `interface` | interface | interface | 描述 Model、Tool 等边界 |
| `Promise<T>` | `Future<T>` | 返回值配合 `context.Context` | 表示将来完成的异步结果 |
| `async/await` | 阻塞 `Future.get()` 或组合异步任务 | goroutine/channel | 等待网络或工具完成 |
| `AsyncIterable<T>` | Listener/`Flow.Publisher` | channel/回调 | 按增量消费流式事件 |
| `AbortSignal` | cancellation token/interrupt | `context.Context` | 传递停止意图 |

这些只是行为类比，不是类型级等价。例如取消一个 HTTP 请求，不代表已经发生的远端计费或文件写入会自动回滚。

## 每章的学习方法

每页至少做四件事：

1. **先回答场景问题。** 例如“模型返回 JSON 后，谁真的打开文件？”
2. **画数据流。** 把输入、输出、状态改变和副作用分别画出来。
3. **运行最小实验。** 优先使用离线 Fake/Scripted Model，先验证控制流，再接真实 API。
4. **写失败路径。** 至少考虑 timeout、坏 JSON、unknown tool、取消和达到 max steps。

读源码时不要只复制类型定义。对每个入口写下：调用方是谁、它接收什么、返回什么、下一步调用谁、失败是否改变 Session。

## 哪些内容可以暂时略读

- 已熟悉 HTTP/SSE 的读者可以先跳过协议细节，但不能跳过 Provider adapter 的归一化边界。
- 只做单轮问答的读者可以先跳过 `07-harness/reliability`，但完成 Tool Calling 后必须回来理解崩溃和恢复。
- 只想使用 Pi 的读者可以先查阅 `pi-docs/`；要自己实现 Harness 的读者必须完成原创教材和 Go/Java 示例。
- Provider 的厂商差异可以先掌握表格，再回看每个 API adapter 的源码路径。

## 三种语言的职责

| 层 | TypeScript/Pi | Go 示例 | Java 示例 |
| --- | --- | --- | --- |
| 模型边界 | `Model`、`AsyncIterable` | `Model`、`StreamingModel` | `Model`、SSE callback |
| 工具边界 | `AgentTool` | `Tool` + `Registry` | `Tool` + `ToolRegistry` |
| 取消 | `AbortSignal` | `context.Context` | `CancellationToken` + interruption |
| 并发 | Promise/async iterator | goroutine、channel | `ExecutorService`/`Future` |
| 插件 | Extension loader | explicit registry | SPI/`ServiceLoader` |
| 持久化 | Session manager | JSONL `Session` | Jackson JSONL `Session` |

这里的比较是为了看设计约束，不是声称三者实现相同功能。Pi 当前公共 `AgentHarness` 仍是 scaffold；可运行的 coding-agent 主路径是 `Agent`、`AgentSession`、`SessionManager` 和 `ExtensionRunner`。

所有 Pi 源码结论绑定 commit `853a80d26c90a14c1886f0ebb8ffaae133ca2185`。核心入口包括：

## 动手实验：画你的第一张边界图

### 目标

把一条“用户让 Agent 修改文件”的请求拆成模型输出、Runtime 动作和 Harness 状态。

### 准备

准备纸、Mermaid 编辑器或任意文本文件；不需要 API key。节点至少包括 User、Context、LLM、Provider、Agent Loop、Tool Executor、Session 和 Telemetry。

### 步骤

1. 从 User 画箭头到 Context，并写出 system prompt、history、tools 三类输入。
2. 从 Context 画箭头到 Provider/LLM，标注“请求”而不是“执行”。
3. 从 LLM 画出 assistant text 与 Tool Call 两条可能路径。
4. 从 Tool Call 画到 schema、permission、execute，再画回 Tool Result。
5. 在 execute 旁标出唯一产生文件/进程副作用的位置。
6. 在 run 结束后画 Session persistence 和 Telemetry，但不要把它们画成模型输出。

### 观察点

模型只产生候选内容和调用意图；Runtime 决定是否执行；Harness 保存状态并处理失败。Provider 只负责协议适配。

### 预期结果

你的图中至少有两条回路：Tool Result 回到下一次模型请求，Session/Telemetry 记录一次运行但不代替 Context。

### 思考题

如果把 Permission 放在 UI 而不放在 Tool Executor 前面，脚本调用或 RPC 调用能否绕过它？如果 Session 保存了 Tool Call 却没有 Tool Result，恢复时应该怎样标记？

## 自测清单

在进入下一章前，用自己的话回答：

- Context Window、Session 和 Memory 为什么不是一个东西？
- `tool_call` 和真正的函数执行分别在哪一层？
- 为什么 `maxSteps` 不能省略？
- 为什么 Provider adapter 不应散落在 Agent Loop 中？
- 一个进程崩溃后，哪些信息足以恢复，哪些外部副作用无法撤销？

答不出来时，不要继续堆框架。回到对应的 JSON、测试和事件图，把一次请求从输入追到终点。

## 小结

学习 Agent 的有效顺序是：先理解协议，再实现循环；先用 Fake Model 测控制流，再研究真实 Provider；先知道副作用在哪里，再讨论 Harness 的恢复和安全。这样读 Pi 源码时，你看到的是一组工程决策，而不是一堆陌生的 TypeScript 语法。
