## 中文译文

### 遥测文档怎么读

这份 schema 描述的是 span，而不是把整段 prompt 写进日志。每个 span 有父子关系、默认状态、开始属性和结束属性。开始属性回答“这次操作是什么”，结束属性回答“它怎样结束”。`Required` 表示创建 span 时必须提供的字段；结束属性都是可选的补充信息，不能因为没有某个 usage 字段就把整次请求判为失败。

### `pi.ai.request`：一次 Provider 请求

`pi.ai.request` 覆盖 `stream`、`fetch_deferred`、`cancel_deferred` 和 `generate_images` 等逻辑操作。创建时应记录 Provider id、model id、API id、是否 streaming，以及是否 deferred。请求完成后可以补充实际响应 model/id、规范化的 `stop_reason`、HTTP 状态、输入/输出/cache/reasoning token、总成本、chunk 数、首个 chunk 的延迟和低基数错误类型。

这里的 `response.id` 被标为 high cardinality：它适合排查单次请求，不适合作为聚合维度。`time_to_first_chunk_ms` 衡量首个增量事件，不等于整次 LLM latency；两者都应保留。Provider 抛出异常或返回错误结果时，span 状态才应变为 error。

### `pi.harness.*`：可靠性边界

`pi.harness.run`、`compaction` 和 `navigation` 都对应一次已接纳的 Harness 操作，并要求 session、lane、operation id、是否 recovery 以及 operation kind。结束时写 `completed`、`aborted`、`failed` 或 `suspended` 等 outcome；稳定的 `error.code` 适合告警和统计，具体异常类名放在 `error.type`。

`pi.harness.checkpoint` 是 run 内的提交边界，可区分 `normal`、`failure_drain` 和 `abort_reconcile`。`pi.harness.turn` 表示一次 assistant response 加其 Tool batch；`pi.harness.step` 表示一个可重试的 assistant、compaction 或 branch-summary attempt，因此 `attempt` 必须是一开始就确定的、从 1 开始的编号。overflow 不是普通失败，`step.outcome` 可以明确记录 `overflow` 或 `retry`。

### Tool、Hook 与被动事件

`pi.harness.tool` 只表示原始 phase-2 Tool 执行。开始时记录 tool name、call id、声明的 replay policy（`never` 或 `safe`）和是否 recovery；结束时记录 `is_error`。这不等于模型生成了一个 Tool Call：模型输出应由普通 message/event 记录，真正的副作用执行才创建 Tool span。

`pi.harness.hook` 记录 handler 的 name 和 registration id，结束 outcome 可以是 `completed`、`skipped`、`blocked` 或 `failed`。`pi.harness.event_handler` 是被动 listener 的调用 span；listener 出错仍应留下 `handler_error`，不能静默吞掉。`pi.harness.sleep` 专门记录 retry delay，并区分正常 elapsed 与 aborted。

### Session 写入与隐私

`pi.session.write` 表示一次已提交的 session mutation：entry、record、lane 或 fact。只有 commit 成功后才应报告 committed sequence。schema 中多个 id 被标为 high cardinality，并不意味着可以发送原始文件、完整 Tool 参数、认证 header 或 prompt；采集端需要脱敏、采样和访问控制。跨 provider、run、turn、Tool 的关联使用 id，聚合使用低基数字段。

**实验**：先用一次 ScriptedModel run 产生一个成功的 `pi.ai.request` 和 `pi.harness.run`，再注入 429、Tool exception、abort 和 compaction overflow。检查每个失败 span 有 outcome/error，usage 没有被误写进 message，日志中没有 API key 和文件正文。
