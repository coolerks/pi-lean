## 安装与启动

```bash
git clone https://github.com/earendil-works/pi-mono
cd pi-mono
npm install
npm run build
```

如果当前工作区已经是仓库副本，不要再次执行 clone 覆盖它。`npm install` 安装 workspace 依赖，`npm run build` 构建项目。

从源码启动：

```bash
/path/to/pi-mono/pi-test.sh
```

这个脚本可以从任意目录执行，Pi 会保留调用者的当前工作目录。因此，脚本所在目录和 Pi 处理项目文件时使用的 cwd 不是同一个概念。

> 译者注：Java 读者可以把当前工作目录类比为进程的 `user.dir`，把源码入口类比为启动器；Go 中则对应 `os.Getwd()`，而不是可执行文件所在目录。相对路径问题通常来自混淆这两者。

## Fork 与重新命名（Forking / Rebranding）

在 `package.json` 中配置：

```json
{
  "piConfig": {
    "name": "pi",
    "configDir": ".pi"
  }
}
```

为自己的 fork 修改 `name`、`configDir` 和 `bin` 字段。这些字段会影响 CLI banner、配置路径以及环境变量名称。重新命名后，应在干净的 HOME、空会话目录和全新安装中检查旧配置是否仍被读取。

## 路径解析

Pi 有三种运行方式：npm 安装、standalone binary，以及从源码使用 tsx 启动。读取 package asset 时必须使用 `src/config.ts`：

```typescript
import { getPackageDir, getThemeDir } from "./config.js";
```

不要直接使用 `__dirname`。不同运行方式可能把资源放在源码目录、bundle 附近或安装目录；`getPackageDir` 和 `getThemeDir` 将这些布局差异收口到统一入口。

## 调试命令

隐藏命令 `/debug` 会写入 `~/.pi/agent/pi-debug.log`，其中包括：

- 带 ANSI 控制码的渲染后 TUI 行；
- 最近发送给 LLM 的消息。

调试日志可能含有项目代码、prompt、路径或敏感数据。提交 issue 或分享日志前，应先检查并脱敏。

## 测试

```bash
./test.sh                         # Run non-LLM tests (no API keys needed)
npm test                          # Run all tests
npm test -- test/specific.test.ts # Run specific test
```

`./test.sh` 用于运行不需要模型凭据的测试；`npm test` 运行完整测试；第三条命令只运行指定测试。执行完整测试前应确认项目脚本是否包含需要环境变量或真实服务的测试。测试 Agent Loop 时优先使用 faux 或 scripted provider，测试 HTTP adapter 时使用本地 fake server。

## 项目结构

```text
packages/
  ai/           # LLM provider abstraction
  agent/        # Agent loop and message types
  tui/          # Terminal UI components
  coding-agent/ # CLI and interactive mode
```

`ai` 提供 LLM provider 抽象，`agent` 提供 Agent Loop 和消息类型，`tui` 负责终端界面，`coding-agent` 将 CLI、交互模式以及这些能力组合起来。阅读源码时应沿着 `coding-agent` → `agent` → `ai` 的依赖方向追踪，不要只从 TUI 的显示文本倒推运行逻辑。

## Go 与 Java 对照

| 开发动作 | Go | Java |
| --- | --- | --- |
| 当前目录 | `os.Getwd()` | `Path.of("").toAbsolutePath()` |
| 依赖安装 | `go mod download` | Maven dependency resolution |
| 指定测试 | `go test -run` | `mvn -Dtest=... test` |
| 子进程 | `exec.CommandContext` | `ProcessBuilder` |
| 取消 | `context.Context` | `Future`/interrupt |

## 实验

1. 记录 `git rev-parse HEAD` 和 `git remote -v`，确认正在研究的 commit。
2. 从临时 cwd 执行 `pi-test.sh`，验证 Pi 使用调用者的工作目录。
3. 在临时分支中比较通过 `src/config.ts` 和直接使用 `__dirname` 读取资源的差异，然后恢复修改。
4. 用不含秘密的测试运行 `/debug`，检查日志中的 TUI 行和最近 messages。
5. 先执行指定测试，再执行非 LLM 测试，分别记录退出码。

## 小结

本页的核心是分清源码入口、当前工作目录、package asset 路径、配置目录和测试边界。`pi-test.sh` 解决源码启动，`src/config.ts` 解决资源定位，`/debug` 提供运行观察，指定测试则用于快速验证改动。
