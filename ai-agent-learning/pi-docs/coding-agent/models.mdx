# 自定义 Models

> 本页是 `packages/coding-agent/docs/models.md` 的中文参考译本，研究 commit 为 `853a80d26c90a14c1886f0ebb8ffaae133ca2185`。API 名称、命令、路径、配置字段和代码标识符保留原样。

## 中文导读

`~/.pi/agent/models.json` 是把自定义 Provider 和模型目录接入 Pi 的配置入口。
它适合 Ollama、vLLM、LM Studio、公司代理和自建网关。
本文件描述“Pi 怎样理解一个模型”，不是把任意 HTTP 服务自动变成兼容服务的转换器。

Provider 层保存共用信息：`baseUrl`、`api`、认证、headers 和 provider 级 `compat`。
Model 层保存单个模型的信息：`id`、展示名、输入类型、thinking 能力、上下文窗口、输出上限、价格和 model 级兼容字段。
配置读取、模型选择器、实际 API 请求和认证可用性是相互关联但不同的阶段。
读完本页后，应能从一个 `models.json` 条目追踪到 `/model`、LLM 请求和错误处理。

## 你会学到什么

1. 用最小配置注册一个本地 OpenAI-compatible 服务。
2. 区分 Provider 默认值和 model 覆盖值。
3. 理解 `apiKey`、`/login`、`auth.json`、环境变量和 shell command 的优先级。
4. 配置 `reasoning`、`thinkingLevelMap`、`samplingParams` 和兼容性字段。
5. 为内置 Provider 增加自定义模型，而不是误删内置模型。
6. 用 `modelOverrides` 修改一个已有模型的路由或上下文窗口。
7. 根据 401、空模型列表、坏 JSON、thinking 不兼容和 context overflow 定位问题。

<Note>

模型能出现在配置文件中，不等于它能被选择，也不等于它能成功完成请求。
Pi 至少还要处理认证可用性、API 适配器、模型能力和服务端实际行为。

</Note>

## 源码级中文译文

### 1. 最小配置：先让一个模型可见

对于 Ollama、LM Studio 和 vLLM，单个 model 通常只需要 `id`。
Provider 仍需要 `baseUrl`、`api`、`apiKey` 和 `models`。

```json
{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "models": [
        { "id": "llama3.1:8b" },
        { "id": "qwen2.5-coder:7b" }
      ]
    }
  }
}
```

这份 JSON 的输入是一个名为 `ollama` 的 Provider 配置。
`baseUrl` 是请求服务的基础地址，不要把它误写成浏览器页面地址。
`api` 决定 Pi 使用哪个请求和流解析器；本例选择 OpenAI Chat Completions 形状。
`models` 是该 Provider 提供的模型条目数组，`id` 会原样传给 API。

Ollama 会忽略 `apiKey`，所以这里的 `ollama` 是占位值。
Pi 仍会把“存在认证配置”作为模型可用性判断的一部分。
如果不提供任何认证配置，模型可能已经从文件加载，却不会出现在 `/model` 或 `--list-models` 的可用列表中。
解决办法有三种：保留占位值、用 `/login` 为该 Provider 保存 key，或在选择模型时使用 `--api-key`。

> 译者注：这里的“需要 key”不是说 Ollama 真会校验这个值，而是选择器的可用性门槛。
> 本地服务可以接受任意占位字符串，但生产代理不能照搬这个做法，否则会把真实认证问题隐藏起来。

### 2. OpenAI-compatible 服务的角色和 reasoning 差异

有些兼容服务不认识 reasoning-capable 请求使用的 `developer` role。
这时在 Provider 或 model 的 `compat` 中把 `supportsDeveloperRole` 设为 `false`。
Pi 会把 system prompt 作为 `system` message 发送，而不是发送 `developer` message。

如果服务也不支持 `reasoning_effort`，同时把 `supportsReasoningEffort` 设为 `false`。
Provider 级配置作用于全部模型；model 级配置可以为一个特殊模型恢复或关闭能力。

```json
{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "compat": {
        "supportsDeveloperRole": false,
        "supportsReasoningEffort": false
      },
      "models": [
        {
          "id": "gpt-oss:20b",
          "reasoning": true
        }
      ]
    }
  }
}
```

`reasoning: true` 只表示这个模型在目录中具有 extended thinking 能力。
它不会替服务端补上缺失的参数，也不会保证模型支持所有 thinking level。
真正发送哪些字段，还要看 `thinkingLevelMap` 和 `compat`。

> 译者注：Provider compatibility 是“协议翻译提示”，不是能力模拟器。
> 如果后端没有实现 thinking，写 `reasoning: true` 只会让请求更容易失败，不能让模型突然获得推理能力。

### 3. 完整模型条目

需要控制展示名、上下文和价格时，可以写出完整条目。

```json
{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "models": [
        {
          "id": "llama3.1:8b",
          "name": "Llama 3.1 8B (Local)",
          "reasoning": false,
          "input": ["text"],
          "contextWindow": 128000,
          "maxTokens": 32000,
          "cost": { "input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0 }
        }
      ]
    }
  }
}
```

`id` 是发送给 Provider 的真实模型标识。
`name` 是给人看的标签，也参与 `--model` 的匹配，但不替换状态栏里的 model id。
`reasoning` 控制模型目录对 thinking 能力的声明。
`input` 描述允许的输入类型，`["text", "image"]` 不代表服务端接受任意图片格式。
`contextWindow` 是上下文 token 上限；`maxTokens` 是一次输出的最大 token 数。
`cost` 使用每百万 token 的费率，零价格适合本地模型，但不代表网络代理没有费用。

每次打开 `/model` 时，Pi 会重新加载 `models.json`。
这意味着修改配置后不需要重启当前 session，但选择器重载不等于已经发送过的请求会改变。
已经创建的运行仍可能携带当时解析出的模型设置。

### 4. Google AI Studio 自定义模型

`google-generative-ai` 的自定义模型必须提供 `baseUrl`。
下面的条目增加一个 Gemma 模型，并声明它接受文本和图片。

```json
{
  "providers": {
    "my-google": {
      "baseUrl": "https://generativelanguage.googleapis.com/v1beta",
      "api": "google-generative-ai",
      "apiKey": "$GEMINI_API_KEY",
      "models": [
        {
          "id": "gemma-4-31b-it",
          "name": "Gemma 4 31B",
          "input": ["text", "image"],
          "contextWindow": 262144,
          "reasoning": true
        }
      ]
    }
  }
}
```

`$GEMINI_API_KEY` 是环境变量引用，不是字面量字符串。
Pi 在需要读取认证时解析它；缺失变量会让值保持 unresolved。
Google API 使用自己的请求和流协议，所以不能因为模型名字相似就改成 `openai-completions`。

### 5. 支持的 API 与选择原则

当前配置支持四种 `api`：

| `api` | 实际协议 | 适用场景 |
| --- | --- | --- |
| `openai-completions` | OpenAI Chat Completions | 大多数 OpenAI-compatible 服务 |
| `openai-responses` | OpenAI Responses API | 需要 Responses 事件和字段的服务 |
| `anthropic-messages` | Anthropic Messages API | Anthropic 或兼容代理 |
| `google-generative-ai` | Google Generative AI | Google AI Studio 和兼容服务 |

可以在 Provider 层设置默认 `api`，也可以在 model 层覆盖它。

> 译者注：`api` 是 wire protocol 选择，而不是 Provider 名称。
> “这个服务号称 OpenAI-compatible”只说明它可能兼容其中一部分字段，仍要用 fake server 或受限请求验证角色、tool call、stream 和 usage。

### 6. Provider 配置字段

| 字段 | 作用 |
| --- | --- |
| `baseUrl` | API endpoint 基础地址 |
| `api` | 默认 API 适配器 |
| `apiKey` | API key 的解析配置，可省略 |
| `oauth` | 动态 OAuth Provider 类型，目前支持 `radius` |
| `headers` | 每次请求携带的自定义 header |
| `authHeader` | 为 true 时自动发送 `Authorization: Bearer <apiKey>` |
| `models` | 自定义模型数组 |
| `modelOverrides` | 对内置或 Extension 注册模型做单模型覆盖 |
| `compat` | Provider 级协议兼容开关 |

自定义 Provider 通常需要 `baseUrl` 和 `api`，两者可以分别放在 Provider 或 model 层。
`apiKey` 不是加载文件的硬性条件；没有 key 时模型可以进入目录，但会保持不可用。
可用认证来源包括 `/login`、`auth.json`、CLI `--api-key` 和 Provider 的 `apiKey`。

### 7. 值解析：command、环境变量和字面量

`apiKey` 与 `headers` 支持三种动态写法和一种静态写法。
解析规则必须区分命令执行、环境变量插值、转义和普通文本。

#### Shell command

值以 `!` 开头时，整个值作为 shell command 执行，stdout 作为认证值。

```json
"apiKey": "!security find-generic-password -ws 'anthropic'"
"apiKey": "!op read 'op://vault/item/credential'"
```

输入是命令字符串，输出是命令的标准输出。
命令失败、退出码非零或 stdout 不符合预期都会使认证解析失败。
这类 command 在请求时解析，Pi 不会替你提供 TTL、旧值复用或崩溃恢复。

如果 command 慢、昂贵、有限流，或者临时失败时应该继续使用旧值，请自己写 wrapper。
wrapper 可以实现缓存、TTL、重试和旧值策略，因为只有业务方知道这些语义。

#### Environment interpolation

`$ENV_VAR` 或 `${ENV_VAR}` 读取环境变量，也可以插入更长的字面量。

```json
"apiKey": "$MY_API_KEY"
"apiKey": "${KEY_PREFIX}_${KEY_SUFFIX}"
```

`$FOO_BAR` 表示完整变量名 `FOO_BAR`。
如果 `BAR` 是普通文本，应写成 `${FOO}_BAR`。
缺失环境变量会使值 unresolved，不要默认为空字符串然后继续请求。

#### Escapes 与 literal

`$$` 输出一个字面量 `$`；`$!` 输出一个字面量 `!`，不会触发 command。

```json
"apiKey": "$$literal-dollar-prefix"
"apiKey": "$!literal-bang-prefix"
```

普通大写字符串如 `MY_API_KEY` 是字面量，不会自动查找环境变量。
只有 `$MY_API_KEY` 才表示环境变量引用。

`/model` 的可用性检查只看认证是否存在，不执行 shell command。
这是避免打开选择器就运行任意外部命令的重要边界。

> 译者注：把 secret 写成 `!command` 等于允许 Pi 在请求时执行一个外部程序。
> 这不是“安全的 Secret Manager”本身；要限制命令、环境、输出长度和日志泄露，wrapper 仍需要自己的安全设计。

### 8. 自定义 headers

```json
{
  "providers": {
    "custom-proxy": {
      "baseUrl": "https://proxy.example.com/v1",
      "apiKey": "$MY_API_KEY",
      "api": "anthropic-messages",
      "headers": {
        "x-portkey-api-key": "$PORTKEY_API_KEY",
        "x-secret": "!op read 'op://vault/item/secret'"
      },
      "models": [...]
    }
  }
}
```

header 值沿用与 `apiKey` 相同的解析规则。
它们适合 corporate proxy、租户标识和网关路由，但不应把 token 打进调试日志。
请求级显式 header 的优先级高于自动认证 header；如果代理要求非 Bearer 认证，应使用自定义 header 而不是误改 Model Loop。

### 9. Model 配置字段

| 字段 | 必需 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `id` | 是 | — | 传给 API 的模型标识 |
| `name` | 否 | `id` | 人类可读名称，用于匹配和次级展示 |
| `api` | 否 | Provider 的 `api` | 单模型 API 覆盖 |
| `reasoning` | 否 | `false` | 是否支持 extended thinking |
| `thinkingLevelMap` | 否 | 未设置 | Pi level 到 Provider 值的映射 |
| `input` | 否 | `["text"]` | 输入类型，可增加 `image` |
| `contextWindow` | 否 | `128000` | 上下文 token 数 |
| `maxTokens` | 否 | `16384` | 输出 token 上限 |
| `samplingParams` | 否 | 未设置 | 原样合并进请求体的采样参数 |
| `cost` | 否 | 全部零 | 每百万 token 费率及可选 tier |
| `compat` | 否 | Provider 的 `compat` | model 级兼容覆盖 |

配置字段中的默认值是目录层默认，不代表每个 Provider 服务端的默认值。
尤其要检查 `contextWindow` 和 `maxTokens`，错误的过大值会导致服务端拒绝请求，错误的过小值会过早截断回答。

#### Cost tiers

一个 cost tier 是一组完整的替代费率。
当一次请求的总输入量 `input + cacheRead + cacheWrite` 超过 `inputTokensAbove` 时，整次请求使用该 tier。
多个 tier 同时匹配时，使用 threshold 最高的那个，而不是分别为不同 token 段相加。

```json
{
  "cost": {
    "input": 5,
    "output": 30,
    "cacheRead": 0.5,
    "cacheWrite": 6.25,
    "tiers": [
      {
        "inputTokensAbove": 272000,
        "input": 10,
        "output": 45,
        "cacheRead": 1,
        "cacheWrite": 12.5
      }
    ]
  }
}
```

价格只影响 usage/cost 计算，不会控制 Provider 是否接受请求。
`/model`、`--list-models` 和 footer 按 model `id` 展示条目；`name` 主要用于匹配和次级说明。

> 译者注：费率 tier 不是“超过阈值的 token 用另一种价格”，而是整次请求选择一组费率。
> 这会直接影响账务审计，因此测试时要覆盖刚好等于阈值、刚超过阈值和多个 tier 命中的情况。

### 10. Sampling parameters

`samplingParams` 是自由形状对象，会原样合并到该 model 的每个请求体中。
它发生在 Pi 设置自身字段之后，因此同名 key 会覆盖请求级字段。

```json
{
  "id": "deepseek-v4-flash",
  "samplingParams": {
    "temperature": 1.0,
    "top_p": 0.95,
    "top_k": 0,
    "min_p": 0.0
  }
}
```

它只作用于 `openai-completions`、`openai-responses` 和 `azure-openai-responses`。
其他 API 会忽略它。
适合传递 Pi 没有专门建模的服务端字段，如 llama.cpp 的 `min_p` 或 vLLM 的 `top_k`。

因为自定义 key 会覆盖 Pi 的命名字段，建议一个模型只保留一个 sampling truth。
在 `modelOverrides` 中，`samplingParams` 按 key 与基础模型合并，而不是把整个对象盲目替换。

不要把固定 thinking token cap 和 `thinkingBudgets` 混为一谈。
固定 cap 可能不给最终答案留下空间；需要随 thinking level 变化时，应使用 `compat.thinkingTokenBudgetField` 或其别名。

### 11. Thinking level map

`thinkingLevelMap` 的 key 是 Pi 的 `off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`。
映射允许有空洞，例如模型可以支持 `high` 和 `max`，但不支持 `xhigh`。

| 值 | 语义 |
| --- | --- |
| 省略 | `high` 前的标准级别使用 Provider 默认映射；`xhigh` 和 `max` 不支持 |
| 字符串 | 该级别支持，并把字符串发送给 Provider |
| `null` | 该级别不支持，在 UI 中隐藏、跳过或 clamp |

只支持 off、high、max 的模型可以这样声明：

```json
{
  "id": "deepseek-v4-pro",
  "reasoning": true,
  "thinkingLevelMap": {
    "minimal": null,
    "low": null,
    "medium": null,
    "high": "high",
    "xhigh": null,
    "max": "max"
  }
}
```

如果模型无法关闭 thinking，可以只禁用 `off`：

```json
{
  "id": "always-thinking-model",
  "reasoning": true,
  "thinkingLevelMap": {
    "off": null
  }
}
```

旧配置中的 `compat.reasoningEffortMap` 应迁移到 model-level `thinkingLevelMap`。
对于不应出现在 UI 的级别，使用 `null`，不要用一个似是而非的 Provider 字符串。

> 译者注：这里的 `null` 是“能力不存在/不展示”，不是“把空值发送给 Provider”。
> 初学者若把 `null` 和省略混用，会看到选择器里出现不可用 level，或让服务端收到错误参数。

### 12. 覆盖内置 Provider

只想让内置 Provider 走代理时，不要重新列出全部模型。

```json
{
  "providers": {
    "anthropic": {
      "baseUrl": "https://my-proxy.example.com/v1"
    }
  }
}
```

省略 `models` 时，内置 Anthropic 模型仍保留。
已有 OAuth 或 API key 认证也继续工作。

如果还要向内置 Provider 增加模型，加入 `models`：

```json
{
  "providers": {
    "anthropic": {
      "baseUrl": "https://my-proxy.example.com/v1",
      "apiKey": "$ANTHROPIC_API_KEY",
      "api": "anthropic-messages",
      "models": [...]
    }
  }
}
```

合并规则是：保留内置模型；按 Provider 内的 `id` upsert 自定义模型；同 id 会替换内置模型；新 id 会并列增加。
因此“覆盖 URL”和“重定义模型数组”是两个不同操作。

### 13. 单模型 `modelOverrides`

`modelOverrides` 适合改变一个内置模型或 Extension 注册模型，而不替换整个 Provider 的目录。

```json
{
  "providers": {
    "openrouter": {
      "modelOverrides": {
        "anthropic/claude-sonnet-4": {
          "name": "Claude Sonnet 4 (Bedrock Route)",
          "compat": {
            "openRouterRouting": {
              "only": ["amazon-bedrock"]
            }
          }
        }
      }
    }
  }
}
```

可覆盖字段包括 `name`、`reasoning`、`thinkingLevelMap`、`input`、部分 `cost`、`contextWindow`、`maxTokens`、按 key 合并的 `samplingParams`、`headers` 和 `compat`。
未知 model id 会被忽略。
Provider 级 `baseUrl`/`headers` 可以和 model override 同时使用。
如果同时定义 `models`，自定义模型在内置 override 之后合并；同 id 的自定义条目会替换最终内置条目。

OpenAI GPT-5.6 Sol、Terra、Luna 默认使用 `272000` context window，以保持短上下文价格 tier。
若要使用 1.05M 上下文，必须逐模型把 `contextWindow` 改为 `1050000`。
超过 272K 的请求使用长上下文费率，且是整次请求的费率。

> 译者注：override 的优点是小范围改变配置，风险是容易误以为未知 id 已生效。
> 实践时先用 `--list-models` 和一次打印请求的 fake server 验证“匹配到了哪个 id、最终字段是什么”。

### 14. Anthropic Messages 兼容性

使用 `api: "anthropic-messages"` 的 Provider 或代理，需要用 `compat` 描述 Anthropic-specific 行为。

默认情况下 Pi 为每个 tool 发送 `eager_input_streaming: true`。
如果代理拒绝该字段，把 `supportsEagerToolInputStreaming` 设为 `false`。
Pi 会移除 `tools[].eager_input_streaming`，并在启用工具的请求中发送 legacy `fine-grained-tool-streaming-2025-05-14` beta header。

某些 Anthropic 模型要求 adaptive thinking：`thinking.type: "adaptive"` 加 `output_config.effort`，而不是旧的 budget payload。
内置模型会自动设置；自定义 Provider 或 alias 路由到这些模型时，要设置 `forceAdaptiveThinking: true`。

有些兼容服务返回空 thinking signature，却要求 replay 时保留 thinking block。
只有这类服务才设置 `allowEmptySignature: true`；真实 Anthropic 会拒绝空 signature。

内置 Anthropic 模型在 metadata 中启用 `supportsStrictTools`。
自定义兼容模型只有在 endpoint 接受严格 JSON Schema tool definition 时才设为 true。

```json
{
  "providers": {
    "anthropic-proxy": {
      "baseUrl": "https://proxy.example.com",
      "api": "anthropic-messages",
      "apiKey": "$ANTHROPIC_PROXY_KEY",
      "compat": {
        "supportsEagerToolInputStreaming": false,
        "supportsLongCacheRetention": true,
        "forceAdaptiveThinking": true,
        "allowEmptySignature": true
      },
      "models": [
        {
          "id": "claude-opus-4-7",
          "reasoning": true,
          "input": ["text", "image"]
        }
      ]
    }
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `supportsEagerToolInputStreaming` | 是否接受每个 tool 的 eager 输入流，默认 true |
| `supportsLongCacheRetention` | 是否接受 `cache_control.ttl: "1h"`，默认 true |
| `sendSessionAffinityHeaders` | caching 开启时是否根据 session id 发送 `x-session-affinity` |
| `supportsCacheControlOnTools` | 是否接受 tool definition 上的 Anthropic cache markers |
| `forceAdaptiveThinking` | 是否强制 adaptive thinking，默认 false |
| `allowEmptySignature` | 是否 replay 空 thinking signature，默认 false |
| `supportsStrictTools` | 是否接受严格 JSON Schema tool definitions，默认 false |

### 15. OpenAI 兼容性字段

Provider 级 `compat` 为该 Provider 的所有模型提供默认值。
model 级 `compat` 覆盖 Provider 默认值；两者不是简单的“model 对象完全替换”。

```json
{
  "providers": {
    "local-llm": {
      "baseUrl": "http://localhost:8080/v1",
      "api": "openai-completions",
      "compat": {
        "supportsUsageInStreaming": false,
        "maxTokensField": "max_tokens"
      },
      "models": [...]
    }
  }
}
```

下面是常用字段的含义：

| 字段 | 解决的问题 |
| --- | --- |
| `supportsStore` | 是否支持 `store` 字段 |
| `supportsDeveloperRole` | 发送 `developer` 还是 `system` |
| `supportsReasoningEffort` | 是否支持 `reasoning_effort` |
| `supportsUsageInStreaming` | 是否支持流末尾 usage |
| `supportsFinishReason` | 流事件是否带 `finish_reason`；false 时 Pi 推断 stop/toolUse |
| `maxTokensField` | 使用 `max_completion_tokens` 还是 `max_tokens` |
| `requiresToolResultName` | tool result message 是否要带 name |
| `requiresAssistantAfterToolResult` | tool result 后 user message 前是否插入 assistant |
| `requiresThinkingAsText` | 是否把 thinking block 转为纯文本 |
| `requiresReasoningContentOnAssistantMessages` | replay assistant 时是否补空 reasoning_content |
| `thinkingFormat` | 使用哪一种 Provider thinking 参数格式 |
| `chatTemplateKwargs` | chat-template 的可配置模板参数 |
| `chatTemplateArgs` | baseten 模板的参数 |
| `thinkingTokenBudgetField` | 发送 thinking token 上限的顶层字段 |
| `supportsThinkingTokenBudget` | vLLM 字段的兼容别名 |
| `cacheControlFormat` | 是否用 Anthropic cache_control 标记 |
| `sendSessionAffinityHeaders` | 是否发送 session affinity header |
| `sessionAffinityFormat` | OpenAI/OpenRouter affinity header 形状 |
| `supportsStrictMode` | 是否支持严格 function schema |
| `supportsOpenAIGrammarTools` | 是否支持 Lark/regex grammar tools |
| `deferredToolsMode` | 是否使用 Provider-specific deferred tool serialization |
| `supportsLongCacheRetention` | 是否支持长 cache retention |
| `openRouterRouting` | OpenRouter 的 provider routing 对象 |
| `vercelGatewayRouting` | Vercel AI Gateway 的 provider selection |

`thinkingFormat` 不是一个可随意填写的标签，它决定 payload 的具体结构：
`openrouter` 使用 `reasoning: { effort }`；
`together` 使用 `reasoning: { enabled }`，并可在能力允许时发送 `reasoning_effort`；
`qwen` 使用顶层 `enable_thinking`；
`qwen-chat-template` 用于需要 `chat_template_kwargs.enable_thinking` 和 `preserve_thinking` 的本地 Qwen 服务；
`chat-template` 用于 vLLM/Hugging Face 模板；
`baseten` 使用 `chatTemplateArgs`，也可能支持顶层 `reasoning_effort`。

`thinkingTokenBudgetField` 独立于 `thinkingFormat`。
不要在生成的 Qwen catalog 上启用它，因为这些模型已经发送 `reasoning_effort`，DashScope 会拒绝同时出现 `thinking_budget`。
`cacheControlFormat: "anthropic"` 适合通过文本内容和 tool definition 的 `cache_control` 暴露 Anthropic 风格缓存的 OpenAI-compatible 服务。

### 16. 典型排错路径

#### 模型不在 `/model`

先确认 JSON 是合法的，且文件位于 `~/.pi/agent/models.json`。
再确认 Provider 名称、`models` 数组、model `id` 和认证配置。
没有认证时，模型可能已加载但保持 unavailable。
记住 `/model` 可用性检查不执行 `!command`，所以 command 本身失败要到真正请求时才发现。

#### 401 或 403

检查 `apiKey` 是字面量还是 `$ENV_VAR`，环境变量是否存在。
检查 `/login` 保存的 Provider 名称是否与配置一致。
检查 `authHeader` 是否适合该代理；非 Bearer 网关应使用正确的 `headers`。
不要把 secret 放进 `models.json` 后提交到仓库。

#### 404、空 choices 或坏 JSON

404 通常说明 `baseUrl` 与 API path 组合错误，或选错 `api`。
200 但 `choices: []` 仍是协议错误，不是成功的空回答。
坏 JSON、缺少 `message`、缺少 tool call 字段都应在 adapter 层报告，不能让 Loop 继续使用半成品。

#### Tool call、thinking 或 streaming 失败

先用单工具和 fake server 验证请求体。
OpenAI-compatible 服务检查 `supportsDeveloperRole`、`maxTokensField`、`supportsUsageInStreaming` 和 `supportsFinishReason`。
Anthropic-compatible 服务检查 eager tool streaming、strict tools、adaptive thinking 和 signature replay。
断流时区分 provider error、用户 abort 和正常 stop；不要把所有断流都改写成 final answer。

#### Context overflow

确认 `contextWindow` 没有比服务端真实上限更大。
检查 `maxTokens` 是否给输出保留空间。
Pi 的 overflow recovery 只对它识别的 overflow 生效；不要把 429 或普通 5xx 错误标为 context overflow。

### 17. Java/Go 对照

| 责任 | Pi/TypeScript | Go | Java |
| --- | --- | --- | --- |
| Provider 配置 | provider/model object | struct + `Model` interface | record + `Model` interface |
| 请求取消 | `AbortSignal` | `context.Context` | `CancellationToken` + interruption |
| 流事件 | `AsyncIterable` | callback/channel | callback/`Flow` |
| 动态扩展 | Extension API | explicit registry | `ServiceLoader` |
| 认证值 | credential store + resolver | env/显式注入 | env/显式注入 |

Go/Java 示例只实现教学级的 OpenAI-compatible adapter。
它们不会复刻 Pi 所有 provider、OAuth 和 thinking compatibility。
学习时应把 `models.json` 当成“配置到统一边界的映射”，而不是直接把 JSON 拼进任意 HTTP 请求。

> 译者注：Java 的 `record` 很适合表示解析后的 model metadata，但认证解析仍应是独立的 resolver interface。
> Go 中可把兼容开关放在 struct 中，并让 HTTP adapter 根据它决定 JSON 字段，而不要让业务 Loop 判断 Provider 名称。

### 18. 实践实验：从本地服务到可验证配置

#### 实验目标

完成一个本地 Provider 的注册，并证明“目录可见”“认证可用”“请求协议正确”是三个不同断言。

#### 准备

准备一个 fake HTTP server，或本地 Ollama/LM Studio/vLLM。
先使用不产生费用的测试模型。
准备临时 `HOME` 或备份现有 `~/.pi/agent/models.json`，不要覆盖真实配置。

#### 步骤

1. 从最小配置开始，只写 `baseUrl`、`api`、`apiKey` 和一个 model `id`。
2. 执行 `pi --list-models`，记录模型是否出现以及显示的是 `id` 还是 `name`。
3. 打开 `/model`，修改 `name`，确认选择匹配和 footer 展示的差异。
4. 删除 `apiKey`，观察模型是否加载但变为 unavailable。
5. 把 key 改成 `$TEST_KEY`，分别设置和取消环境变量。
6. 把 key 改成 `$$literal` 和 `$!literal`，确认不会意外执行 command。
7. 让 fake server 检查 `model`、`messages`、`tools` 和 `stream` 字段。
8. 返回 200 加空 choices、坏 JSON、429 和 500，分别记录 adapter 的错误。
9. 添加 model-level `compat`，验证最终请求字段变化。
10. 添加 `modelOverrides`，确认未知 id 不会产生假覆盖。

#### 观察点

配置解析阶段不应执行 `/model` 检查中的 shell command。
请求阶段应使用正确的 API adapter 和认证 header。
`Tool Call` 的 JSON、thinking 字段和 usage 需要单独检查，不能只看 HTTP 状态码。

#### 预期结果

你能写出一张表：

| 阶段 | 证据 |
| --- | --- |
| 文件被读取 | JSON parse 成功 |
| 模型进入目录 | `--list-models` 能看到 id |
| 模型可选择 | 认证存在且 `/model` 显示可用 |
| 请求可用 | fake server 收到正确 path/header/body |
| Loop 可用 | assistant/tool result 能完成一轮闭环 |

#### 思考题

1. 为什么本地 Ollama 的 `apiKey` 可以是占位值，而公司代理不应该这样做？
2. Provider 级 `compat` 和 model 级 `compat` 同时存在时，怎样判断最终字段？
3. 如果模型条目 `id` 正确但 `api` 错误，错误最可能出现在哪一层？
4. 为什么 `contextWindow` 不能只照抄厂商营销页？
5. `modelOverrides` 的 unknown id 被忽略，为什么比静默创建一个新模型更安全？
6. `samplingParams` 覆盖了 Pi 自己的 `temperature` 后，谁是最终 source of truth？

## 翻译说明与初学者陷阱

1. `provider`、`model`、`api`、`compat`、`reasoning` 和 `thinking level` 是不同维度，不能互换。
2. `name` 是展示和匹配标签，`id` 才是发送给 API 的模型身份。
3. 加载成功、选择可用和请求成功必须分开测试。
4. `models` 数组会影响合并语义；只改 URL 时不要无意中重写模型目录。
5. `apiKey` 的 `$`、`!` 和普通文本具有不同解析规则。
6. `null`、省略和字符串在 `thinkingLevelMap` 中有三种不同语义。
7. `cost` 只负责计费估算，不会替你限制 token 或预算。
8. `compat` 解决已知协议差异，不应当被用来掩盖未知服务行为。

> 译者注：本页的配置示例都应先在隔离目录和 fake server 中验证。
> “能看到模型”是一个 UI/目录事实，“能安全完成 Tool Calling”还需要请求、响应、权限和错误路径测试。

## 小结

`models.json` 是 Provider/model 元数据与运行时请求之间的配置边界。
先确定 API 形状和认证，再填写模型能力、上下文、成本和兼容字段。
遇到问题时按“文件读取 → 目录可见 → 认证可用 → 请求协议 → Loop 结果”的顺序排查。

````markdown
For local models (Ollama, LM Studio, vLLM), only `id` is required per model:

```json
{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "models": [
        { "id": "llama3.1:8b" },

      ]
    }
  }

```

You can set `compat` at the provider level to apply to all models, or at the model level to override a specific model. This commonly applies to Ollama, vLLM, SGLang, and similar OpenAI-compatible servers.

```json
{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "compat": {
        "supportsDeveloperRole": false,
        "supportsReasoningEffort": false
      },
      "models": [
        {
          "id": "gpt-oss:20b",
          "reasoning": true
        }
      ]
    }
  }
}

## Provider Configuration

| Field | Description |
|-------|-------------|
| `baseUrl` | API endpoint URL |
| `api` | API type (see above) |
| `apiKey` | Optional API key config (see value resolution below). Omit it when auth is provided by `/login`/`auth.json` or CLI `--api-key`. |
| `oauth` | Dynamic OAuth provider type. Currently supports `"radius"`; requires the gateway `baseUrl`. |
| `headers` | Custom headers (see value resolution below) |
| `authHeader` | Set `true` to add `Authorization: Bearer <apiKey>` automatically |
| `models` | Array of model configurations |
| `modelOverrides` | Per-model overrides for built-in or extension-registered models on this provider |

For providers with `models`, non-built-in provider configs need `baseUrl` and an `api` value at either provider or model level. `apiKey` is not required to load the file: models become available when auth is configured through `/login`/`auth.json`, CLI `--api-key`, or provider `apiKey`. If no auth is configured, the models load but stay unavailable in `/model` and `--list-models`.

### Value Resolution

The `apiKey` and `headers` fields support command execution, environment interpolation, and literals:

- **Shell command:** `"!command"` at the start executes the whole value as a command and uses stdout
  ```json
  "apiKey": "!security find-generic-password -ws 'anthropic'"
  "apiKey": "!op read 'op://vault/item/credential'"
  ```
- **Environment interpolation:** `"$ENV_VAR"` or `"${ENV_VAR}"` uses the value of the named variable. Interpolation works inside larger literals.
  ```json
  "apiKey": "$MY_API_KEY"
  "apiKey": "${KEY_PREFIX}_${KEY_SUFFIX}"
  ```
  `$FOO_BAR` is the variable `FOO_BAR`; use `${FOO}_BAR` when `BAR` is literal text. Missing environment variables make the value unresolved.
- **Escapes:** `"$$"` emits a literal `"$"`; `"$!"` emits a literal `"!"` without triggering command execution.
  ```json
  "apiKey": "$$literal-dollar-prefix"
  "apiKey": "$!literal-bang-prefix"
  ```
- **Literal value:** Used directly. Plain uppercase strings such as `MY_API_KEY` are literals; use `$MY_API_KEY` for environment variables.
  ```json
  "apiKey": "sk-..."
  ```

For `models.json`, shell commands are resolved at request time. pi intentionally does not apply built-in TTL, stale reuse, or recovery logic for arbitrary commands. Different commands need different caching and failure strategies, and pi cannot infer the right one.

If your command is slow, expensive, rate-limited, or should keep using a previous value on transient failures, wrap it in your own script or command that implements the caching or TTL behavior you want.

`/model` availability checks use configured auth presence and do not execute shell commands.

## Model Configuration

| Field | Required | Default | Description |
|-------|----------|---------|-------------|
| `id` | Yes | — | Model identifier (passed to the API) |
| `name` | No | `id` | Human-readable model label. Used for matching (`--model` patterns) and shown as secondary model detail text. |
| `api` | No | provider's `api` | Override provider's API for this model |
| `reasoning` | No | `false` | Supports extended thinking |
| `thinkingLevelMap` | No | omitted | Maps pi thinking levels to provider values and marks unsupported levels (see below) |
| `input` | No | `["text"]` | Input types: `["text"]` or `["text", "image"]` |
| `contextWindow` | No | `128000` | Context window size in tokens |
| `maxTokens` | No | `16384` | Maximum output tokens |
| `samplingParams` | No | omitted | Sampling parameters merged verbatim into every request body (see below) |
| `cost` | No | all zeros | Per-million-token rates with optional request-wide input pricing tiers |
| `compat` | No | provider `compat` | Provider compatibility overrides. Merged with provider-level `compat` when both are set. |

A cost tier supplies a complete alternate rate set and applies to the full request when total input usage (`input + cacheRead + cacheWrite`) exceeds `inputTokensAbove`. When multiple tiers match, the highest threshold wins.

```json
{
  "cost": {
    "input": 5,
    "output": 30,
    "cacheRead": 0.5,
    "cacheWrite": 6.25,
    "tiers": [
      {
        "inputTokensAbove": 272000,
        "input": 10,
        "output": 45,
        "cacheRead": 1,
        "cacheWrite": 12.5
      }
    ]
  }
}
```

Current behavior:
- `/model`, `--list-models`, and the interactive footer display entries by model `id`.
- The configured `name` is used for model matching and secondary model detail text. It does not replace the footer/status-bar model id.

### Sampling Parameters

`samplingParams` is a free-form object merged verbatim into every request body for the model, after the fields pi sets itself, so its keys win. Use it to send sampling parameters pi does not model — including server-specific ones like llama.cpp's `min_p` or vLLM's `top_k`:

```json
{
  "id": "deepseek-v4-flash",
  "samplingParams": {
    "temperature": 1.0,
    "top_p": 0.95,
    "top_k": 0,
    "min_p": 0.0
  }
}
```

Only OpenAI-compatible APIs apply it (`openai-completions`, `openai-responses`, `azure-openai-responses`); other APIs ignore it. Keys override pi's named request fields (for example a `temperature` key here beats the request-level temperature), so prefer it as the single source of sampling truth for a model. In `modelOverrides`, `samplingParams` merges per key with the base model's value.

A constant thinking-token cap can go here too, but it will not follow `thinkingBudgets` or leave room for the answer. Prefer `compat.thinkingTokenBudgetField` (or the `supportsThinkingTokenBudget` alias) for that.

### Thinking Level Map

Use `thinkingLevelMap` on a model to describe model-specific thinking controls. Keys are pi thinking levels: `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. Maps may contain holes; for example, a model can expose `high` and `max` without exposing `xhigh`.

Values are tristate:

| Value | Meaning |
|-------|---------|
| omitted | Standard levels through `high` use the provider's default mapping; extended `xhigh` and `max` levels are unsupported |
| string | Level is supported and this value is sent to the provider |
| `null` | Level is unsupported and hidden/skipped/clamped away |

Example for a model that only supports off, high, and max reasoning:

```json
{
  "id": "deepseek-v4-pro",
  "reasoning": true,
  "thinkingLevelMap": {
    "minimal": null,
    "low": null,
    "medium": null,
    "high": "high",
    "xhigh": null,
    "max": "max"
  }
}
```

Example for a model where thinking cannot be disabled:

```json
{
  "id": "always-thinking-model",
  "reasoning": true,
  "thinkingLevelMap": {
    "off": null
  }
}
```

Migration: older configs that used `compat.reasoningEffortMap` should move that mapping to model-level `thinkingLevelMap`. Use `null` for levels that should not appear in the UI.

## Overriding Built-in Providers

Route a built-in provider through a proxy without redefining models:

```json
{
  "providers": {
    "anthropic": {
      "baseUrl": "https://my-proxy.example.com/v1"
    }
  }
}
```

All built-in Anthropic models remain available. Existing OAuth or API key auth continues to work.

To merge custom models into a built-in provider, include the `models` array:

```json
{
  "providers": {
    "anthropic": {
      "baseUrl": "https://my-proxy.example.com/v1",
      "apiKey": "$ANTHROPIC_API_KEY",
      "api": "anthropic-messages",
      "models": [...]
    }
  }
}
```

Merge semantics:
- Built-in models are kept.
- Custom models are upserted by `id` within the provider.
- If a custom model `id` matches a built-in model `id`, the custom model replaces that built-in model.
- If a custom model `id` is new, it is added alongside built-in models.

## Per-model Overrides

Use `modelOverrides` to customize built-in models and matching extension-registered models without replacing the provider's full model list.

```json
{
  "providers": {
    "openrouter": {
      "modelOverrides": {
        "anthropic/claude-sonnet-4": {
          "name": "Claude Sonnet 4 (Bedrock Route)",
          "compat": {
            "openRouterRouting": {
              "only": ["amazon-bedrock"]
            }
          }
        }
      }
    }
  }
}
```

`modelOverrides` supports these fields per model: `name`, `reasoning`, `thinkingLevelMap`, `input`, `cost` (partial), `contextWindow`, `maxTokens`, `samplingParams` (merged per key), `headers`, `compat`.

Direct OpenAI GPT-5.6 Sol, Terra, and Luna default to a `272000` context window so requests remain within OpenAI's short-context pricing tier. To opt into OpenAI's 1.05M context window, increase it for each model you use:

```json
{
  "providers": {
    "openai": {
      "modelOverrides": {
        "gpt-5.6-sol": {
          "contextWindow": 1050000
        }
      }
    }
  }
}
```

The override preserves the built-in pricing metadata. Requests with more than 272K total input tokens use GPT-5.6's long-context rates for the entire request. Apply the same override to `gpt-5.6-terra` or `gpt-5.6-luna` when needed.

Behavior notes:
- `modelOverrides` are applied to built-in provider models and matching extension-registered provider models.
- Unknown model IDs are ignored.
- You can combine provider-level `baseUrl`/`headers` with `modelOverrides`.
- Overriding `name` changes model matching and secondary detail text only; the footer and primary model lists continue to show the model `id`.
- If `models` is also defined for a provider, custom models are merged after built-in overrides. A custom model with the same `id` replaces the overridden built-in model entry.

## Anthropic Messages Compatibility

For providers or proxies using `api: "anthropic-messages"`, use `compat` to control Anthropic-specific request compatibility.

By default pi sends per-tool `eager_input_streaming: true`. If a proxy or Anthropic-compatible backend rejects that field, set `supportsEagerToolInputStreaming` to `false`. Pi will omit `tools[].eager_input_streaming` and send the legacy `fine-grained-tool-streaming-2025-05-14` beta header for tool-enabled requests instead.

Some Anthropic models require adaptive thinking (`thinking.type: "adaptive"` plus `output_config.effort`) instead of the legacy budget-based thinking payload. Built-in models set this automatically. For custom providers or aliases that route to those models, set `forceAdaptiveThinking` to `true`.

Some Anthropic-compatible providers emit thinking blocks with empty signatures and still expect them on replay. Set `allowEmptySignature` to `true` only for those providers; real Anthropic rejects empty thinking signatures.

Built-in Anthropic models enable `supportsStrictTools` in their model metadata. Custom Anthropic-compatible models must set it to `true` when their endpoint accepts strict JSON-schema tool definitions.

```json
{
  "providers": {
    "anthropic-proxy": {
      "baseUrl": "https://proxy.example.com",
      "api": "anthropic-messages",
      "apiKey": "$ANTHROPIC_PROXY_KEY",
      "compat": {
        "supportsEagerToolInputStreaming": false,
        "supportsLongCacheRetention": true,
        "forceAdaptiveThinking": true,
        "allowEmptySignature": true
      },
      "models": [
        {
          "id": "claude-opus-4-7",
          "reasoning": true,
          "input": ["text", "image"]
        }
      ]
    }
  }
}
```

| Field | Description |
|-------|-------------|
| `supportsEagerToolInputStreaming` | Whether the provider accepts per-tool `eager_input_streaming`. Default: `true`. Set to `false` to omit that field and use the legacy fine-grained tool streaming beta header on tool-enabled requests. |
| `supportsLongCacheRetention` | Whether the provider accepts Anthropic long cache retention (`cache_control.ttl: "1h"`) when cache retention is `long`. Default: `true`. |
| `sendSessionAffinityHeaders` | Whether to send `x-session-affinity` from the session id when caching is enabled. Default: auto-detected for known providers. |
| `supportsCacheControlOnTools` | Whether the provider accepts Anthropic-style `cache_control` markers on tool definitions. Default: `true`. |
| `forceAdaptiveThinking` | Whether to send adaptive thinking (`thinking.type: "adaptive"` plus `output_config.effort`) for this model. Built-in adaptive models set this automatically. Default: `false`. |
| `allowEmptySignature` | Whether to replay empty thinking signatures as `signature: ""` instead of converting thinking to text. Default: `false`. |
| `supportsStrictTools` | Whether the provider accepts strict JSON-schema tool definitions. Default: `false`; built-in Anthropic models enable it in generated metadata. |

## OpenAI Compatibility

For providers with partial OpenAI compatibility, use the `compat` field.

- Provider-level `compat` applies defaults to all models under that provider.
- Model-level `compat` overrides provider-level values for that model.

```json
{
  "providers": {
    "local-llm": {
      "baseUrl": "http://localhost:8080/v1",
      "api": "openai-completions",
      "compat": {
        "supportsUsageInStreaming": false,
        "maxTokensField": "max_tokens"
      },
      "models": [...]
    }
  }
}
```

| Field | Description |
|-------|-------------|
| `supportsStore` | Provider supports `store` field |
| `supportsDeveloperRole` | Use `developer` vs `system` role |
| `supportsReasoningEffort` | Support for `reasoning_effort` parameter |
| `supportsUsageInStreaming` | Supports `stream_options: { include_usage: true }` (default: `true`) |
| `supportsFinishReason` | Whether streamed responses include `finish_reason`. When `false`, pi infers `stop` or `toolUse` when the stream ends. Default: `true`. |
| `maxTokensField` | Use `max_completion_tokens` or `max_tokens` |
| `requiresToolResultName` | Include `name` on tool result messages |
| `requiresAssistantAfterToolResult` | Insert an assistant message before a user message after tool results |
| `requiresThinkingAsText` | Convert thinking blocks to plain text |
| `requiresReasoningContentOnAssistantMessages` | Include empty `reasoning_content` on all replayed assistant messages when reasoning is enabled |
| `thinkingFormat` | Use `reasoning_effort`, `openrouter`, `deepseek`, `together`, `baseten`, `zai`, `qwen`, `chat-template`, or `qwen-chat-template` thinking parameters |
| `chatTemplateKwargs` | `chat_template_kwargs` values for `thinkingFormat: "chat-template"`; use `{ "$var": "thinking.enabled" }`, `{ "$var": "thinking.effort" }`, or `{ "$var": "thinking.budget" }` for pi-controlled thinking values |
| `chatTemplateArgs` | `chat_template_args` values for `thinkingFormat: "baseten"`; use `{ "$var": "thinking.enabled" }`, `{ "$var": "thinking.effort" }`, or `{ "$var": "thinking.budget" }` for pi-controlled thinking values |
| `thinkingTokenBudgetField` | Top-level request field used to cap reasoning tokens from `thinkingBudgets`, clamped so at least 1024 tokens remain for the answer. `"thinking_token_budget"` (vLLM), `"thinking_budget"` (Qwen/DashScope/SGLang), `"thinking_budget_tokens"` (llama.cpp). Off by default; not set on the generated catalog. |
| `supportsThinkingTokenBudget` | Alias for `thinkingTokenBudgetField: "thinking_token_budget"` (vLLM). Prefer `thinkingTokenBudgetField`. Default: `false`. |
| `cacheControlFormat` | Use Anthropic-style `cache_control` markers on the system prompt, last tool definition, and last user, assistant, or tool-result text content. Currently only `anthropic` is supported. |
| `sendSessionAffinityHeaders` | For `openai-completions`, send session-affinity headers from the session id when caching is enabled. Default: `false`. |
| `sessionAffinityFormat` | For `openai-completions` and `openai-responses`, the session-affinity header format: `openai` sends `session_id`/`x-client-request-id` (completions also `x-session-affinity`), `openai-nosession` omits the underscore-containing `session_id` header, `openrouter` sends `x-session-id`. Does not affect the `prompt_cache_key` body param. Default: auto-detected. |
| `supportsStrictMode` | Whether the provider accepts strict JSON-schema function tool definitions. Defaults depend on the API; built-in OpenAI models carry explicit capability metadata. |
| `supportsOpenAIGrammarTools` | Whether OpenAI-compatible APIs emit custom Lark/regex grammar tools. When `false`, grammar-constrained tools fall back to normal function tools. Default: `false`; the built-in model catalog enables it for GPT-5+ models on OpenAI, OpenAI Codex, Azure OpenAI, GitHub Copilot, opencode, and Cloudflare AI Gateway. |
| `deferredToolsMode` | Use provider-specific deferred tool serialization. Currently only `"kimi"` is supported for Kimi's OpenAI-compatible Chat Completions format. |
| `supportsLongCacheRetention` | Whether the provider accepts long cache retention when cache retention is `long`: `prompt_cache_retention: "24h"` for OpenAI prompt caching, or `cache_control.ttl: "1h"` when `cacheControlFormat` is `anthropic`. Default: `true`. |
| `openRouterRouting` | OpenRouter provider routing preferences. This object is sent as-is in the `provider` field of the [OpenRouter API request](https://openrouter.ai/docs/guides/routing/provider-selection). |
| `vercelGatewayRouting` | Vercel AI Gateway routing config for provider selection (`only`, `order`) |

`openrouter` uses `reasoning: { effort }`. `together` uses `reasoning: { enabled }` and also `reasoning_effort` when `supportsReasoningEffort` is enabled. `qwen` uses top-level `enable_thinking`. Use `qwen-chat-template` for local Qwen-compatible servers that require `chat_template_kwargs.enable_thinking` and `preserve_thinking`. Use `chat-template` for vLLM/Hugging Face chat templates that need configurable `chat_template_kwargs`, such as `chatTemplateKwargs: { "thinking": { "$var": "thinking.enabled" } }` for DeepSeek V3.x templates. Use `thinkingFormat: "baseten"` with `chatTemplateArgs` for providers that expose toggle controls through `chat_template_args` and optionally support top-level `reasoning_effort`.

`thinkingTokenBudgetField` is independent of `thinkingFormat`. Do not enable it on the generated Qwen catalog: those models already send `reasoning_effort`, and DashScope rejects `thinking_budget` together with `reasoning_effort`.

`cacheControlFormat: "anthropic"` is for OpenAI-compatible providers that expose Anthropic-style prompt caching through `cache_control` markers on text content and tool definitions.
````
