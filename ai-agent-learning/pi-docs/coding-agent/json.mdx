# JSON 事件流模式

> 本页根据 `packages/coding-agent/docs/json.md` 重新翻译，研究基线为 commit `853a80d26c90a14c1886f0ebb8ffaae133ca2185`。代码、字段名、事件值、路径和链接保持原样。

## 中文译文

```bash
pi --mode json "Your prompt"
```

该命令把所有会话事件以 JSON Lines（JSONL）写到 stdout。它适合接入其他工具或自定义 UI。每行都是一个独立 JSON 对象，因此消费端应逐行读取和解析，而不是等进程结束后把整个输出解析成一个数组。

## 事件类型

协议事件使用 `JsonAgentSessionEvent`。它与 [`AgentSessionEvent`](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/src/core/agent-session.ts) 对应，但流式消息更新不再携带不断增长的累计快照：

```typescript
type WithoutPartial<T> = T extends { partial: unknown } ? Omit<T, "partial"> : T;

type JsonAssistantMessageEvent<T> = T extends { type: "toolcall_start"; partial: unknown }
  ? WithoutPartial<T> & { id: string; toolName: string }
  : WithoutPartial<T>;

type JsonAgentSessionEvent =
  | Exclude<AgentSessionEvent, { type: "message_update" }>
  | {
      type: "message_update";
      usage: Usage;
      assistantMessageEvent: JsonAssistantMessageEvent<AssistantMessageEvent>;
    };
```

`WithoutPartial<T>` 是条件类型：有 `partial` 字段时用 `Omit` 删除它，没有时保留原类型。`JsonAssistantMessageEvent<T>` 对 `toolcall_start` 额外保留固定大小的 `id` 和 `toolName`。`JsonAgentSessionEvent` 排除旧的 `message_update`，再定义新的增量形式。

`queue_update` 在待处理的引导消息（steering）或后续消息（follow-up）队列发生变化时输出完整队列。`compaction_start` 和 `compaction_end` 同时覆盖手动和自动压缩。

其他基础事件来自 [`AgentEvent`](https://github.com/earendil-works/pi-mono/blob/main/packages/agent/src/types.ts)：

```typescript
type AgentEvent =
  // Agent lifecycle
  | { type: "agent_start" }
  | { type: "agent_end"; messages: AgentMessage[] }
  // Turn lifecycle
  | { type: "turn_start" }
  | { type: "turn_end"; message: AgentMessage; toolResults: ToolResultMessage[] }
  // Message lifecycle
  | { type: "message_start"; message: AgentMessage }
  | { type: "message_update"; message: AgentMessage; assistantMessageEvent: AssistantMessageEvent }
  | { type: "message_end"; message: AgentMessage }
  // Tool execution
  | { type: "tool_execution_start"; toolCallId: string; toolName: string; args: any }
  | { type: "tool_execution_update"; toolCallId: string; toolName: string; args: any; partialResult: any }
  | { type: "tool_execution_end"; toolCallId: string; toolName: string; result: any; isError: boolean };
```

这里有一个关键区别：模型输出的 `toolcall_start` 只说明模型开始提出工具调用，`tool_execution_start` 才表示运行时（Runtime）开始执行工具。参数校验、权限检查或工具本身都可能在之后失败。

## 消息类型

基础消息来自 [`packages/ai/src/types.ts`](https://github.com/earendil-works/pi-mono/blob/main/packages/ai/src/types.ts#L134)：

- `UserMessage`（第 134 行）：用户输入。
- `AssistantMessage`（第 140 行）：模型生成的消息，可能包含文本、思考内容或工具调用。
- `ToolResultMessage`（第 152 行）：Runtime 执行工具后返回给模型的结果。

Coding Agent 在 [`packages/coding-agent/src/core/messages.ts`](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/src/core/messages.ts#L29) 扩展：

- `BashExecutionMessage`（第 29 行）：bash 执行记录。
- `CustomMessage`（第 46 行）：扩展或宿主写入的自定义消息。
- `BranchSummaryMessage`（第 55 行）：分支导航产生的摘要。
- `CompactionSummaryMessage`（第 62 行）：上下文压缩产生的摘要。

这些消息都有明确的类型字段。消费端应根据 `type`、`role` 和具体字段分支，不要把所有对象强行压缩成只有 `content` 的结构。

## 输出格式

每一行都是 JSON 对象。第一行是会话头：

```json
{"type":"session","version":3,"id":"uuid","timestamp":"...","cwd":"/path"}
```

随后事件按实际运行过程输出：

```json
{"type":"agent_start"}
{"type":"turn_start"}
{"type":"message_start","message":{"role":"assistant","content":[],...}}
{"type":"message_update","usage":{...},"assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"Hello"}}
{"type":"message_end","message":{...}}
{"type":"turn_end","message":{...},"toolResults":[]}
{"type":"agent_end","messages":[...]}
```

`message_update` 只包含增量，不包含累计的 `message` 和 `assistantMessageEvent.partial`。顶层 `usage` 是 provider 最近报告的累计用量；如果 provider 只在完成时报告用量，中间值可能仍为零。消费者应按 `contentIndex` 和 `delta` 组合文本、思考内容或工具参数，并以 `message_end` 中的最终消息作为权威结果。

> 译者注：JSONL 的逐行协议不保证一次系统 `read` 恰好得到一行。Go 可以使用 `bufio.Scanner`，Java 可以使用 `BufferedReader.readLine()`；两者都还需要处理长行、EOF、子进程取消以及 stdout 背压。

## 示例

下面的命令只提取最终定稿的消息：

```bash
pi --mode json "List files" 2>/dev/null | jq -c 'select(.type == "message_end")'
```

`2>/dev/null` 将诊断信息从 stdout 协议中隔离出来，`jq -c` 则逐行输出紧凑 JSON。生产消费者还应结合进程退出码、`agent_end` 和 stderr 判断运行是否真正完成。

## Event Types

[`AgentSessionEvent`](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/src/core/agent-session.ts)

## Output Format

Each line is a JSON object. The first line is the session header:

```json
{"type":"session","version":3,"id":"uuid","timestamp":"...","cwd":"/path"}
```

Followed by events as they occur:

```json
{"type":"agent_start"}
{"type":"turn_start"}
{"type":"message_start","message":{"role":"assistant","content":[],...}}
{"type":"message_update","usage":{...},"assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"Hello"}}
{"type":"message_end","message":{...}}
{"type":"turn_end","message":{...},"toolResults":[]}
{"type":"agent_end","messages":[...]}
```

`message_update` records are delta-only. They omit both the cumulative `message` field and
`assistantMessageEvent.partial` to keep stream size linear. The top-level `usage` field contains
the latest cumulative provider-reported usage and may remain zero when a provider only reports
usage at completion. Use `contentIndex` and `delta` to assemble live text, thinking, or tool-call
arguments if needed. A `toolcall_start` event also includes the constant-sized `id` and `toolName`
fields. `message_end` contains the final authoritative message.
