## 中文译文

Pi package 是可共享的资源包，能够捆绑 extensions、skills、prompt templates 和 themes，通过 npm 或 git 分发。资源可以写在 `package.json` 的 `pi` manifest 中，也可以使用约定目录。安装第三方 package 前必须审查源码：Extension 在宿主进程中运行任意代码，Skill 也可能指示模型执行危险命令。

### 安装、更新与来源

常用命令是 `pi install npm:@foo/bar@1.0.0`、`pi install git:github.com/user/repo@v1`、HTTP URL 和本地绝对/相对路径；`pi remove` 删除声明，`pi list` 查看已安装包，`pi update --all` 同时更新 Pi、package 并校准 pinned git refs，`--extensions` 只更新资源，`--models` 只更新模型目录，`--self` 只更新 Pi。`pi -e`/`--extension` 只在当前运行临时安装，不写持久设置。默认写入 `~/.pi/agent/settings.json`，`-l` 写入项目 `.pi/settings.json`；项目启动前必须通过 trust。

npm spec 可以是 `npm:@scope/pkg@1.2.3` 或 `npm:pkg`。带版本的 spec 会固定并跳过普通更新；用户 package 在 `~/.pi/agent/npm/`，项目 package 在 `.pi/npm/`。`npmCommand` 可把查找/安装交给 `mise` 或 `asdf` wrapper。

git spec 支持 `git:github.com/user/repo@v1`、`git:git@github.com:user/repo@v1`、`https://` 和 `ssh://`；没有 `git:` 前缀时只能使用完整 protocol URL，有此前缀才允许 host/path shorthand。tag 或 commit ref 会固定，`pi update` 不主动移动 ref，但会把现有 clone 校准到配置的 ref。global clone 位于 `~/.pi/agent/git/<host>/<path>`，project clone 位于 `.pi/git/<host>/<path>`；CI 可设 `GIT_TERMINAL_PROMPT=0`，SSH 可用 `GIT_SSH_COMMAND` fail fast。Local path 不复制文件，按出现它的 settings 文件解析；目录按 package 规则，单文件可作为一个 extension。

### 创建与目录约定

在 `package.json` 加入 `pi` 字段和 `pi-package` keyword：`extensions`、`skills`、`prompts`、`themes` 的路径相对 package root，数组支持 glob、`!exclusions` 和直接列出 dot-prefixed 路径。没有 manifest 时，Pi 从 `extensions/`、`skills/`、`prompts/` 和 `themes/` 约定目录自动发现相应 `.ts`/`.js`、`SKILL.md`、`.md` 和 `.json`。Gallery 可添加 `video` 或 `image`，其中 MP4 会优先于图片。

Runtime 第三方依赖放 `dependencies`；Pi Core 会以 `peerDependencies` 提供 `@earendil-works/pi-ai`、`@earendil-works/pi-agent-core`、`@earendil-works/pi-coding-agent`、`@earendil-works/pi-tui` 和 `typebox`，这些不应打包。其他 Pi package 要放入 `dependencies` 与 `bundledDependencies`，并把 `node_modules/` 下的资源列入 manifest；Pi 为 package 使用分离的 module roots，因此不同 package 的安装不会共享模块。

### Filtering、Scope 与去重

settings 中 package 字符串会加载全部资源；对象形式可以分别写 `extensions`、`skills`、`prompts` 和 `themes`，空数组表示该类全部禁用，省略字段表示不限制。`!pattern` 排除 glob，`+path` 强制包含 exact path，`-path` 强制排除 exact path；过滤只会收窄 manifest 已允许的资源，不会越权扩大它。`pi config` 可在 global 与 project-local settings 间切换，`-l` 从项目覆盖开始。

同一 package 同时出现在 global/project settings 时，project entry 胜出；若 project entry 设置 `autoload: false`，则作为 global entry 的 delta。npm 的身份是 package name，git 的身份是去掉 ref 的 repository URL，local 的身份是解析后的绝对路径。去重规则决定实际装载哪一个资源，因此修改 project package 前要检查 global package 是否提供了同名能力。

> 译者注：Package 只解决分发和资源声明，不提供 sandbox。Go 更适合显式 `Plugin.Register`/registry，Java 可用 `ServiceLoader`/SPI；无论哪种 loader，都要在安装前校验来源、权限、版本和依赖，并为加载失败设计 fail-fast 或隔离策略。

**实践实验**：创建一个只含 `extensions/`、`skills/`、`prompts/` 的本地 package，先用 `pi -e` 验证，再用 `pi install -l` 写入项目设置；加入 `!legacy.ts`、`+themes/legacy.json`，对比过滤结果。然后在全局和项目各声明同一 npm name，观察 project precedence，并模拟缺依赖和未信任项目的错误路径。

### 一次安装究竟改变了什么

`pi install` 不只是下载文件。它解析 package source，决定安装范围，把声明写入 global 或 project settings，并在需要时安装依赖。启动时 ResourceLoader 再依据 settings、manifest 和过滤条件发现 extension、skill、prompt template、theme。可以把生命周期画成：

```text
source spec
  -> resolve npm/git/local
  -> materialize package
  -> install dependencies
  -> write settings
  -> trust check
  -> discover resources
  -> load selected resources
```

每一步都可能失败。Git ref 解析成功不代表 `npm install` 成功；package 被写进 settings 也不代表未信任项目会加载它；manifest 声明了 extension 也不代表过滤器允许它进入 registry。

> 译者注：Package 是分发边界，ResourceLoader 是发现边界，Extension runner 是执行边界。把三者写成一个“安装后立刻运行”的动作，会遗漏权限、依赖和恢复问题。Java 生态中可以类比 Maven artifact、ServiceLoader discovery 和实际 bean lifecycle，但 Pi package 的 resource 类型更多。

### npm、git 和 local 的选择

npm 适合有版本发布和依赖树的 package。带版本号的 npm spec 会固定版本，更新命令不会擅自移动它；不带版本的 spec 则允许 update 根据包管理策略取得新版本。git source 适合直接跟踪仓库中的资源，但 ref 应尽量使用 tag 或 commit，而不是漂移的 branch。local path 适合开发和调试，它不复制目录，因此修改原目录会立即影响下一次加载。

一个实际决策表：

| 场景 | 推荐 source | 需要额外检查 |
| --- | --- | --- |
| 团队发布稳定扩展 | `npm:@scope/pkg@version` | 版本、依赖、包内容 |
| 内部仓库固定实现 | `git:host/org/repo@commit` | ref、SSH 凭据、构建脚本 |
| 本地开发 | `./path/to/package` | 路径解析、是否误提交密钥 |
| 临时试用 | `pi -e <source>` | 临时目录和任意代码权限 |

裸 URL、SSH shorthand 和 `git:` 前缀的解析规则不同，不能把所有字符串都当作同一种 git URL。CI 中设置 `GIT_TERMINAL_PROMPT=0` 可以避免等待交互式凭据；这不是给 CI 自动提供凭据。

### Manifest、约定目录与 glob

manifest 中的路径相对 package root，而不是相对执行 `pi install` 的 cwd。正模式先发现资源，`!pattern` 做排除；dot-prefixed 路径应直接列出。没有 `pi` manifest 时，Pi 才使用 `extensions/`、`skills/`、`prompts/`、`themes/` 的约定发现。

下面这个例子只允许 review extension 和一个 prompt：

```json
{
  "pi": {
    "extensions": ["extensions/*.ts", "!extensions/legacy.ts"],
    "skills": [],
    "prompts": ["prompts/review.md"],
    "themes": []
  }
}
```

注意 `skills: []` 是全部不加载，而省略 `skills` 是不限制该类型。过滤器只能收窄 manifest 的允许范围，`+path` 不是越过 manifest 的万能授权。路径中出现 symlink 时，还要按源文档规则直接列出 resource root，避免 glob 穿过链接造成意外发现。

> 译者注：glob 过滤是集合运算，不是逐文件的权限审批。若 package manifest 已经允许一个目录，settings filter 可以减少它；如果 manifest 根本没有声明某资源，`+path` 也不应被理解为扩大权限。实现自己的 loader 时，应先得到 allowed set，再应用 filter。

### 依赖与 module root

扩展运行时依赖放在 `dependencies`，Pi core 提供的包放在 `peerDependencies` 并使用 `*`，不要把宿主核心重复打进 tarball。其他 Pi package 如果被 package 代码导入，要放进 `dependencies` 和 `bundledDependencies`，并用 `node_modules/` 下的资源路径引用它们。

这条规则解决的是模块隔离：不同 package 有分离的 module roots，不应依赖“另一个 package 已经安装了某个 npm 模块”。如果本地开发时恰好能解析，发布后的独立安装仍可能失败。因此要用干净临时目录执行 package 安装测试，而不是只在 monorepo 根目录运行。

### Scope、autoload 与 precedence

global settings 为用户所有项目提供资源，project settings 为当前仓库提供资源。相同 package identity 同时出现时，project entry 优先；`autoload: false` 则表示 project entry 作为对 global entry 的增量修改。npm identity 是 package name，git identity 是去掉 ref 的 repository URL，local identity 是解析后的绝对路径。

这会产生一个常见 trace：

```text
global: npm:review-tools, extensions=[review.ts]
project: npm:review-tools, autoload=false, skills=[review]
=> 项目设置不会简单“替换整个 global package”，而是按 scope 规则合并/收窄
```

不要用“项目里没写 extension”推断 extension 一定不存在；先看 entry 的 scope、autoload 和资源过滤字段。

### 更新、失败和回滚

`pi update --all` 可能同时更新 Pi、packages 和 pinned git refs 的 checkout；`--extensions` 只处理 package 资源，`--models` 刷新模型目录，`--self` 只处理 Pi。实验性 installer-managed 安装会先写 staged、lockfile-backed release，验证成功才激活，因此失败时应保留当前版本。普通 package update 若需要运行 `npm install`，应把它视为任意代码执行步骤，审查脚本和网络访问。

> 译者注：安装的“成功”至少包含 source resolved、package materialized、依赖安装、settings 写入和资源加载五个层次。建议把每层写事件并可重试；不要只依据进程 exit code 判断 extension 已生效。

### 可执行实验：构造一个最小 package

1. 在临时目录创建 `package.json`、`extensions/hello.ts`、`prompts/review.md` 和 `skills/review/SKILL.md`。
2. 写入 `pi` manifest，并故意加入 `!extensions/legacy.ts` 与 `skills: []`。
3. 用 `pi -e ./package` 试用，确认不会把设置持久化。
4. 用 `pi install -l ./package` 安装到项目设置，确认 `.pi/settings.json` 的变化。
5. 在 global 和 project 分别声明相同 npm identity，观察 precedence 与 `autoload`。
6. 删除一个依赖或制造坏 manifest，记录失败发生在哪个生命周期阶段。
7. 用干净临时 npm cache 重复安装，排除 monorepo 中已有依赖造成的假成功。

实验结果应包含 source、settings、discovery、filter、dependency 和 load 的实际证据。不要安装未审查的第三方 package，也不要在实验 package 中执行 shell、读取 home 凭据或发送网络请求。

> 译者注：如果只想学习资源解析，可以先用 local path；如果要学习发布与可复现性，再使用固定 npm/git ref。两者的测试重点不同，不能用 local path 的成功替代发布包测试。

````markdown
## Install and Manage

> **Security:** Pi packages run with full system access. Extensions execute arbitrary code, and skills can instruct the model to perform any action including running executables. Review source code before installing third-party packages.

```bash
pi install npm:@foo/bar@1.0.0
pi install git:github.com/user/repo@v1
pi install https://github.com/user/repo  # raw URLs work too
pi install /absolute/path/to/package
pi install ./relative/path/to/package

pi remove npm:@foo/bar
pi list                     # show installed packages from settings
pi update                   # update pi only
pi update --all             # update pi, update packages, and reconcile pinned git refs
pi update --extensions      # update packages and reconcile pinned git refs only
pi update --models          # refresh model catalogs only
pi update --self            # update pi only
pi update --self --force    # reinstall pi even if current
pi update npm:@foo/bar      # update one package
pi update --extension npm:@foo/bar
```

These commands manage pi packages and `pi update` can update the pi CLI installation. For experimental installer-managed installations, `pi update` installs the exact checked version into a staged, lockfile-backed release and activates it only after verification, leaving the current release intact if the update fails. Managed installations do not support `--force`; rerun the installer to repair one. To uninstall pi itself, see [Quickstart](quickstart.md#uninstall).

By default, `install` and `remove` write to user settings (`~/.pi/agent/settings.json`). Use `-l` to write to project settings (`.pi/settings.json`) instead. Project settings can be shared with your team, and pi installs any missing packages automatically on startup after the project is trusted.

To try a package without installing it, use `--extension` or `-e`. This installs to a temporary directory for the current run only:

```bash
pi -e npm:@foo/bar
pi -e git:github.com/user/repo
```

## Package Sources

Pi accepts three source types in settings and `pi install`.

### npm

```
npm:@scope/pkg@1.2.3
npm:pkg
```

- Versioned specs are pinned and skipped by package updates (`pi update --extensions`, `pi update --all`).
- User installs go under `~/.pi/agent/npm/`.
- Project installs go under `.pi/npm/`.
- Set `npmCommand` in `settings.json` to pin npm package lookup and install operations to a specific wrapper command such as `mise` or `asdf`.

Example:

```json
{
  "npmCommand": ["mise", "exec", "node@20", "--", "npm"]
}
```

### git

```
git:github.com/user/repo@v1
git:git@github.com:user/repo@v1
https://github.com/user/repo@v1
ssh://git@github.com/user/repo@v1
```

- Without `git:` prefix, only protocol URLs are accepted (`https://`, `http://`, `ssh://`, `git://`).
- With `git:` prefix, shorthand formats are accepted, including `github.com/user/repo` and `git@github.com:user/repo`.
- HTTPS and SSH URLs are both supported.
- SSH URLs use your configured SSH keys automatically (respects `~/.ssh/config`).
- For non-interactive runs (for example CI), you can set `GIT_TERMINAL_PROMPT=0` to disable credential prompts and set `GIT_SSH_COMMAND` (for example `ssh -o BatchMode=yes -o ConnectTimeout=5`) to fail fast.
- Refs are pinned tags or commits. `pi update --extensions` and `pi update --all` do not move them to newer refs, but they do reconcile an existing clone to the configured ref.
- Use `pi install git:host/user/repo@new-ref` to update settings and move an existing package to a new pinned ref.
- Cloned to `~/.pi/agent/git/<host>/<path>` (global) or `.pi/git/<host>/<path>` (project).
- When reconciliation changes the checkout, pi resets and cleans the clone, then runs `npm install` if `package.json` exists.

**SSH examples:**
```bash
# git@host:path shorthand (requires git: prefix)
pi install git:git@github.com:user/repo

# ssh:// protocol format
pi install ssh://git@github.com/user/repo

# With version ref
pi install git:git@github.com:user/repo@v1.0.0
```

### Local Paths

```
/absolute/path/to/package
./relative/path/to/package
```

Local paths point to files or directories on disk and are added to settings without copying. Relative paths are resolved against the settings file they appear in. If the path is a file, it loads as a single extension. If it is a directory, pi loads resources using package rules.

## Creating a Pi Package

Add a `pi` manifest to `package.json` or use conventional directories. Include the `pi-package` keyword for discoverability.

```json
{
  "name": "my-package",
  "keywords": ["pi-package"],
  "pi": {
    "extensions": ["./extensions"],
    "skills": ["./skills"],
    "prompts": ["./prompts"],
    "themes": ["./themes"]
  }
}
```

Paths are relative to the package root. Arrays support glob patterns and `!exclusions`. Positive manifest globs discover visible paths in lexical order. List dot-prefixed paths directly. If a glob would need to continue through a symlink, list the symlinked resource root directly.

### Gallery Metadata

The [package gallery](https://pi.dev/packages) displays packages tagged with `pi-package`. Add `video` or `image` fields to show a preview:

```json
{
  "name": "my-package",
  "keywords": ["pi-package"],
  "pi": {
    "extensions": ["./extensions"],
    "video": "https://example.com/demo.mp4",
    "image": "https://example.com/screenshot.png"
  }
}
```

- **video**: MP4 only. On desktop, autoplays on hover. Clicking opens a fullscreen player.
- **image**: PNG, JPEG, GIF, or WebP. Displayed as a static preview.

If both are set, video takes precedence.

## Package Structure

### Convention Directories

If no `pi` manifest is present, pi auto-discovers resources from these directories:

- `extensions/` loads `.ts` and `.js` files
- `skills/` recursively finds `SKILL.md` folders and loads top-level `.md` files as skills
- `prompts/` loads `.md` files
- `themes/` loads `.json` files

## Dependencies

Third party runtime dependencies belong in `dependencies` in `package.json`. Dependencies that do not register extensions, skills, prompt templates, or themes also belong in `dependencies`. When pi installs a package from npm or git, it runs `npm install`, so those dependencies are installed automatically.

Pi bundles core packages for extensions and skills. If you import any of these, list them in `peerDependencies` with a `"*"` range and do not bundle them: `@earendil-works/pi-ai`, `@earendil-works/pi-agent-core`, `@earendil-works/pi-coding-agent`, `@earendil-works/pi-tui`, `typebox`.

Other pi packages must be bundled in your tarball. Add them to `dependencies` and `bundledDependencies`, then reference their resources through `node_modules/` paths. Pi loads packages with separate module roots, so separate installs do not collide or share modules.

Example:

```json
{
  "dependencies": {
    "shitty-extensions": "^1.0.1"
  },
  "bundledDependencies": ["shitty-extensions"],
  "pi": {
    "extensions": ["extensions", "node_modules/shitty-extensions/extensions"],
    "skills": ["skills", "node_modules/shitty-extensions/skills"]
  }
}
```

## Package Filtering

Filter what a package loads using the object form in settings:

```json
{
  "packages": [
    "npm:simple-pkg",
    {
      "source": "npm:my-package",
      "extensions": ["extensions/*.ts", "!extensions/legacy.ts"],
      "skills": [],
      "prompts": ["prompts/review.md"],
      "themes": ["+themes/legacy.json"]
    }
  ]
}
```

`+path` and `-path` are exact paths relative to the package root.

- Omit a key to load all of that type.
- Use `[]` to load none of that type.
- `!pattern` excludes matches.
- `+path` force-includes an exact path.
- `-path` force-excludes an exact path.
- Filters layer on top of the manifest. They narrow down what is already allowed.

## Enable and Disable Resources

Use `pi config` to enable or disable extensions, skills, prompt templates, and themes from installed packages and local directories. `pi config` starts in global settings (`~/.pi/agent/settings.json`); press Tab to switch between global and project-local modes. Use `pi config -l` to start in project overrides (`.pi/settings.json`) with inherited global resources dimmed.

## Scope and Deduplication

Packages can appear in both global and project settings. If the same package appears in both, the project entry wins unless the project entry has `autoload: false`, in which case it is applied as a delta over the global entry. Identity is determined by:

- npm: package name
- git: repository URL without ref
- local: resolved absolute path

````
