## 中文译文

本节按源文档的顺序完整说明 Session File Format。为了避免把“文件里保存了什么”和“模型实际看到了什么”混成一件事，全文反复区分三层：JSONL entry 是持久化记录，Session tree 是这些记录的组织方式，Context builder 则把活动分支投影成一次 Provider request 的消息列表。

### 1. 文件格式总览

Pi 用 JSONL（JSON Lines）保存 session。

JSONL 的规则很简单：一个物理行对应一个 JSON object。

每个 object 都有一个 `type` 字段，用来决定其余字段如何解释。

因此，读取文件不能只把所有行反序列化成同一种消息。

读者必须先看 `type`，再按照 entry 类型校验字段。

首行是 `session` header。

header 描述文件本身，不是对话树中的一个节点。

header 之后的 entry 通常有 `id`、`parentId` 和 `timestamp`。

`id` 指向当前节点，`parentId` 指向它在树中的父节点。

这种设计让多个分支可以共存于同一个文件。

例如，用户回到较早的消息后选择另一条方案，Pi 只需从那个旧节点追加新的 child。

它不需要把整段历史复制到第二个文件。

> 译者注：这里的“tree”不是把每次对话复制成多个 session。
>
> 它更像 Git commit graph：旧节点保持不变，新的工作从某个节点继续。
>
> Java 可以用 `Map<String, Entry>` 加 parent lookup 表示它；Go 可以用 `map[string]Entry` 加当前 leaf id 表示它。

### 2. File Location：文件位置

默认 session 文件位于：

```text
~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl
```

这里的 `<path>` 是工作目录。

为了把目录映射到 session 子目录，路径中的 `/` 会替换为 `-`。

例如，工作目录 `/Users/alice/project` 会参与形成一个类似 `--Users-alice-project--` 的目录名。

文件名由创建时间和 UUID 组成。

时间戳便于按时间排序。

UUID 用来避免同一时间创建多个 session 时发生碰撞。

文件名不是 session 内容的替代品。

真正的当前分支位置仍由 entry 的 parent chain 和 SessionManager 的 leaf 状态决定。

> 译者注：路径编码适合人类查看，但不要在程序里反向猜测原始工作目录。
>
> 读取 `SessionHeader.cwd` 才是可靠来源；目录名只是存储布局。

### 3. Deleting Sessions：删除 Session

删除 session 的最直接方式是删除 `~/.pi/agent/sessions/` 下对应的 `.jsonl` 文件。

删除文件会让 Pi 无法再从磁盘恢复该 session。

它不会自动撤销此前已经发生的 shell、网络或文件写入。

所以“删除对话”与“撤销 Agent 副作用”是两个不同的操作。

Pi 也支持从 `/resume` 交互删除。

用户先选择一个 session。

然后按 `Ctrl+D`，再确认删除。

如果当前环境提供 `trash` CLI，Pi 会优先使用它。

这样删除通常会进入系统回收站，而不是立即永久移除。

> 译者注：如果扩展或运维工具直接删除 JSONL，必须同时考虑备份、审计和并发写入。
>
> 一个正在运行的 Agent 可能仍持有 writer；删除文件并不等于安全地关闭运行。

### 4. Session Version：版本与迁移

header 中有 `version` 字段。

版本描述的是 session 文件格式，不是模型版本，也不是 Pi CLI 的版本。

源文档列出三个版本：

- **Version 1**：entry 按线性顺序排列，是旧格式。
- **Version 2**：增加 `id`/`parentId`，entry 可以组成树。
- **Version 3**：把 `hookMessage` role 重命名为 `custom`，统一扩展消息语义。

Version 1 没有树链接。

读取 v1 时，加载器需要根据线性顺序补出父子关系。

Version 2 把“当前历史”从一个数组提升为一棵树。

Version 3 处理的是扩展消息命名，而不是把 `custom` 自动加入模型上下文。

现有 session 在加载时会自动迁移到当前版本 v3。

迁移的目标是让读取代码面对统一结构。

它不意味着旧文件的每个语义都能无损变成新语义。

升级格式时要特别检查自定义 entry、compaction 边界和分支 leaf。

> 译者注：迁移是读取边界的兼容工作，不等于随意重写原文件。
>
> 如果你的 Harness 要支持升级后恢复，建议先在内存中完成 normalize，再用新格式写出；不要边读边覆盖原文件。

### 5. Source Files：源码入口

源文档列出四类源码入口。

`packages/coding-agent/src/core/session-manager.ts` 负责 Session entry 类型和 `SessionManager`。

`packages/coding-agent/src/core/messages.ts` 放置 Coding Agent 扩展的消息类型，例如 `BashExecutionMessage` 和 `CustomMessage`。

`packages/ai/src/types.ts` 提供 `UserMessage`、`AssistantMessage` 和 `ToolResultMessage` 等基础消息。

`packages/agent/src/types.ts` 定义 `AgentMessage` union。

如果需要查看已安装包的 TypeScript 定义，可以检查 `node_modules/@earendil-works/pi-coding-agent/dist/` 和 `node_modules/@earendil-works/pi-ai/dist/`。

阅读顺序建议从 `AgentMessage` 开始，再看 Session entry wrapper。

这样可以先弄清楚 `message` entry 里面的内容，再理解树结构。

不要把 `SessionEntry` 与 `AgentMessage` 当作同一层类型。

前者有 `id`、`parentId` 和 entry `type`。

后者描述发给模型或由模型返回的消息。

### 6. Message Types：消息类型为什么重要

Session entry 中的 `message` 字段包含 `AgentMessage`。

理解这些类型是解析 session 和编写 extension 的前提。

同一个 JSONL 文件可能同时保存用户消息、assistant 消息、工具结果、shell 结果、分支摘要和扩展消息。

它们的 `role` 和 entry `type` 不一定相同。

例如，外层可以是 `type: "message"`，内层是 `role: "toolResult"`。

外层说明“这是一条树 entry”。

内层说明“这条 entry 在消息语义上是什么”。

> 译者注：这是最容易误读的两层标签。
>
> `type` 负责 Session tree 的持久化分派；`role` 负责 Agent/Provider 的消息分派。
>
> 解析器如果只检查其中一个字段，就可能把 custom state 错当成模型消息。

#### 6.1 Content Blocks：内容块

消息内容可以是字符串，也可以是有明确 `type` 的内容块数组。

`TextContent` 表示普通文本。

`ImageContent` 使用 base64 数据和 MIME 类型保存图像。

`mimeType` 例如 `image/jpeg` 或 `image/png`。

`ThinkingContent` 保存模型的 thinking 文本。

`ToolCall` 保存模型提出的一次工具调用。

Tool Call 包含 `id`、`name` 和 `arguments`。

`id` 用来把后续 Tool Result 与这次调用配对。

`name` 是 Registry 中要查找的工具名。

`arguments` 是结构化参数；它不是 Java 方法已经执行的证明。

典型的内容块定义如下：

```typescript
interface TextContent {
  type: "text";
  text: string;
}

interface ImageContent {
  type: "image";
  data: string;      // base64 encoded
  mimeType: string;  // e.g., "image/jpeg", "image/png"
}

interface ThinkingContent {
  type: "thinking";
  thinking: string;
}

interface ToolCall {
  type: "toolCall";
  id: string;
  name: string;
  arguments: Record<string, any>;
}
```

代码中的字段名必须保持原样。

`data` 是编码后的内容，不是文件路径。

`arguments` 是模型返回的对象，Runtime 仍需做 JSON Schema 校验、权限检查和执行。

### 6.2 Base Message Types：pi-ai 基础消息

`UserMessage` 的 `role` 固定为 `user`。

它的 `content` 可以是文本，也可以是文本/图像内容块数组。

`timestamp` 是 Unix 毫秒时间戳。

`AssistantMessage` 的 `content` 可以包含文本、thinking 和 Tool Call。

它还带有 `api`、`provider` 和 `model`，说明这次响应经过了哪个适配器。

`usage` 保存 token 和 cost 统计。

`stopReason` 告诉 Runtime 这次 assistant 响应为什么结束。

`errorMessage` 只在需要记录错误文本时出现。

`ToolResultMessage` 必须通过 `toolCallId` 找到对应的 assistant Tool Call。

`toolName` 用于展示和诊断。

`content` 可以包含文本或图像。

`details` 是工具专用的附加数据，不应默认发送给 Provider。

`usage` 可以记录工具内部额外执行的 LLM 工作。

`isError` 区分工具正常返回和工具失败。

三类基础接口的原始形状如下：

```typescript
interface UserMessage {
  role: "user";
  content: string | (TextContent | ImageContent)[];
  timestamp: number;  // Unix ms
}

interface AssistantMessage {
  role: "assistant";
  content: (TextContent | ThinkingContent | ToolCall)[];
  api: string;
  provider: string;
  model: string;
  usage: Usage;
  stopReason: "stop" | "length" | "toolUse" | "error" | "aborted";
  errorMessage?: string;
  timestamp: number;
}

interface ToolResultMessage {
  role: "toolResult";
  toolCallId: string;
  toolName: string;
  content: (TextContent | ImageContent)[];
  details?: any;      // Tool-specific metadata
  usage?: Usage;      // Nested LLM work performed by the tool
  isError: boolean;
  timestamp: number;
}

interface Usage {
  input: number;
  output: number;
  cacheRead: number;
  cacheWrite: number;
  totalTokens: number;
  cost: {
    input: number;
    output: number;
    cacheRead: number;
    cacheWrite: number;
    total: number;
  };
}
```

这里的 `Usage` 不是简单的 output 字符数。

`cacheRead` 和 `cacheWrite` 反映 Provider 可能提供的缓存计费数据。

`cost` 是分项成本，便于汇总一次 session 的总花费。

#### 6.3 StopReason 与 pending

导出的 `pi-ai` `StopReason` 类型还包含 `pending`。

`pending` 只表示流式响应尚未结束。

它适合存在于内存中的 partial assistant message 或 stream event。

当收到 terminal `done` 或 `error` 事件时，Runtime 必须把它转换成完成原因。

因此，写入 session JSONL 的 assistant message 不应保留 `stopReason: "pending"`。

落盘终态可以是 `stop`、`length`、`toolUse`、`error` 或 `aborted`。

> 译者注：`pending` 是生命周期状态，不是一个可以长期恢复的答案状态。
>
> 如果程序崩溃时只把 pending message 写入磁盘，恢复逻辑无法判断它是可重试请求、断流响应还是用户取消。
>
> 持久化层应写清楚 terminal outcome，或把未完成工作记录成可恢复 operation。

#### 6.4 Extended Message Types：Coding Agent 扩展消息

`BashExecutionMessage` 记录 shell 命令、输出、退出码、是否取消以及输出是否截断。

`fullOutputPath` 指向未截断的完整输出文件。

`excludeFromContext` 可以让特定命令输出不进入模型上下文，例如 `!!` 前缀命令。

`CustomMessage` 是扩展定义的消息。

它使用 `customType` 标识扩展。

`display` 决定 TUI 是否展示它。

`details` 保存扩展元数据。

`BranchSummaryMessage` 描述从某个 `fromId` 分支时生成的摘要。

`CompactionSummaryMessage` 保存旧消息摘要和压缩前 token 数。

这些消息定义如下：

```typescript
interface BashExecutionMessage {
  role: "bashExecution";
  command: string;
  output: string;
  exitCode: number | undefined;
  cancelled: boolean;
  truncated: boolean;
  fullOutputPath?: string;
  excludeFromContext?: boolean;  // true for !! prefix commands
  timestamp: number;
}

interface CustomMessage {
  role: "custom";
  customType: string;            // Extension identifier
  content: string | (TextContent | ImageContent)[];
  display: boolean;              // Show in TUI
  details?: any;                 // Extension-specific metadata
  timestamp: number;
}

interface BranchSummaryMessage {
  role: "branchSummary";
  summary: string;
  fromId: string;                // Entry we branched from
  timestamp: number;
}

interface CompactionSummaryMessage {
  role: "compactionSummary";
  summary: string;
  tokensBefore: number;
  timestamp: number;
}
```

`AgentMessage` 是这些消息的 union：

```typescript
type AgentMessage =
  | UserMessage
  | AssistantMessage
  | ToolResultMessage
  | BashExecutionMessage
  | CustomMessage
  | BranchSummaryMessage
  | CompactionSummaryMessage;
```

union 的意义是：一个变量可以是多种消息，但实际操作前要根据 `role` 做 type narrowing。

Java 可以用 sealed interface 加多个 record 表示这个关系。

Go 可以用统一 struct 加 `Role` 字段，或用不同 struct 在边界处显式分派。

### 7. Entry Base：树节点共同字段

除 `SessionHeader` 外，所有 entry 都扩展 `SessionEntryBase`。

共同字段是：

- `type`：entry 类型名。
- `id`：8 字符 hex id。
- `parentId`：父 entry id；第一条树 entry 为 `null`。
- `timestamp`：ISO 时间戳。

原始定义是：

```typescript
interface SessionEntryBase {
  type: string;
  id: string;           // 8-char hex ID
  parentId: string | null;  // Parent entry ID (null for first entry)
  timestamp: string;    // ISO timestamp
}
```

`id` 应在 session 内唯一。

`parentId` 只能指向已存在的父节点，或者在读取 v1 迁移时由加载器补出。

`timestamp` 用于展示和排序，但不能替代 parent chain。

一个时间较晚的 entry 仍可能属于较早的分支。

### 8. Entry Types：外层持久化记录

下面逐一解释源文档列出的 entry。

#### 8.1 SessionHeader

它是文件第一行。

它只记录 session 元数据，不进入对话树。

因此没有 `id`/`parentId` 的树语义。

最小 header 示例：

```json
{"type":"session","version":3,"id":"uuid","timestamp":"2024-12-03T14:00:00.000Z","cwd":"/path/to/project"}
```

通过 `/fork`、`/clone` 或 `newSession({ parentSession })` 创建的 session 还会记录父文件：

```json
{"type":"session","version":3,"id":"uuid","timestamp":"2024-12-03T14:00:00.000Z","cwd":"/path/to/project","parentSession":"/path/to/original/session.jsonl"}
```

`id` 是 session UUID。

`cwd` 是创建 session 时的工作目录。

`parentSession` 表示文件级来源关系；它不等同于 entry 的 `parentId`。

> 译者注：Session fork 有两种关系不要混淆。
>
> header 的 `parentSession` 指向另一个文件；entry 的 `parentId` 只在当前文件的 tree 内连边。

#### 8.2 SessionMessageEntry

它把一个 `AgentMessage` 放进对话树。

外层 `type` 是 `message`。

内层 `message` 字段保存具体的 `AgentMessage`。

示例包含三条相互连接的 entry：

```json
{"type":"message","id":"a1b2c3d4","parentId":"prev1234","timestamp":"2024-12-03T14:00:01.000Z","message":{"role":"user","content":"Hello"}}
{"type":"message","id":"b2c3d4e5","parentId":"a1b2c3d4","timestamp":"2024-12-03T14:00:02.000Z","message":{"role":"assistant","content":[{"type":"text","text":"Hi!"}],"provider":"anthropic","model":"claude-sonnet-4-5","usage":{...},"stopReason":"stop"}}
{"type":"message","id":"c3d4e5f6","parentId":"b2c3d4e5","timestamp":"2024-12-03T14:00:03.000Z","message":{"role":"toolResult","toolCallId":"call_123","toolName":"bash","content":[{"type":"text","text":"output"}],"isError":false}}
```

第一条是用户输入。

第二条是 assistant 响应。

第三条是与 assistant Tool Call 配对的工具结果。

这里的 `prev1234` 必须能解析到当前 session 的父 entry。

`toolCallId` 必须能在对应 assistant content 中找到。

#### 8.3 ModelChangeEntry

用户在 session 中切换模型时写入 `model_change`。

它影响后续请求，不会修改已经保存的 assistant message。

```json
{"type":"model_change","id":"d4e5f6g7","parentId":"c3d4e5f6","timestamp":"2024-12-03T14:05:00.000Z","provider":"openai","modelId":"gpt-4o"}
```

`provider` 与 `modelId` 是之后 Model resolution 的输入。

#### 8.4 ThinkingLevelChangeEntry

用户改变 thinking/reasoning level 时写入 `thinking_level_change`。

它同样只影响后续请求。

```json
{"type":"thinking_level_change","id":"e5f6g7h8","parentId":"d4e5f6g7","timestamp":"2024-12-03T14:06:00.000Z","thinkingLevel":"high"}
```

#### 8.5 CompactionEntry

上下文压缩时创建 `compaction` entry。

它保存旧消息的摘要。

旧格式使用 `firstKeptEntryId` 标记保留范围：

```json
{"type":"compaction","id":"f6g7h8i9","parentId":"e5f6g7h8","timestamp":"2024-12-03T14:10:00.000Z","summary":"User discussed X, Y, Z...","firstKeptEntryId":"c3d4e5f6","tokensBefore":50000}
```

较新的 Harness-generated compaction 直接保存 `retainedTail`：

```json
{"type":"compaction","id":"f6g7h8i9","parentId":"e5f6g7h8","timestamp":"2024-12-03T14:10:00.000Z","summary":"User discussed X, Y, Z...","tokensBefore":50000,"retainedTail":[{"role":"user","content":"latest request"},{"role":"assistant","content":[{"type":"text","text":"latest reply"}],"provider":"anthropic","model":"claude-sonnet-4-5","usage":{...},"stopReason":"stop"}]}
```

可选字段有：

- `usage`：生成摘要的 LLM usage，会计入 session token 和 cost。
- `retainedTail`：压缩点之后保留的 `AgentMessage[]`。新格式写它，旧文件没有它也必须能读。
- `details`：实现相关数据，例如默认实现记录 `readFiles` 和 `modifiedFiles`，扩展可写自定义数据。
- `fromHook`：`true` 表示由 extension 生成；`false`/`undefined` 表示 Pi 生成，这是旧字段名。
- `firstKeptEntryId`：为了兼容旧 entry 保留的字段。

`retainedTail` 的价值是把 checkpoint 自包含化。

恢复 Context 时不必再走 compaction 之前的整条旧分支。

> 译者注：compaction summary 是给模型看的语义压缩结果，entry 本身仍是树中的一个节点。
>
> `tokensBefore` 是观测数据，不足以重建消息；重建依赖 `retainedTail` 或旧的 `firstKeptEntryId`。

#### 8.6 BranchSummaryEntry

通过 `/tree` 切换分支时，可以生成 `branch_summary`。

它总结被放弃路径直到公共祖先的上下文。

```json
{"type":"branch_summary","id":"g7h8i9j0","parentId":"a1b2c3d4","timestamp":"2024-12-03T14:15:00.000Z","fromId":"f6g7h8i9","summary":"Branch explored approach A..."}
```

`fromId` 指向被总结的分支位置。

可选 `usage` 记录生成摘要的 LLM 成本。

`details` 保存默认文件追踪数据或扩展数据。

`fromHook` 说明摘要是否由 extension 生成。

branch summary 让新分支知道旧分支尝试过什么。

它不应被误解为把整个旧分支重新发送给模型。

#### 8.7 CustomEntry

`custom` entry 用于保存 extension state。

它不参与 LLM context。

示例：

```json
{"type":"custom","id":"h8i9j0k1","parentId":"g7h8i9j0","timestamp":"2024-12-03T14:20:00.000Z","customType":"my-extension","data":{"count":42}}
```

`customType` 是扩展自己的稳定标识。

扩展重启时可以按这个字段找回计数器或配置。

interactive mode 可以通过 `pi.registerEntryRenderer(customType, renderer)` 渲染它。

即使 TUI 显示了它，它仍不会自动成为 LLM context message。

#### 8.8 CustomMessageEntry

`custom_message` 是 extension 注入、并且会参与 LLM context 的消息。

```json
{"type":"custom_message","id":"i9j0k1l2","parentId":"h8i9j0k1","timestamp":"2024-12-03T14:25:00.000Z","customType":"my-extension","content":"Injected context...","display":true}
```

`content` 可以是字符串，也可以是文本/图像 block 数组。

`display: true` 表示 TUI 展示。

`display: false` 表示隐藏展示，但不代表它不会进入 context。

`details` 是扩展元数据，不发送给 LLM。

> 译者注：`custom` 与 `custom_message` 只有一个下划线之差，却是重要安全边界。
>
> 前者适合状态，后者适合上下文；如果把敏感扩展状态写成后者，模型可能看到它。

#### 8.9 LabelEntry

`label` 是用户在 entry 上设置的书签或标记。

```json
{"type":"label","id":"j0k1l2m3","parentId":"i9j0k1l2","timestamp":"2024-12-03T14:30:00.000Z","targetId":"a1b2c3d4","label":"checkpoint-1"}
```

`targetId` 指定被标记的 entry。

把 `label` 设置为 `undefined` 可以清除标记。

label 是导航和展示事实，不是 conversation message。

#### 8.10 SessionInfoEntry

`session_info` 保存 session metadata，例如用户定义的显示名称。

名称可以通过 `/name`、`--name`、`-n` 或 extension 中的 `pi.setSessionName()` 设置。

```json
{"type":"session_info","id":"k1l2m3n4","parentId":"j0k1l2m3","timestamp":"2024-12-03T14:35:00.000Z","name":"Refactor auth module"}
```

设置名称后，`/resume` 的 session selector 会显示该名称，而不是第一条消息。

### 9. Tree Structure：树结构

entry 形成一棵有向树。

第一条 entry 的 `parentId` 是 `null`。

后续 entry 通过 `parentId` 指向父节点。

分支操作从较早 entry 创建新的 child。

旧 child 不会因为新分支而消失。

leaf 是当前所在位置。

示意图中，左边是一条主路径，右边是从旧节点创建的 alternate branch：

```text
[user msg] ─── [assistant] ─── [user msg] ─── [assistant] ─┬─ [user msg] ← current leaf
                                                            │
                                                            └─ [branch_summary] ─── [user msg] ← alternate branch
```

如果用户回到 `[assistant]` 并继续输入，新消息会成为另一条 child path。

`getBranch()` 之类的 API 通常从 leaf 向 root 走，再反转为请求顺序。

不要按文件物理顺序代替 parent chain。

物理顺序表示 append 顺序，parent chain 才表示当前 branch。

### 10. Context Building：构建模型上下文

`buildContextEntries()` 从当前 leaf 向 root 遍历。

它先收集活动路径上的 entry。

如果路径上没有 compaction，就可以把这条路径转换成上下文。

如果路径上有 compaction，则要按 checkpoint 规则裁剪。

处理步骤如下：

1. 收集当前 leaf 到 root 的所有 path entry。
2. 如果遇到 `CompactionEntry`，先放入 compaction entry。
3. 如果有 `retainedTail`，把它视为自包含 checkpoint。
4. 如果没有 `retainedTail`，使用从 `firstKeptEntryId` 开始的旧保留范围。
5. 再加入 compaction 之后的 entry。
6. 选定范围中的非 message entry 仍保留，以便 interactive mode 展示。

`buildSessionContext()` 建立在 `buildContextEntries()` 之上。

它先从完整 path 找到当前 model 和 thinking level。

然后把 entry 投影为 LLM 能理解的消息：

- `message` 投影为保存的 `AgentMessage`。
- `compaction` 投影为 `compactionSummary`，有 `retainedTail` 时一并加入。
- `branch_summary` 投影为 `branchSummary`。
- `custom_message` 投影为 `CustomMessage`。
- `custom` 不产生 context message。

因此，Session 文件保存的 entry 集合比一次 Provider request 看到的 message 集合更大。

模型可能看不到 label、session_info 或 extension state。

TUI 可能展示 branch summary，而 Provider 只接收它的消息投影。

> 译者注：Context builder 是持久化和模型之间的防火墙。
>
> 不要直接把所有 JSONL 行拼成 `messages`；那会把 UI metadata、扩展状态和错误格式泄漏给模型。

### 11. Parsing Example：逐行解析

源文档的 TypeScript 示例先读取整个文件，再按换行切分：

```typescript
import { readFileSync } from "fs";

const lines = readFileSync("session.jsonl", "utf8").trim().split("\n");

for (const line of lines) {
  const entry = JSON.parse(line);

  switch (entry.type) {
    case "session":
      console.log(`Session v${entry.version ?? 1}: ${entry.id}`);
      break;
    case "message":
      console.log(`[${entry.id}] ${entry.message.role}: ${JSON.stringify(entry.message.content)}`);
      break;
    case "compaction":
      console.log(`[${entry.id}] Compaction: ${entry.tokensBefore} tokens summarized`);
      break;
    case "branch_summary":
      console.log(`[${entry.id}] Branch from ${entry.fromId}`);
      break;
    case "custom":
      console.log(`[${entry.id}] Custom (${entry.customType}): ${JSON.stringify(entry.data)}`);
      break;
    case "custom_message":
      console.log(`[${entry.id}] Extension message (${entry.customType}): ${entry.content}`);
      break;
    case "label":
      console.log(`[${entry.id}] Label "${entry.label}" on ${entry.targetId}`);
      break;
    case "model_change":
      console.log(`[${entry.id}] Model: ${entry.provider}/${entry.modelId}`);
      break;
    case "thinking_level_change":
      console.log(`[${entry.id}] Thinking: ${entry.thinkingLevel}`);
      break;
  }
}
```

这段代码适合观察文件，不适合直接作为生产恢复器。

它没有逐行 try/catch。

它没有校验 parent 是否存在。

它没有检测重复 id、孤儿 parent、错误版本或坏尾行。

它把整个文件读入内存，也没有处理空文件和尾部换行。

Go 的教学实现可以用 `bufio.Scanner` 和 `json.Decoder` 逐行处理。

Java 可以用 `Files.lines`，并把 Jackson decode 错误包装为带行号的异常。

> 译者注：观察脚本可以宽松，恢复器必须 fail closed。
>
> 对一个 session 来说，静默跳过坏 entry 可能比直接失败更危险，因为它会把错误历史伪装成一条可继续执行的历史。

### 12. SessionManager API：程序化操作

`SessionManager` 提供静态创建、静态列表和实例操作。

#### 12.1 Static Creation Methods

- `SessionManager.create(cwd, sessionDir?)`：创建新的持久化 session。
- `SessionManager.open(path, sessionDir?)`：打开已有 session 文件。
- `SessionManager.continueRecent(cwd, sessionDir?)`：继续最近一个 session；没有时创建新的。
- `SessionManager.inMemory(cwd?)`：创建不写磁盘的内存 session。
- `SessionManager.forkFrom(sourcePath, targetCwd, sessionDir?)`：从另一个项目的 session 分叉。

创建方法决定 storage 生命周期。

`inMemory` 适合测试和一次性实验。

`open` 应先验证 header 和 entry tree，再把 handle 交给上层。

#### 12.2 Static Listing Methods

- `SessionManager.list(cwd, sessionDir?, onProgress?)`：列出某个目录对应的 session。
- `SessionManager.listAll(onProgress?)`：列出所有项目的 session。

列表 API 是发现入口，不等于打开全部文件。

`onProgress` 用于大目录扫描时反馈进度。

调用者不应把 listing 的摘要字段当成完整 session state。

#### 12.3 Instance Methods：Session 管理

- `newSession(options?)`：开始新 session，可用 `{ parentSession?: string }` 记录父文件。
- `setSessionFile(path)`：切换到另一个 session 文件。
- `createBranchedSession(leafId)`：把某个 leaf 的分支提取为新文件。

切换文件必须先完成当前 writer 的 flush。

否则新旧文件可能各自只包含半段 prefix。

#### 12.4 Instance Methods：追加 entry

下列方法都会追加 entry，并返回 entry id：

- `appendMessage(message)`：追加普通 `AgentMessage`。
- `appendThinkingLevelChange(level)`：记录 thinking level 改变。
- `appendModelChange(provider, modelId)`：记录模型改变。
- `appendCompaction(summary, firstKeptEntryId, tokensBefore, details?, fromHook?)`：追加压缩记录。
- `appendCustomEntry(customType, data?)`：保存扩展状态，不进入 Context。
- `appendSessionInfo(name)`：设置 session 展示名称。
- `appendCustomMessageEntry(customType, content, display, details?)`：追加会进入 Context 的扩展消息。
- `appendLabelChange(targetId, label)`：设置或清除 label。

返回 id 的作用是让调用者可以继续设置 label 或构建调试链接。

追加方法必须在当前 leaf 上建立 parent link。

如果有并发 writer，返回 id 只有在 append 成功提交后才应对外可见。

#### 12.5 Instance Methods：树导航

- `getLeafId()`：读取当前 leaf。
- `getLeafEntry()`：读取当前 leaf entry。
- `getEntry(id)`：按 id 查 entry。
- `getBranch(fromId?)`：从指定节点向 root 遍历。
- `getTree()`：获取完整树结构。
- `getChildren(parentId)`：读取直接 child。
- `getLabel(id)`：读取 entry 的 label。
- `branch(entryId)`：把 leaf 移到较早 entry。
- `resetLeaf()`：把 leaf 置为 `null`，表示还没有任何 entry。
- `branchWithSummary(entryId, summary, details?, fromHook?)`：带摘要切换分支。

导航改变的是未来追加的位置。

它不应删除旧 branch。

`getBranch` 的输出通常用于 Context builder。

`getTree` 更适合 TUI、调试和分支选择器。

#### 12.6 Instance Methods：Context 与信息

- `buildContextEntries()`：得到应用 compaction 后的活动分支 entry。
- `buildSessionContext()`：得到给 LLM 的消息、thinkingLevel 和 model。
- `getEntries()`：读取除 header 外的全部 entry。
- `getHeader()`：读取 header 元数据。
- `getSessionName()`：读取最新 `session_info` 的名称。
- `getCwd()`：读取工作目录。
- `getSessionDir()`：读取 session 存储目录。
- `getSessionId()`：读取 session UUID。
- `getSessionFile()`：读取文件路径；内存 session 时为 `undefined`。
- `isPersisted()`：判断当前 session 是否持久化。

这些方法有意把“树查询”和“Context 投影”分开。

`getEntries()` 可以用于审计，但不应直接当作 Provider messages。

`buildSessionContext()` 才是模型请求的候选输入。

> 译者注：API 名字看起来像 CRUD，但 Session 不是普通可变列表。
>
> append 会增加历史；branch 只改变 leaf；context build 只读并投影。
>
> 这种分离让旧 branch 可以审计，也让新的请求不会意外修改旧消息。

### 13. Go 与 Java 实现对照

Go 版本可以这样分层：

- `SessionEntry` struct 保存外层 `type`、id、parent 和 timestamp。
- `Message` struct 保存内部 role 和 content。
- `bufio.Scanner` 逐行读取 JSONL。
- `encoding/json` 解码 header 和 entry。
- `context.Context` 传递取消。
- `os.CreateTemp` 加 `os.Rename` 实现一次文件替换。

Java 版本可以这样分层：

- Jackson `JsonNode` 先读取 `type`，再映射到 record/DTO。
- `Files.lines` 或 buffered reader 逐行读取。
- `ExecutorService` 或单 writer 线程保护 append 顺序。
- `Future.cancel`/中断只表达取消意图，不保证远端副作用撤销。
- `Path.resolve` 和 normalized path 检查文件边界。

两个实现都要区分以下错误：

1. JSON 语法错误。
2. JSON 合法但缺少必要字段。
3. parent 不存在。
4. 重复 entry id。
5. tool call 与 tool result 不匹配。
6. compaction 保留点不可解析。
7. session version 不支持。
8. 文件截断或并发写入。

### 14. 可执行检查实验

#### 实验 A：观察一条 message 的生命周期

目标是看清模型消息如何变成 Session entry。

准备一个只包含 user、assistant 和 tool result 的临时 JSONL 文件。

步骤：

1. 打印每行的外层 `type`。
2. 对 `type: "message"` 再打印内层 `message.role`。
3. 记录每条 entry 的 `id` 与 `parentId`。
4. 找到 assistant content 中的 Tool Call id。
5. 用同一个 id 查找 `toolResult.toolCallId`。
6. 观察 tool result 是否是 `isError: true`。

预期结果是：Tool Call 只出现在 assistant message，真正的工具输出出现在后续 Tool Result message。

思考：如果 Tool Result 没有对应 call，恢复器应该继续还是拒绝文件？为什么？

#### 实验 B：观察分支与 leaf

目标是证明文件物理顺序不等于当前 Context。

步骤：

1. 创建 user A、assistant A、user B、assistant B。
2. 把 leaf 移回 user A。
3. 从 user A 追加 user C。
4. 打印 `getChildren(userA)`，确认 B 和 C 都保留。
5. 调用 `buildContextEntries()`，确认只返回 A→C 路径。

预期结果是旧的 A→B branch 仍可查询，但模型下一次只看到 A→C。

#### 实验 C：观察 compaction

目标是区分 `firstKeptEntryId`、`retainedTail` 和模型上下文。

步骤：

1. 准备十条较长消息，记录压缩前 token estimate。
2. 追加一个带 `firstKeptEntryId` 的旧格式 compaction。
3. 再准备一个带 `retainedTail` 的新格式 compaction。
4. 分别调用 `buildContextEntries()` 和 `buildSessionContext()`。
5. 比较文件 entry 数量与最终 Provider message 数量。

预期结果是 compaction entry 仍在树中，但旧消息不会全部发送给模型。

#### 实验 D：损坏检测

依次制造以下输入：

- 把一行改成非法 JSON。
- 删除一个 parent entry。
- 复用已有 id。
- 把 `toolCallId` 改成不存在的值。
- 把 version 改成不支持的数字。
- 在文件尾部写半行 JSON。

对每种输入记录加载器行为。

教学实现可以把坏尾行作为可恢复截断，但坏中间行应直接失败。

生产 Harness 必须记录错误位置，不能静默跳过。

> 译者注：这组实验把“能解析”与“能恢复”分开。
>
> JSON parser 通过只说明语法正确；Session validator 还要证明树、消息配对和版本语义正确。

### 15. 小结

Session File Format 的核心不是“把聊天保存成 JSON”。

它保存的是一组可导航的、带父子关系的历史 entry。

`AgentMessage` 描述消息语义。

`SessionEntryBase` 描述树结构。

`SessionManager` 负责创建、追加、导航和 Context 投影。

`compaction` 让长历史可以从 checkpoint 继续。

`custom` 与 `custom_message` 划定扩展状态和模型上下文的边界。

`pending` 不能直接作为永久 session 状态。

恢复器必须验证版本、id、parent、Tool Call 配对、compaction 范围和坏行。

最后记住：文件里存在的东西，不一定应该发送给 LLM；模型看到的东西，也不一定是文件的全部。

> 译者注：如果要把这个格式升级成 durable Agent Harness，下一层还需要 operation intent/result、单 writer、crash recovery、幂等外部副作用和 telemetry ledger。
>
> 当前 Pi session format 提供了很好的树和 Context 基础，但不能仅凭 JSONL 文件声称已经实现完整 exactly-once Harness。

# Session File Format

Sessions are stored as JSONL (JSON Lines) files. Each line is a JSON object with a `type` field. Session entries form a tree structure via `id`/`parentId` fields, enabling in-place branching without creating new files.

## File Location

```
~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl
```

Where `<path>` is the working directory with `/` replaced by `-`.

## Deleting Sessions

Sessions can be removed by deleting their `.jsonl` files under `~/.pi/agent/sessions/`.

Pi also supports deleting sessions interactively from `/resume` (select a session and press `Ctrl+D`, then confirm). When available, pi uses the `trash` CLI to avoid permanent deletion.

## Session Version

Sessions have a version field in the header:

- **Version 1**: Linear entry sequence (legacy, auto-migrated on load)
- **Version 2**: Tree structure with `id`/`parentId` linking
- **Version 3**: Renamed `hookMessage` role to `custom` (extensions unification)

Existing sessions are automatically migrated to the current version (v3) when loaded.

## Source Files

Source on GitHub ([pi-mono](https://github.com/earendil-works/pi-mono)):
- [`packages/coding-agent/src/core/session-manager.ts`](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/src/core/session-manager.ts) - Session entry types and SessionManager
- [`packages/coding-agent/src/core/messages.ts`](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/src/core/messages.ts) - Extended message types (BashExecutionMessage, CustomMessage, etc.)
- [`packages/ai/src/types.ts`](https://github.com/earendil-works/pi-mono/blob/main/packages/ai/src/types.ts) - Base message types (UserMessage, AssistantMessage, ToolResultMessage)

## Entry Types

### SessionHeader

First line of the file. Metadata only, not part of the tree (no `id`/`parentId`).

```json
{"type":"session","version":3,"id":"uuid","timestamp":"2024-12-03T14:00:00.000Z","cwd":"/path/to/project"}
```

For sessions with a parent (created via `/fork`, `/clone`, or `newSession({ parentSession })`):

```json
{"type":"session","version":3,"id":"uuid","timestamp":"2024-12-03T14:00:00.000Z","cwd":"/path/to/project","parentSession":"/path/to/original/session.jsonl"}
```

### SessionMessageEntry

A message in the conversation. The `message` field contains an `AgentMessage`.

```json
{"type":"message","id":"a1b2c3d4","parentId":"prev1234","timestamp":"2024-12-03T14:00:01.000Z","message":{"role":"user","content":"Hello"}}
{"type":"message","id":"b2c3d4e5","parentId":"a1b2c3d4","timestamp":"2024-12-03T14:00:02.000Z","message":{"role":"assistant","content":[{"type":"text","text":"Hi!"}],"provider":"anthropic","model":"claude-sonnet-4-5","usage":{...},"stopReason":"stop"}}
{"type":"message","id":"c3d4e5f6","parentId":"b2c3d4e5","timestamp":"2024-12-03T14:00:03.000Z","message":{"role":"toolResult","toolCallId":"call_123","toolName":"bash","content":[{"type":"text","text":"output"}],"isError":false}}
```

### ModelChangeEntry

Emitted when the user switches models mid-session.

```json
{"type":"model_change","id":"d4e5f6g7","parentId":"c3d4e5f6","timestamp":"2024-12-03T14:05:00.000Z","provider":"openai","modelId":"gpt-4o"}
```

### ThinkingLevelChangeEntry

Emitted when the user changes the thinking/reasoning level.

```json
{"type":"thinking_level_change","id":"e5f6g7h8","parentId":"d4e5f6g7","timestamp":"2024-12-03T14:06:00.000Z","thinkingLevel":"high"}
```

### CompactionEntry

Created when context is compacted. Stores a summary of earlier messages.

```json
{"type":"compaction","id":"f6g7h8i9","parentId":"e5f6g7h8","timestamp":"2024-12-03T14:10:00.000Z","summary":"User discussed X, Y, Z...","firstKeptEntryId":"c3d4e5f6","tokensBefore":50000}
```

Newer harness-generated compactions embed the retained post-compaction context directly on the entry, instead of `firstKeptEntryId`:

```json
{"type":"compaction","id":"f6g7h8i9","parentId":"e5f6g7h8","timestamp":"2024-12-03T14:10:00.000Z","summary":"User discussed X, Y, Z...","tokensBefore":50000,"retainedTail":[{"role":"user","content":"latest request"},{"role":"assistant","content":[{"type":"text","text":"latest reply"}],"provider":"anthropic","model":"claude-sonnet-4-5","usage":{...},"stopReason":"stop"}]}
```

Optional fields:
- `usage`: LLM usage from generating the summary; included in session token and cost totals
- `retainedTail`: Materialized `AgentMessage[]` kept after compaction. This is optional only for backward compatibility with older sessions. Newer harness-generated compactions include it so we can rebuild context from this checkpoint without walking older entries before the compaction entry.
- `details`: Implementation-specific data (e.g., `{ readFiles: string[], modifiedFiles: string[] }` for default, or custom data for extensions)
- `fromHook`: `true` if generated by an extension, `false`/`undefined` if pi-generated (legacy field name)
- `firstKeptEntryId`: for compatibility with old entry format.

### BranchSummaryEntry

Created when switching branches via `/tree` with an LLM generated summary of the left branch up to the common ancestor. Captures context from the abandoned path.

```json
{"type":"branch_summary","id":"g7h8i9j0","parentId":"a1b2c3d4","timestamp":"2024-12-03T14:15:00.000Z","fromId":"f6g7h8i9","summary":"Branch explored approach A..."}
```

Optional fields:
- `usage`: LLM usage from generating the summary; included in session token and cost totals
- `details`: File tracking data (`{ readFiles: string[], modifiedFiles: string[] }`) for default, or custom data for extensions
- `fromHook`: `true` if generated by an extension, `false`/`undefined` if pi-generated (legacy field name)

### CustomEntry

Extension state persistence. Does NOT participate in LLM context.

```json
{"type":"custom","id":"h8i9j0k1","parentId":"g7h8i9j0","timestamp":"2024-12-03T14:20:00.000Z","customType":"my-extension","data":{"count":42}}
```

Use `customType` to identify your extension's entries on reload. Interactive mode can render custom entries via `pi.registerEntryRenderer(customType, renderer)`, but they still do not participate in LLM context.

### CustomMessageEntry

Extension-injected messages that DO participate in LLM context.

```json
{"type":"custom_message","id":"i9j0k1l2","parentId":"h8i9j0k1","timestamp":"2024-12-03T14:25:00.000Z","customType":"my-extension","content":"Injected context...","display":true}
```

Fields:
- `content`: String or `(TextContent | ImageContent)[]` (same as UserMessage)
- `display`: `true` = show in TUI with distinct styling, `false` = hidden
- `details`: Optional extension-specific metadata (not sent to LLM)

### LabelEntry

User-defined bookmark/marker on an entry.

```json
{"type":"label","id":"j0k1l2m3","parentId":"i9j0k1l2","timestamp":"2024-12-03T14:30:00.000Z","targetId":"a1b2c3d4","label":"checkpoint-1"}
```

Set `label` to `undefined` to clear a label.

### SessionInfoEntry

Session metadata (e.g., user-defined display name). Set via `/name`, `--name` / `-n`, or `pi.setSessionName()` in extensions.

```json
{"type":"session_info","id":"k1l2m3n4","parentId":"j0k1l2m3","timestamp":"2024-12-03T14:35:00.000Z","name":"Refactor auth module"}
```

The session name is displayed in the session selector (`/resume`) instead of the first message when set.

## Tree Structure

Entries form a tree:
- First entry has `parentId: null`
- Each subsequent entry points to its parent via `parentId`
- Branching creates new children from an earlier entry
- The "leaf" is the current position in the tree

```
[user msg] ─── [assistant] ─── [user msg] ─── [assistant] ─┬─ [user msg] ← current leaf
                                                            │
                                                            └─ [branch_summary] ─── [user msg] ← alternate branch
```

## Context Building

`buildContextEntries()` walks from the current leaf to the root, producing the active entry list while honoring compaction:

1. Collects all entries on the path
2. If a `CompactionEntry` is on the path:
   - Includes the compaction entry first
   - If `retainedTail` is present, it acts as a self-contained checkpoint and entries after the compaction are included
   - Otherwise entries from `firstKeptEntryId` to the compaction are included
   - Then entries after compaction are included
3. Preserves non-message entries in the selected range so interactive mode can render them

`buildSessionContext()` builds on that entry list to produce the message list for the LLM:

1. Extracts current model and thinking level settings from the full path
2. Converts selected entries to messages:
   - `message` -> stored `AgentMessage`
   - `compaction` -> `compactionSummary` plus `retainedTail` when present
   - `branch_summary` -> `branchSummary`
   - `custom_message` -> `CustomMessage`
   - `custom` -> no context message

This makes newer compactions act like self-contained checkpoints. `retainedTail` is optional only so older sessions that only store `firstKeptEntryId` continue to load correctly.

## Parsing Example

```typescript
import { readFileSync } from "fs";

const lines = readFileSync("session.jsonl", "utf8").trim().split("\n");

for (const line of lines) {
  const entry = JSON.parse(line);

  switch (entry.type) {
    case "session":
      console.log(`Session v${entry.version ?? 1}: ${entry.id}`);
      break;
    case "message":
      console.log(`[${entry.id}] ${entry.message.role}: ${JSON.stringify(entry.message.content)}`);
      break;
    case "compaction":
      console.log(`[${entry.id}] Compaction: ${entry.tokensBefore} tokens summarized`);
      break;
    case "branch_summary":
      console.log(`[${entry.id}] Branch from ${entry.fromId}`);
      break;
    case "custom":
      console.log(`[${entry.id}] Custom (${entry.customType}): ${JSON.stringify(entry.data)}`);
      break;
    case "custom_message":
      console.log(`[${entry.id}] Extension message (${entry.customType}): ${entry.content}`);
      break;
    case "label":
      console.log(`[${entry.id}] Label "${entry.label}" on ${entry.targetId}`);
      break;
    case "model_change":
      console.log(`[${entry.id}] Model: ${entry.provider}/${entry.modelId}`);
      break;
    case "thinking_level_change":
      console.log(`[${entry.id}] Thinking: ${entry.thinkingLevel}`);
      break;
  }
}
```

## SessionManager API

Key methods for working with sessions programmatically.

### Static Creation Methods
- `SessionManager.create(cwd, sessionDir?)` - New session
- `SessionManager.open(path, sessionDir?)` - Open existing session file
- `SessionManager.continueRecent(cwd, sessionDir?)` - Continue most recent or create new
- `SessionManager.inMemory(cwd?)` - No file persistence
- `SessionManager.forkFrom(sourcePath, targetCwd, sessionDir?)` - Fork session from another project

### Static Listing Methods
- `SessionManager.list(cwd, sessionDir?, onProgress?)` - List sessions for a directory
- `SessionManager.listAll(onProgress?)` - List all sessions across all projects

### Instance Methods - Session Management
- `newSession(options?)` - Start a new session (options: `{ parentSession?: string }`)
- `setSessionFile(path)` - Switch to a different session file
- `createBranchedSession(leafId)` - Extract branch to new session file

### Instance Methods - Appending (all return entry ID)
- `appendMessage(message)` - Add message
- `appendThinkingLevelChange(level)` - Record thinking change
- `appendModelChange(provider, modelId)` - Record model change
- `appendCompaction(summary, firstKeptEntryId, tokensBefore, details?, fromHook?)` - Add compaction
- `appendCustomEntry(customType, data?)` - Extension state (not in context)
- `appendSessionInfo(name)` - Set session display name
- `appendCustomMessageEntry(customType, content, display, details?)` - Extension message (in context)
- `appendLabelChange(targetId, label)` - Set/clear label

### Instance Methods - Tree Navigation
- `getLeafId()` - Current position
- `getLeafEntry()` - Get current leaf entry
- `getEntry(id)` - Get entry by ID
- `getBranch(fromId?)` - Walk from entry to root
- `getTree()` - Get full tree structure
- `getChildren(parentId)` - Get direct children
- `getLabel(id)` - Get label for entry
- `branch(entryId)` - Move leaf to earlier entry
- `resetLeaf()` - Reset leaf to null (before any entries)
- `branchWithSummary(entryId, summary, details?, fromHook?)` - Branch with context summary

### Instance Methods - Context & Info
- `buildContextEntries()` - Get active branch entries with compaction applied
- `buildSessionContext()` - Get messages, thinkingLevel, and model for LLM
- `getEntries()` - All entries (excluding header)
- `getHeader()` - Session header metadata
- `getSessionName()` - Get display name from latest session_info entry
- `getCwd()` - Working directory
- `getSessionDir()` - Session storage directory
- `getSessionId()` - Session UUID
- `getSessionFile()` - Session file path (undefined for in-memory)
- `isPersisted()` - Whether session is saved to disk
