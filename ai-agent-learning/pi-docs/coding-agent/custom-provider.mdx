# 自定义 Provider

> 本页是 `packages/coding-agent/docs/custom-provider.md` 的中文参考译本，研究 commit 为 `853a80d26c90a14c1886f0ebb8ffaae133ca2185`。API 名称、命令、路径、配置字段和代码标识符保留原样。

## 中文导读

本页的主题不是“换一个 URL”。Provider 是 Pi 把外部模型接入统一 Agent Runtime 的适配边界：它要回答如何认证、如何把内部 `Context` 编码成请求、如何把流转换成 `AssistantMessageEventStream`、如何处理 thinking/tool call/usage，以及哪些错误可以交给上层恢复。

读者可以把整条链路记成：

```text
Extension 注册 Provider
  -> Model Registry 暴露模型
  -> Agent Loop 取得统一 Model
  -> Provider API adapter 发请求
  -> streamSimple 产生统一事件
  -> AgentSession 消费 assistant/tool result
```

本译文按源文档的标题顺序展开。代码标识符、字段名、协议值和命令保持原样；代码后面的中文说明专门解释输入、输出、状态变化、取消和错误边界。

## 使用建议

1. 先阅读“快速参考”和“API 类型”，确定自己需要覆盖现有 Provider 还是实现完整 Provider。
2. 再阅读 OAuth 和 streaming；这两部分最容易把异步回调误解成模型能力。
3. 最后按照“测试实现”的清单写 fake server/fake stream，不要一上来连接收费 API。
4. 每次修改配置后，用 `/list-models`、`/model` 和受限 prompt 验证模型是否真正可见。

## 源码级中文译文

### 1. 示例扩展：先看可运行的最小边界

源文档首先给出两个完整例子：`examples/extensions/custom-provider-anthropic/` 和 `examples/extensions/custom-provider-gitlab-duo/`。

这两个目录的价值不在于复制某个厂商的请求，而在于展示 Provider registration 所在的层次。

Extension factory 获得 `pi: ExtensionAPI`。

它调用 `pi.registerProvider(...)`，把模型、认证和 API adapter 注册到宿主。

随后 Agent Loop 只拿统一的 `Model`，不需要知道 Extension 文件的路径。

一个 Provider 可以只改变现有服务的 `baseUrl`。

它也可以注册完全不同的模型目录。

如果 API 不符合内置格式，还可以提供 `streamSimple`。

> 译者注：在 Java 中，这个 Extension factory 最接近一个实现了 `Plugin` 接口的模块；在 Go 中，通常由显式 `RegisterProvider` 函数完成。两者都不应让业务代码直接依赖某个厂商的 JSON response。

### 2. 快速参考：先决定 Provider 的类型

Pi 支持两种注册形态。

第一种是完整的 `pi-ai Provider`。

它适合自定义认证、过滤模型、刷新 OAuth 凭据或实现特殊流式协议。

第二种是 legacy provider-config。

它适合给现有 Provider 改 `baseUrl`、header、apiKey 或模型列表。

在新的复杂集成中，优先选择完整 Provider，因为生命周期和能力边界更清楚。

`models.json` 的覆盖层仍然会作用在已注册的 native Provider 之上。

这意味着注册函数不是唯一配置来源。

调试时要区分三份数据：Extension 注册值、`models.json` 覆盖值和最终解析出的 Model。

下面这段源代码中的 `createProvider` 会创建一个 native Provider：

```typescript
import { createProvider, openAICompletionsApi } from "@earendil-works/pi-ai";
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerProvider(createProvider({
    id: "native-local",
    name: "Native Local",
    baseUrl: "http://localhost:8080/v1",
    auth: {
      apiKey: {
        name: "Local server API key",
        async login(interaction) {
          return {
            type: "api_key",
            key: await interaction.prompt({ type: "secret", message: "API key" })
          };
        },
        async resolve({ credential }) {
          return credential?.key
            ? { auth: { apiKey: credential.key }, source: "stored API key" }
            : undefined;
        }
      }
    },
    models: [],
    api: openAICompletionsApi()
  }));
}
```

输入是 `ExtensionAPI` 和 Provider options。

输出不是一次模型回答，而是一个进入 registry 的 Provider。

`models: []` 表示这个例子暂时没有静态模型。

`login` 的返回值进入受控 credential store，不应打印到日志。

`resolve` 在请求时把已保存 credential 转成 adapter 使用的 auth。

> 译者注：`async` 只表示该函数返回 Promise，不表示模型会并行推理。Java 可用 `CompletableFuture` 表达同一边界；本页的 Java 教学代码也可以先用同步接口再在外层封装。

### 3. Extension factory 与动态模型发现

Extension factory 可以是 `async` 函数。

如果模型列表来自远程 `/v1/models`，应在 factory 中完成 fetch 和 register。

不要等到 `session_start` 才注册，否则交互式启动和 `pi --list-models` 可能看不到模型。

Pi 会等待 factory 完成后继续启动。

因此 factory 失败属于启动阶段错误，而不是一次普通模型请求错误。

远程目录响应需要做结构校验。

`id`、上下文窗口和最大输出 token 缺失时必须提供明确默认值或拒绝该模型。

不要把远程返回的任意字段直接当成内部 `ProviderModelConfig`。

先建立一个白名单映射，再写入模型 registry。

这种边界同时保护了 prompt 中展示的模型信息和计费字段。

### 4. 覆盖现有 Provider

最简单的场景是把现有请求改走企业代理：

```typescript
pi.registerProvider("anthropic", {
  baseUrl: "https://proxy.example.com"
});

pi.registerProvider("openai", {
  headers: {
    "X-Custom-Header": "value"
  }
});
```

只提供 `baseUrl` 或 `headers`、不提供 `models` 时，原 Provider 的模型会被保留。

覆盖改变的是请求路由或 header，不是模型的能力声明。

如果同时传入 `models`，语义就发生变化：模型列表会替换，而不是合并。

调试代理时先确认最终 URL。

再确认显式 header 是否覆盖自动认证 header。

最后确认模型的 `api` 没有被误改成不兼容的 adapter。

企业代理可能支持 Anthropic API，但不一定支持 OpenAI Responses API。

不要根据“都是 HTTPS JSON”判断两个 API 可以互换。

> 译者注：这是 Provider adapter 的实际价值。Agent Loop 只需要“完成一次统一请求”，代理、header 和厂商 wire format 都留在 adapter 层。Java 中可把它类比为 `HttpClient` 前的 `HttpRequest` builder；Go 中则是 `http.RoundTripper` 或 Provider interface 的职责。

### 5. 注册新 Provider 与模型目录

新 Provider 至少要说明 `baseUrl`、`api`、`models` 和认证来源。

每个模型要有稳定 `id`。

`name` 用于 UI 展示，不应作为请求中的模型 id。

`reasoning` 表示该模型是否支持扩展思考，不是“这个模型一定会思考得更好”。

`input` 声明 text/image 等输入能力。

`cost` 为 usage 计算提供每百万 token 的价格。

`contextWindow` 决定上下文预算。

`maxTokens` 是单次输出上限。

缺少这些字段会让后续 compaction、成本统计或输入校验失去依据。

远程发现例子先 fetch `/v1/models`，再把每条数据映射成模型配置。

映射过程中要把 snake_case 的 `context_window` 变成 Pi 使用的 `contextWindow`。

要给 `name`、`contextWindow` 和 `maxTokens` 设置保守默认值。

Provider 的模型目录应在启动前稳定下来。

不要在第一次 prompt 期间临时改变目录，这会使 UI、session 和请求看到不同的模型集合。

### 6. `models` 是替换语义，不是追加语义

源文档特别强调：传入 `models` 会替换该 Provider 的全部现有模型。

这对“只增加一个模型”的直觉很容易造成误解。

如果要保留内置模型，必须先读取或明确重建完整目录。

否则 `/model` 选择器会突然减少选项。

替换模型也会移除与旧模型绑定的能力声明。

例如 thinking map、cache control 和 token cost 可能一起变化。

在生产 Extension 中，建议在注册前打印“新目录的 id 集合”，但不要打印 credential。

测试应断言替换和覆盖两种场景的结果不同。

> 译者注：这不是 TypeScript 的数组 `push`。它是 registry 的配置更新操作。Go 的 map 赋值和 Java 的 registry `put` 也要明确选择 merge 或 replace，不能让调用者猜。

### 7. 配置值解析

`apiKey` 和自定义 header 使用与 `models.json` 相同的值语法。

`$ENV_VAR` 和 `${ENV_VAR}` 读取环境变量。

`!command` 在整个值上执行命令。

`$$` 表示字面量 `$`。

`$!` 表示字面量 `!`。

这套语法让配置可以引用外部 secret，但也引入了命令执行边界。

只允许可信配置目录使用 `!command`。

不要把用户输入拼接进命令字符串。

不要把解析后的 key 放进 Event、Telemetry、Skill 或 session transcript。

失败时错误消息也应避免回显完整 secret。

### 8. 注销 Provider

调用 `pi.unregisterProvider(name)` 会移除动态模型。

它也会移除 API key fallback、OAuth 注册和 custom stream handler。

如果此前覆盖了 built-in Provider，注销后会恢复原行为。

初始 Extension load phase 之后的调用立即生效，不需要 `/reload`。

这意味着运行中的选择器和后续请求可能观察到 registry 变化。

正在进行的请求是否已拿到旧 Model，应由运行时的快照语义决定。

不要在注销操作中删除 session 历史中的 provider 字符串。

session 记录的是历史事实，registry 记录的是当前可用能力。

测试注销时至少验证模型可见性、认证 fallback 和 stream handler 都恢复。

### 9. `api` 字段与 adapter 选择

`api` 决定使用哪一种流式实现。

常见值包括 `anthropic-messages`、`openai-completions`、`openai-responses`、`google-generative-ai` 和 `bedrock-converse-stream`。

大多数 OpenAI-compatible endpoint 可以从 `openai-completions` 开始。

但 URL 相似并不保证 thinking、tool result 或 response id 兼容。

Mistral 原生接口使用 `mistral-conversations`。

Azure Responses 使用单独的 `azure-openai-responses`。

OpenAI Codex 使用 `openai-codex-responses`。

Google Vertex 和 Google Generative AI 的认证、请求结构和流事件也不同。

Adapter 选择错误通常表现为“请求成功但消息为空”或“Tool Call 无法恢复”。

因此先读最接近的 `packages/ai/src/api/*.ts`，再复制结构。

### 10. thinking level map 与 compat

`thinkingLevelMap` 把 Pi 的 `minimal`、`low`、`medium`、`high`、`xhigh`、`max` 映射为 Provider 值。

值为 `null` 表示该级别不支持，并且 UI 不应把它当成可选项。

`xhigh` 和 `max` 是 opt-in，不应因为模型有 `reasoning: true` 就自动开放。

映射可以有 unsupported holes。

`compat` 用来描述 Provider 的具体兼容性差异。

例如 `supportsDeveloperRole: false` 表示必须用 `system`。

`maxTokensField` 解决 `max_tokens` 与 `max_completion_tokens` 的字段差异。

`requiresToolResultName` 处理某些 Provider 对 Tool Result 的额外要求。

`thinkingFormat` 说明 thinking 参数位于 openai、qwen、together 或其他特定结构。

`cacheControlFormat: "anthropic"` 影响系统 prompt、最后一个 tool definition 和文本内容的缓存标记。

不要为“请求能返回文本”就随意开启所有 compat 开关。

每个开关都应该有一个 fake response 或 provider regression test。

### 11. Provider-specific reasoning 与迁移提示

OpenRouter 使用 `reasoning: { effort }`。

Together 使用 `reasoning: { enabled }`，并可在 `supportsReasoningEffort` 时发送 `reasoning_effort`。

Qwen 可能使用顶层 `enable_thinking`。

本地 Qwen-compatible server 可能需要 `chat_template_kwargs.enable_thinking` 和 `preserve_thinking`。

Anthropic-compatible 的 adaptive thinking 需要 `forceAdaptiveThinking`。

只有真正返回空 thinking signature 的 Provider 才应设置 `allowEmptySignature`。

Mistral 已从 `openai-completions` 迁移到 `mistral-conversations`。

如果刻意把 Mistral-compatible endpoint 走旧 adapter，必须显式设置 compat。

> 译者注：这些字段不是“模型个性化 prompt”。它们是 wire protocol 的兼容开关。Java 可以把它们建模为不可变 `record`；Go 可以用明确字段的 struct，避免用无类型 map 到处传播。

### 12. Auth Header

Provider 如果期待 `Authorization: Bearer <key>`，可以设置 `authHeader: true`。

key 会在每次请求时解析。

显式 request `Authorization` header 优先于自动生成的 header。

因此优先级是：请求级显式值、Provider 解析值、自动 Bearer。

不要同时把 key 放在 query string，除非上游协议明确要求。

HTTP 日志只记录 header 名，不记录值。

fake server 测试应断言 header 存在，但输出时用 `[redacted]`。

请求取消后不应继续刷新 OAuth 或执行外部命令。

### 13. OAuth Support

OAuth Provider 通过 `/login` 接入交互式认证。

`login(callbacks)` 负责选择 browser 或 device flow。

`onAuth` 可以打开授权 URL。

`onDeviceCode` 展示 user code、verification URI、轮询间隔和过期时间。

`onProgress` 提供短暂状态，不应包含 access token。

`onPrompt` 读取人工输入的 code。

`onSelect` 让 UI 选择认证方式。

Provider 自己负责 code exchange 和 token refresh。

Pi 只需要保存 OAuth credentials 并在请求时取得 API key。

login 被取消时应抛出明确错误，不能写入半成品 credential。

refresh 必须响应 `AbortSignal`，否则用户退出时可能留下悬挂请求。

### 14. OAuthLoginCallbacks：UI-neutral 的设计

`OAuthLoginCallbacks` 不依赖 TUI、CLI 或浏览器实现。

`onAuth(params)` 的输入是 URL。

`onDeviceCode(params)` 的输入是可展示的 device code 数据。

`onPrompt(params)` 返回 `Promise<string>`，所以 Provider 可以等待用户。

`onSelect(params)` 返回 `Promise&lt;string | undefined&gt;`。

`undefined` 表示用户取消选择，不是一个合法认证方法。

Provider 不应直接访问 TUI 的组件状态。

这让同一个 OAuth flow 可以在 RPC 或非交互模式下由宿主拒绝。

> 译者注：TypeScript 的 `Promise&lt;string | undefined&gt;` 可以类比 Java 的 `CompletableFuture&lt;Optional&lt;String&gt;&gt;`，但 Promise reject 和 `undefined` 是两条不同路径；Go 则应返回 `(string, bool, error)` 或一个带取消的结果结构。

### 15. OAuthCredentials：保存什么，不保存什么

`OAuthCredentials` 包含 `refresh`、`access` 和毫秒级 `expires`。

refresh token 用于再次获取 access token。

access token 由 `getApiKey` 返回给 Provider adapter。

expires 用于判断是否需要刷新。

凭据保存在 `~/.pi/agent/auth.json`，因此文件权限和备份策略很重要。

不要把凭据放入 `models.json`、session JSONL 或 Git。

刷新成功后要原子替换 credential，而不是先清空旧值。

刷新失败时保留错误分类，便于用户重新 `/login`。

如果 refresh token 已撤销，不能无限重试 login。

### 16. Custom Streaming API：统一事件而非返回字符串

非标准 API 使用 `streamSimple`。

它接收 `model`、`context` 和可选 `SimpleStreamOptions`。

返回值是 `AssistantMessageEventStream`，不是 `Promise<string>`。

这一区别很关键：Agent Runtime 需要在文本、thinking、Tool Call 产生时观察 partial 状态。

输出消息一开始的 `stopReason` 是 `pending`。

发送 `start` 后，adapter 才可以处理远端数据。

正常终态必须发送 `done` 并结束 stream。

异常终态发送 `error`。

Abort 应把 stop reason 设成 `aborted`，不能伪装成 provider error。

若 stream 结束时仍是 `pending`，应报告协议错误。

> 译者注：Streaming 是“结果逐步到达”，不是“Agent Loop 自动多跑几轮”。轮次由 tool call 和 Runtime 决定；stream event 只描述当前 assistant response 的生命周期。

### 17. Stream Pattern：先建立 settled message

源示例先创建 `AssistantMessage`，初始化 content、provider、model、usage 和 timestamp。

`start` event 携带这个 partial message。

每个后续 event 都应携带当前状态快照。

收到文字时更新同一个 `output.content`。

收到 usage 时更新同一个 `output.usage`。

收到 terminal event 时设置 stop reason。

`done` 的 message 必须是已 settled 的 assistant message。

catch 分支要把异常转换为 `error` 或 `aborted`。

`stream.end()` 必须在终态之后调用。

重复 end 或遗漏 end 都可能让消费者永久等待。

### 18. Event Types：一个 response 的生命周期

事件顺序从 `start` 开始。

文本 block 使用 `text_start`、多个 `text_delta` 和 `text_end`。

thinking block 使用 `thinking_start`、`thinking_delta` 和 `thinking_end`。

Tool Call 使用 `toolcall_start`、`toolcall_delta` 和 `toolcall_end`。

最后二选一：`done` 或 `error`。

`contentIndex` 标识 partial content 中的 block 位置。

同一个 index 不能在未结束时换成另一种 block 类型。

每个 delta 都应能让调试器看到当前 partial。

如果 Provider 的 chunk 没有语义内容，只更新内部累积缓冲，不要发伪造 delta。

### 19. Content Blocks：按 index 维护可变 partial

文本 block 的最小状态是 `{ type: "text", text: "" }`。

开始事件后，后续 delta 追加到对应的 `text`。

结束事件发送最终文本。

thinking block 应保留 Provider 要求的签名或格式信息。

不能把 thinking 文本未经适配直接塞进普通 text block。

如果一次响应在 text 和 toolCall 之间切换，content array 必须保留两个 block。

UI 可以用 partial 渲染，但 Session 只有在 message end 后才保存 settled message。

因此“用户看到一半文字”不等于“历史已经持久化”。

### 20. Tool Calls：增量 JSON 不是完整参数

Tool Call 的 id 和 name 可能先到，arguments 后到。

adapter 需要按 call 的 index 或 contentIndex 保存缓冲。

每个 JSON delta 追加到 `partialJson`。

中间状态可能不是合法 JSON，不能在每个 delta 都报错。

解析成功后更新 block.arguments。

结束时必须得到一个结构化 `{ type: "toolCall", id, name, arguments }`。

如果结束时 JSON 仍然不合法，应产生 error，而不是执行一个猜出来的参数。

Runtime 随后还会做 tool schema validation。

“JSON 可解析”也不等于“参数有权限”。

> 译者注：模型只生成 Tool Call 数据。真正执行 Tool 的是 Agent Runtime。Provider adapter 的责任是把碎片拼成统一数据，不是绕过 Registry 直接调用 Java 方法或 Go 函数。

### 21. Usage 与 cost

Usage 来自 Provider response，不应使用字符数估算真实计费。

至少记录 input、output、cacheRead、cacheWrite 和 totalTokens。

`totalTokens` 通常是各项 token 的合计，但要按 Provider 的定义确认。

更新 usage 后调用 `calculateCost(model, output.usage)`。

cost 依赖模型配置中的每百万 token 价格。

缺失 usage 时要区分“Provider 没提供”和“确实为零”。

重试通常会产生新的 usage 记录。

不要因为一次请求最终失败就丢弃已发生的计费事实。

Telemetry 可以记录 token 数和成本，但不应记录 prompt、tool args 或 secret。

### 22. Context Overflow Errors

Pi 只会对它识别的 overflow 自动 compaction/retry。

Provider 返回普通 `error` 并不会自动触发 compaction。

识别发生在 finalized assistant message 上。

典型条件是 `stopReason === "error"`，并且 `errorMessage` 命中已知模式。

自定义 Provider 如果返回不同措辞，可以在注册它的同一个 Extension 中规范化。

适合使用 `message_end` handler，因为它发生在 Pi 追踪 assistant message 进行自动 compaction 之前。

规范化必须限定 `message.provider` 和 `ctx.model?.provider`。

还必须匹配 Provider 自己的 overflow pattern。

不能把 `rate limit`、`too many requests` 或 throttling 改成 overflow。

否则系统会错误地 compaction，而不是执行正常 backoff retry。

一次输入的 overflow recovery 必须有上限。

> 译者注：错误分类本身是控制流输入。把所有错误写成 `context_length_exceeded`，就等于把网络故障误报成上下文故障；这会制造重复请求和更高费用。

### 23. overflow handler 的输入、输出和幂等性

handler 输入是 `message_end` event 和 Extension context。

它应先检查 role、stopReason 和 provider。

再读取 `errorMessage`。

已经含有 `context_length_exceeded` 时直接返回，确保重复事件不会再次加前缀。

匹配成功时返回一个 message patch。

输出的 `errorMessage` 以可识别的 `context_length_exceeded:` 开头。

Pi 随后会丢弃失败 assistant 的 live context。

它会执行 compaction。

然后有限地 retry 一次请求。

handler 本身不执行 compaction，也不发第二个模型请求。

### 24. Registration：把自定义 stream 接入 Provider

注册时把 `streamSimple: streamMyProvider` 放进 Provider config。

`api: "my-custom-api"` 应与实际 model metadata 和 adapter 逻辑一致。

注册后 model registry 才能把模型选择与 stream function 关联起来。

不要在 Agent Loop 中通过 `if provider === ...` 分支解析 custom response。

那会把 Provider-specific 代码泄漏到核心控制流。

注册之后先执行模型枚举，再执行一次只返回文本的 fake stream。

随后测试 Tool Call、thinking、错误和 abort。

### 26. fake server 实验：验证 HTTP 边界

目标是确认 Provider adapter 发送了正确 URL、header 和 body。

准备一个只监听 `127.0.0.1` 随机端口的 fake server。

第一种响应返回一个普通文本 assistant。

断言请求中的 model id 和 messages 存在。

断言 `Authorization` 是 `Bearer test-key`，但日志中只显示 `[redacted]`。

第二种响应返回 HTTP 429。

确认它走 retry/backoff，而不是被归类为 overflow。

第三种响应返回 HTTP 200 但 choices 为空。

确认 adapter 抛出结构错误。

第四种响应返回非法 JSON。

确认错误包含 decode 阶段，但不包含 key。

测试结束后关闭 server，避免测试进程泄漏监听端口。

### 27. fake stream 实验：逐事件观察 partial

创建一个固定 chunk 序列：

```text
start
text_start("Hel")
text_delta("lo")
text_end("Hello")
done(stop)
```

记录每个事件的 type、contentIndex 和 partial content。

断言每一个 partial 都能由前一个状态追加得到。

再加入 tool call 的 JSON 碎片：`{"left":`、`2`、`,"right":3}`。

中间碎片不应触发参数执行。

只在 `toolcall_end` 后交给 Runtime 做 schema validation。

再模拟 stream 在 pending 状态结束。

确认测试失败并指出缺少 terminal stop reason。

最后调用 AbortSignal，确认终态是 `aborted` 而不是 `done`。

### 28. Config Reference：ProviderConfig 的职责

`name` 是 UI 展示名。

`baseUrl` 是定义模型时需要的 endpoint 基础地址。

`apiKey` 是字面量、环境变量或命令解析值。

`api` 是默认 streaming adapter。

`streamSimple` 是非标准 API 的自定义实现。

`headers` 是请求 header 的解析配置。

`authHeader` 控制是否生成 Bearer Authorization。

`models` 是要注册的模型数组，并具有替换语义。

`oauth` 提供 `/login` 所需的 OAuth lifecycle。

这些字段共同描述“如何找到模型”和“如何发送一次请求”。

它们不描述 Tool 权限、shell sandbox 或 Session 持久化。

> 译者注：ProviderConfig 不是完整 Harness 配置。把认证、流解析和模型元数据放在这里，是因为它们属于模型边界；权限、重试预算和 Tool 执行仍由更外层 Runtime/Harness 负责。

### 29. Model Definition Reference：模型能力声明

`ProviderModelConfig.id` 是请求使用的模型 id。

`name` 是展示名。

`api` 和 `baseUrl` 可以覆盖 Provider 默认值。

`reasoning` 声明是否支持 extended thinking。

`thinkingLevelMap` 把统一 thinking level 映射到 Provider 值。

`input` 声明 text 或 image。

`cost` 提供四类 token 单价。

`contextWindow` 是输入上下文上限。

`maxTokens` 是输出上限。

`headers` 可以做模型级覆盖。

`compat` 收纳 API-specific quirks。

不要把 `reasoning: true` 当作一定会返回 thinking block 的保证。

也不要把 `contextWindow` 当成 Runtime 当前剩余 token；后者还要减去 system、tools、history 和输出预算。

### 30. compat 字段的测试方法

OpenAI completions 相关字段包括 store、developer role、reasoning effort、streaming usage 和 finish reason。

`supportsStrictMode` 与 `supportsOpenAIGrammarTools` 影响 Tool schema 发送方式。

`requiresAssistantAfterToolResult` 影响消息配对。

Anthropic messages 相关字段包括 eager tool input、cache retention、tool cache control、adaptive thinking 和 strict tools。

`chatTemplateKwargs`、`chatTemplateArgs` 是 local server 的模板参数，不是通用 OpenAI 字段。

`thinkingTokenBudgetField` 需要确认 Provider 期待的具体字段名。

`sessionAffinityFormat` 和 `sendSessionAffinityHeaders` 影响会话粘性。

每个 compat 选择都应有“开关前/开关后 payload”断言。

不要仅凭 provider 名称自动推断 compat。

### 31. Go 与 Java 对照实验

Go 的 `context.Context` 对应 TypeScript 的 `AbortSignal`，但它也承载 deadline 和取消传播。

Java 的 `CancellationToken` 加线程 interruption 更接近显式取消协议。

TypeScript 的 `AssistantMessageEventStream` 可以用 Java `Flow.Publisher` 或 listener callback 表达。

Go 可以用 channel 发送 stream event，也可以用 callback 保持示例简单。

Provider config 在 Java 中适合用 immutable record。

Go 中适合用字段明确的 struct 和 interface。

OAuth callback 在 Java 中是 interface。

Go 中是函数值或 callback struct。

两种语言都应在 adapter 边界完成 JSON 编码，不能把厂商 JSON 传到 Agent Loop。

### 32. 源码事实、文档事实与推断

**文档事实：** 本页定义了 `registerProvider`、ProviderConfig、OAuth 和 `streamSimple` 的公开用法。

**源码事实：** 实际 adapter 位于 `packages/ai/src/api/`，统一事件和消息类型位于 `packages/ai/src/types.ts`。

**教学推断：** 把 Provider-specific wire format 隔离在 adapter 中，可以降低 Agent Loop 的条件分支数量。

推断不是作者声明，读者应使用固定 commit 源码验证。

当前 Pi 的 Agent Loop 只消费统一 Model/stream contract。

Coding Agent 的 Extension loader 负责发现和执行扩展。

这并不表示每个 Provider 都有相同能力。

能力差异必须落在 model metadata 和 compat，而不是隐藏在 prompt 文本中。

### 33. 完整实验：从 fake provider 到受限 prompt

第一步，复制最接近的 `openai-completions.ts` adapter，只保留 text response。

第二步，用固定 model config 注册 `my-provider`。

第三步，写 fake server 并断言 request JSON。

第四步，发送一轮 fake stream 并记录全部 event。

第五步，加入 calculator Tool Call，确认 `toolcall_end` 之后才执行。

第六步，返回 429，确认 retry policy 生效。

第八步，调用 `/login` 的 fake OAuth callback，确认取消不会保存 credential。

第九步，执行 `/list-models` 和 `/model`，确认动态模型出现。

第十步，在受限 workspace 中发送一个只读 prompt，确认 Provider、Agent Loop、Tool Registry 和 Telemetry 各自只做自己的工作。

### 34. 安全检查清单

Provider key 不写进代码。

Provider key 不写进 source appendix 以外的日志。

OAuth access/refresh 不进入 session message。

`!command` 只对可信配置启用。

远程模型目录要限制请求地址和响应大小。

fake server 只绑定 loopback。

### 35. 小结

自定义 Provider 的核心不是多写一个请求函数，而是遵守统一的模型边界。

注册层决定模型是否可见。

认证层决定请求是否有凭据。

API adapter 决定 wire format 如何转换。

stream 层决定 partial、Tool Call、usage 和终态如何发送。

Agent Loop 决定是否继续下一轮。

Harness 决定 session、权限、retry、compaction 和 telemetry 如何组合。

当 Provider 文档、源码和测试不一致时，先以固定 commit 的源码和测试确认实际行为。

完成 fake server/fake stream 矩阵后，再连接真实服务。

## Quick Reference

Extensions can register either a complete pi-ai `Provider` or use the legacy provider-config form. Prefer a complete provider when custom authentication, filtering, refresh, or streaming behavior is required. Pi composes `models.json` overrides above registered native providers.

```typescript
import { createProvider, openAICompletionsApi } from "@earendil-works/pi-ai";
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerProvider(createProvider({
    id: "native-local",
    name: "Native Local",
    baseUrl: "http://localhost:8080/v1",
    auth: {
      apiKey: {
        name: "Local server API key",
        async login(interaction) {
          return {
            type: "api_key",
            key: await interaction.prompt({ type: "secret", message: "API key" })
          };
        },
        async resolve({ credential }) {
          return credential?.key
            ? { auth: { apiKey: credential.key }, source: "stored API key" }
            : undefined;
        }
      }
    },
    models: [],
    api: openAICompletionsApi()
  }));

  // Legacy provider-config form:
  // Override baseUrl for existing provider
  pi.registerProvider("anthropic", {
    baseUrl: "https://proxy.example.com"
  });

  // Register new provider with models
  pi.registerProvider("my-provider", {
    name: "My Provider",
    baseUrl: "https://api.example.com",
    apiKey: "$MY_API_KEY",
    api: "openai-completions",
    models: [
      {
        id: "my-model",
        name: "My Model",
        reasoning: false,
        input: ["text", "image"],
        cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
        contextWindow: 128000,
        maxTokens: 4096
      }
    ]
  });
}
```

The extension factory can also be `async`. For dynamic model discovery, fetch and register models in the factory instead of `session_start`. pi waits for the factory before startup continues, so the provider is available during interactive startup and to `pi --list-models`.

## Override Existing Provider

The simplest use case: redirect an existing provider through a proxy.

```typescript
// All Anthropic requests now go through your proxy
pi.registerProvider("anthropic", {
  baseUrl: "https://proxy.example.com"
});

// Add custom headers to OpenAI requests
pi.registerProvider("openai", {
  headers: {
    "X-Custom-Header": "value"
  }
});

// Both baseUrl and headers
pi.registerProvider("google", {
  baseUrl: "https://ai-gateway.corp.com/google",
  headers: {
    "X-Corp-Auth": "$CORP_AUTH_TOKEN"  // env var or literal
  }
});
```

When only `baseUrl` and/or `headers` are provided (no `models`), all existing models for that provider are preserved with the new endpoint.

## Register New Provider

To add a completely new provider, specify `models` along with the required configuration.

If the model list comes from a remote endpoint, use an async extension factory:

```typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default async function (pi: ExtensionAPI) {
  const response = await fetch("http://localhost:1234/v1/models");
  const payload = (await response.json()) as {
    data: Array<{
      id: string;
      name?: string;
      context_window?: number;
      max_tokens?: number;
    }>;
  };

  pi.registerProvider("local-openai", {
    baseUrl: "http://localhost:1234/v1",
    apiKey: "$LOCAL_OPENAI_API_KEY",
    api: "openai-completions",
    models: payload.data.map((model) => ({
      id: model.id,
      name: model.name ?? model.id,
      reasoning: false,
      input: ["text"],
      cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
      contextWindow: model.context_window ?? 128000,
      maxTokens: model.max_tokens ?? 4096,
    })),
  });
}
```

This registers the fetched models before startup finishes.

```typescript
pi.registerProvider("my-llm", {
  baseUrl: "https://api.my-llm.com/v1",
  apiKey: "$MY_LLM_API_KEY",  // env var reference
  api: "openai-completions",  // which streaming API to use
  models: [
    {
      id: "my-llm-large",
      name: "My LLM Large",
      reasoning: true,        // supports extended thinking
      input: ["text", "image"],
      cost: {
        input: 3.0,           // $/million tokens
        output: 15.0,
        cacheRead: 0.3,
        cacheWrite: 3.75
      },
      contextWindow: 200000,
      maxTokens: 16384
    }
  ]
});
```

When `models` is provided, it **replaces** all existing models for that provider.

`apiKey` and custom header values use the same config value syntax as `models.json`: `!command` at the start executes a command for the whole value, `$ENV_VAR` and `${ENV_VAR}` interpolate environment variables, `$$` emits a literal `$`, and `$!` emits a literal `!`.

## Unregister Provider

Use `pi.unregisterProvider(name)` to remove a provider that was previously registered via `pi.registerProvider(name, ...)`:

```typescript
// Register
pi.registerProvider("my-llm", {
  baseUrl: "https://api.my-llm.com/v1",
  apiKey: "$MY_LLM_API_KEY",
  api: "openai-completions",
  models: [
    {
      id: "my-llm-large",
      name: "My LLM Large",
      reasoning: true,
      input: ["text", "image"],
      cost: { input: 3.0, output: 15.0, cacheRead: 0.3, cacheWrite: 3.75 },
      contextWindow: 200000,
      maxTokens: 16384
    }
  ]
});

// Later, remove it
pi.unregisterProvider("my-llm");
```

Unregistering removes that provider's dynamic models, API key fallback, OAuth provider registration, and custom stream handler registrations. Any built-in models or provider behavior that were overridden are restored.

Calls made after the initial extension load phase are applied immediately, so no `/reload` is required.

### API Types

The `api` field determines which streaming implementation is used:

| API | Use for |
|-----|---------|
| `anthropic-messages` | Anthropic Claude API and compatibles |
| `openai-completions` | OpenAI Chat Completions API and compatibles |
| `openai-responses` | OpenAI Responses API |
| `azure-openai-responses` | Azure OpenAI Responses API |
| `openai-codex-responses` | OpenAI Codex Responses API |
| `mistral-conversations` | Native Mistral Chat Completions streaming |
| `google-generative-ai` | Google Generative AI API |
| `google-vertex` | Google Vertex AI API |
| `bedrock-converse-stream` | Amazon Bedrock Converse API |

Most OpenAI-compatible providers work with `openai-completions`. Use model-level `thinkingLevelMap` for model-specific thinking levels, and `compat` for provider quirks. The `xhigh` and `max` levels are opt-in, require non-null map entries, and may be separated by unsupported holes:

```typescript
models: [{
  id: "custom-model",
  // ...
  reasoning: true,
  thinkingLevelMap: {              // map pi levels to provider values; null hides unsupported levels
    minimal: null,
    low: null,
    medium: null,
    high: "default",
    xhigh: null,
    max: "max"
  },
  compat: {
    supportsDeveloperRole: false,   // use "system" instead of "developer"
    supportsReasoningEffort: true,
    maxTokensField: "max_tokens",   // instead of "max_completion_tokens"
    requiresToolResultName: true,   // tool results need name field
    thinkingFormat: "qwen",        // top-level enable_thinking: true
    cacheControlFormat: "anthropic" // Anthropic-style cache_control markers
  }
}]
```

Use `openrouter` for OpenRouter-style `reasoning: { effort }` controls. Use `together` for Together-style `reasoning: { enabled }` controls; with `supportsReasoningEffort`, it also sends `reasoning_effort`. Use `qwen-chat-template` for local Qwen-compatible servers that read `chat_template_kwargs.enable_thinking` and need `preserve_thinking`.
Use `cacheControlFormat: "anthropic"` for OpenAI-compatible providers that expose Anthropic-style prompt caching via `cache_control` on the system prompt, last tool definition, and last user, assistant, or tool-result text content.

For Anthropic-compatible providers using `api: "anthropic-messages"`, set `compat.forceAdaptiveThinking: true` on models or providers whose upstream model requires adaptive thinking (`thinking.type: "adaptive"` plus `output_config.effort`). Built-in adaptive Claude models set this automatically. Set `compat.allowEmptySignature: true` only for providers that emit empty thinking signatures and expect `signature: ""` on replay.

> Migration note: Mistral moved from `openai-completions` to `mistral-conversations`.
> Use `mistral-conversations` for native Mistral models.
> If you intentionally route Mistral-compatible/custom endpoints through `openai-completions`, set `compat` flags explicitly as needed.

### Auth Header

If your provider expects `Authorization: Bearer <key>` but doesn't use a standard API, set `authHeader: true`:

```typescript
pi.registerProvider("custom-api", {
  baseUrl: "https://api.example.com",
  apiKey: "$MY_API_KEY",
  authHeader: true,  // adds Authorization: Bearer header
  api: "openai-completions",
  models: [...]
});
```

The key is resolved for each request. An explicit request `Authorization` header takes precedence over the generated value.

## OAuth Support

Add OAuth/SSO authentication that integrates with `/login`:

```typescript
import type { OAuthCredentials, OAuthLoginCallbacks } from "@earendil-works/pi-ai";

pi.registerProvider("corporate-ai", {
  baseUrl: "https://ai.corp.com/v1",
  api: "openai-responses",
  models: [...],
  oauth: {
    name: "Corporate AI (SSO)",

    async login(callbacks: OAuthLoginCallbacks): Promise<OAuthCredentials> {
      const method = await callbacks.onSelect({
        message: "Select login method:",
        options: [
          { id: "browser", label: "Browser OAuth" },
          { id: "device", label: "Device code" }
        ]
      });
      if (!method) throw new Error("Login cancelled");

      let code: string;
      if (method === "device") {
        callbacks.onDeviceCode({
          userCode: "ABCD-1234",
          verificationUri: "https://sso.corp.com/device",
          intervalSeconds: 5,
          expiresInSeconds: 900
        });
        code = await pollDeviceCodeUntilComplete();
      } else {
        callbacks.onAuth({ url: "https://sso.corp.com/authorize?..." });
        code = await callbacks.onPrompt({ message: "Enter SSO code:" });
      }

      // Exchange for tokens (your implementation)
      const tokens = await exchangeCodeForTokens(code);

      return {
        refresh: tokens.refreshToken,
        access: tokens.accessToken,
        expires: Date.now() + tokens.expiresIn * 1000
      };
    },

    async refreshToken(credentials: OAuthCredentials, signal: AbortSignal): Promise<OAuthCredentials> {
      const tokens = await refreshAccessToken(credentials.refresh, signal);
      return {
        refresh: tokens.refreshToken ?? credentials.refresh,
        access: tokens.accessToken,
        expires: Date.now() + tokens.expiresIn * 1000
      };
    },

    getApiKey(credentials: OAuthCredentials): string {
      return credentials.access;
    }
  }
});
```

After registration, users can authenticate via `/login corporate-ai`.

### Stream Pattern

All providers follow the same pattern:

```typescript
import {
  type AssistantMessage,
  type AssistantMessageEventStream,
  type Context,
  type Model,
  type SimpleStreamOptions,
  calculateCost,
  createAssistantMessageEventStream,
} from "@earendil-works/pi-ai";

function streamMyProvider(
  model: Model<any>,
  context: Context,
  options?: SimpleStreamOptions
): AssistantMessageEventStream {
  const stream = createAssistantMessageEventStream();

  (async () => {
    // Initialize output message
    const output: AssistantMessage = {
      role: "assistant",
      content: [],
      api: model.api,
      provider: model.provider,
      model: model.id,
      usage: {
        input: 0,
        output: 0,
        cacheRead: 0,
        cacheWrite: 0,
        totalTokens: 0,
        cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0, total: 0 },
      },
      stopReason: "pending",
      timestamp: Date.now(),
    };

    try {
      // Push start event
      stream.push({ type: "start", partial: output });

      // Make API request and process response...
      // Push content events as they arrive and set stopReason from the terminal event.
      if (output.stopReason === "pending") {
        throw new Error("Provider stream ended without a stop reason");
      }
      if (output.stopReason === "error" || output.stopReason === "aborted") {
        throw new Error(output.errorMessage || "An unknown error occurred");
      }

      // Push done event
      stream.push({
        type: "done",
        reason: output.stopReason,
        message: output
      });
      stream.end();
    } catch (error) {
      output.stopReason = options?.signal?.aborted ? "aborted" : "error";
      output.errorMessage = error instanceof Error ? error.message : String(error);
      stream.push({ type: "error", reason: output.stopReason, error: output });
      stream.end();
    }
  })();

  return stream;
}
```

### Event Types

Push events via `stream.push()` in this order:

1. `{ type: "start", partial: output }` - Stream started

2. Content events (repeatable, track `contentIndex` for each block):
   - `{ type: "text_start", contentIndex, partial }` - Text block started
   - `{ type: "text_delta", contentIndex, delta, partial }` - Text chunk
   - `{ type: "text_end", contentIndex, content, partial }` - Text block ended
   - `{ type: "thinking_start", contentIndex, partial }` - Thinking started
   - `{ type: "thinking_delta", contentIndex, delta, partial }` - Thinking chunk
   - `{ type: "thinking_end", contentIndex, content, partial }` - Thinking ended
   - `{ type: "toolcall_start", contentIndex, partial }` - Tool call started
   - `{ type: "toolcall_delta", contentIndex, delta, partial }` - Tool call JSON chunk
   - `{ type: "toolcall_end", contentIndex, toolCall, partial }` - Tool call ended

3. `{ type: "done", reason, message }` or `{ type: "error", reason, error }` - Stream ended

The `partial` field in each event contains the current `AssistantMessage` state. Update `output.content` as you receive data, then include `output` as the `partial`.

### Content Blocks

Add content blocks to `output.content` as they arrive:

```typescript
// Text block
output.content.push({ type: "text", text: "" });
stream.push({ type: "text_start", contentIndex: output.content.length - 1, partial: output });

// As text arrives
const block = output.content[contentIndex];
if (block.type === "text") {
  block.text += delta;
  stream.push({ type: "text_delta", contentIndex, delta, partial: output });
}

// When block completes
stream.push({ type: "text_end", contentIndex, content: block.text, partial: output });
```

### Tool Calls

Tool calls require accumulating JSON and parsing:

```typescript
// Start tool call
output.content.push({
  type: "toolCall",
  id: toolCallId,
  name: toolName,
  arguments: {}
});
stream.push({ type: "toolcall_start", contentIndex: output.content.length - 1, partial: output });

// Accumulate JSON
let partialJson = "";
partialJson += jsonDelta;
try {
  block.arguments = JSON.parse(partialJson);
} catch {}
stream.push({ type: "toolcall_delta", contentIndex, delta: jsonDelta, partial: output });

// Complete
stream.push({
  type: "toolcall_end",
  contentIndex,
  toolCall: { type: "toolCall", id, name, arguments: block.arguments },
  partial: output
});
```

### Usage and Cost

Update usage from API response and calculate cost:

```typescript
output.usage.input = response.usage.input_tokens;
output.usage.output = response.usage.output_tokens;
output.usage.cacheRead = response.usage.cache_read_tokens ?? 0;
output.usage.cacheWrite = response.usage.cache_write_tokens ?? 0;
output.usage.totalTokens = output.usage.input + output.usage.output +
                           output.usage.cacheRead + output.usage.cacheWrite;
calculateCost(model, output.usage);
```

### Context Overflow Errors

When a request exceeds the model's context window, pi can recover automatically by compacting the conversation and retrying. This recovery only kicks in if pi recognizes the failure as an overflow.

Detection runs on the finalized assistant message:

- `stopReason === "error"`
- `errorMessage` matches one of pi's known overflow patterns (see [`packages/ai/src/utils/overflow.ts`](https://github.com/earendil-works/pi-mono/blob/main/packages/ai/src/utils/overflow.ts))

If your provider returns overflow errors with a message pi does not recognize, normalize the error from the same extension that registers the provider. Use a `message_end` handler to rewrite the assistant message so its `errorMessage` starts with a phrase pi recognizes. The generic fallback `context_length_exceeded` is the safest choice.

```typescript
const MY_PROVIDER_OVERFLOW_PATTERN = /your provider's overflow phrase/i;

export default function (pi: ExtensionAPI) {
  pi.registerProvider("my-provider", { /* ... */ });

  pi.on("message_end", (event, ctx) => {
    const message = event.message;
    if (message.role !== "assistant") return;
    if (message.stopReason !== "error") return;
    if (
      message.provider !== "my-provider" &&
      ctx.model?.provider !== "my-provider"
    )
      return;

    const errorMessage = message.errorMessage ?? "";
    if (errorMessage.includes("context_length_exceeded")) return;
    if (!MY_PROVIDER_OVERFLOW_PATTERN.test(errorMessage)) return;

    return {
      message: {
        ...message,
        errorMessage: `context_length_exceeded: ${errorMessage}`,
      },
    };
  });
}
```

`message_end` runs before pi tracks the assistant message for auto-compaction, so the rewritten `errorMessage` is what pi checks. With this in place, pi will:

1. Detect the overflow from `errorMessage`.
2. Drop the failed assistant message from live context.
3. Run compaction.
4. Retry the request once.

Guard the rewrite carefully:

- Scope it to your provider (`message.provider` and `ctx.model?.provider`) so unrelated errors from other providers are untouched.
- Match a provider-specific pattern, not pi's generic overflow patterns. Rewriting rate-limit or throttling errors (`rate limit`, `too many requests`) would falsely trigger compaction instead of pi's normal retry-with-backoff path.
- Skip when `errorMessage` already includes `context_length_exceeded` so the handler is idempotent.
