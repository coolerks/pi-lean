# RPC Mode

> 本页是 `packages/coding-agent/docs/rpc.md` 的中文参考译本，研究 commit 为 `853a80d26c90a14c1886f0ebb8ffaae133ca2185`。API 名称、命令、路径、配置字段和代码标识符保留原样。

## 中文导读

RPC Mode 是 Coding Agent 的无界面进程接口：客户端向 `stdin` 写入一条一行 JSON 命令，Pi 向 `stdout` 写出 response 和异步 event。它适合 IDE、自定义 TUI、测试驱动器或其他宿主进程；如果 Node.js 程序与 Agent 在同一进程，优先使用 `AgentSession`，不必为每个调用创建子进程。

## 源码级中文译文

本节按 `rpc.md` 的原文章节顺序翻译。每一节先说明协议事实，再给出客户端实现时需要观察的状态和失败点。示例代码保持原样，命令名、字段名、事件名、路径和 TypeScript 类型不翻译。

### 1. RPC Mode 是什么

RPC Mode 是 Coding Agent 的无界面运行模式。

它通过标准输入接收命令。

它通过标准输出发送 response 和 event。

每个协议记录都是一个 JSON object。

每条记录占一行。

这使它适合 IDE、桌面 UI、测试程序和后端服务嵌入。

它也适合用另一种语言包装 Pi。

但它不是一个通用的模型协议。

它首先是“控制一个 Pi 进程”的应用协议。

Node.js/TypeScript 应用如果可以直接使用 `AgentSession`，通常不必启动子进程。

直接使用 `AgentSession` 可以少经过一层 JSONL framing。

直接使用 `AgentSession` 也可以少处理 stdout/stderr 和进程退出。

子进程 RPC 适合进程隔离、语言隔离和独立升级。

因此选择 RPC 还是 SDK 是部署边界的决定，不是功能高低的决定。

> 译者注：RPC 和 MCP 都可能出现 JSON-RPC 或 JSON，但它们的方向不同。RPC 是宿主控制 Agent；MCP 是 Agent 连接外部工具、资源和 prompt server。把 `pi --mode rpc` 误当成 MCP server，会导致命令方向、生命周期和权限设计全部颠倒。

### 2. 启动参数与进程边界

启动命令是：

```bash
pi --mode rpc [options]
```

`--provider <name>` 选择默认 Provider。

`--model <pattern>` 选择模型或模型模式。

模型可以写成 `provider/id`。

模型后面可以附加 `:<thinking>`。

`--name <name>` 或 `-n <name>` 设置 session 显示名。

`--no-session` 关闭 session 持久化。

`--session-dir <path>` 修改 session 文件所在目录。

客户端启动进程后，应立即分别保存三个句柄。

`stdin` 用于写入命令。

`stdout` 用于读取协议记录。

`stderr` 用于读取诊断信息。

stdout 不能混入普通日志。

stdout 不能打印启动 banner。

stdout 不能打印调试 `console.log`。

stdout 不能打印 Python traceback。

任何非 JSON 行都可能使客户端解析失败。

stderr 可以包含诊断信息。

stderr 也应该由宿主持续读取。

如果不读取 stderr，缓冲区写满后子进程可能阻塞。

客户端应监听 stdout 的 `data`、`end` 和 `error`。

客户端应监听 stderr 的 `data` 和 `error`。

客户端还应监听子进程的 `exit`。

进程退出不是一条普通 event。

进程退出意味着后续 response 不会再到达。

仍处于 pending 状态的请求必须结束或标记为未知。

### 3. JSONL framing

RPC 使用严格的 JSONL framing。

记录分隔符是 LF，也就是字节 `0x0A`。

一条 JSON 记录内部可以包含转义后的 `\n`。

字符串里的 `\n` 不是记录边界。

只有真实的 LF 字节才切分记录。

客户端不应按任意 Unicode 行分隔符切分。

`U+2028` 可以合法出现在 JSON 字符串中。

`U+2029` 也可以合法出现在 JSON 字符串中。

Node 的 `readline` 会额外处理这些 Unicode 分隔符。

因此 Node `readline` 不是这个协议的严格 reader。

客户端可以接受输入端的 CRLF。

接受 CRLF 时只去掉一行末尾的 CR。

不要删除 JSON 字符串内部的 CR。

不要把空格或 tab 当作记录边界。

不要按 chunk 边界解析 JSON。

一次 `data` chunk 可能只包含半个 JSON。

一次 `data` chunk 也可能包含多条 JSON。

正确的 reader 必须维护字符串 buffer。

每次收到 bytes 时先用 UTF-8 decoder 解码。

然后在 buffer 中寻找真实 LF。

找到 LF 后取出前面的完整行。

如果该行以 CR 结尾，去掉最后一个 CR。

把剩余内容保留在 buffer 中。

stream `end` 时必须 flush decoder。

如果 flush 后还有非空 buffer，要处理最后一条记录。

协议发送方通常会以 LF 结束每条记录。

健壮客户端仍应处理 EOF 前的残留 buffer。

```text
chunk 1: {"type":"res
chunk 2: ponse"}\n{"type":"event"}\n
```

上面的 chunk 不能按 chunk 1 和 chunk 2 分别调用 JSON.parse。

正确结果是先拼出完整字符串，再按 LF 切出两条记录。

> 译者注：Go 中不要直接假定 `bufio.Scanner` 的默认 token 长度足够。RPC 的大消息、HTML 路径或 widget 可能超过默认限制；可以提高 buffer，或使用 `bufio.Reader.ReadString('\n')`。Java 中 `BufferedReader.readLine()` 能处理 LF/CRLF，但仍要确认它没有把 stdout 的诊断文本混进 JSON parser。

### 4. 请求、响应与 correlation id

命令由客户端写入 stdin。

命令必须是单行 JSON。

response 由 Pi 写入 stdout。

response 的 `type` 是 `response`。

response 的 `command` 表示对应命令。

response 的 `success` 表示命令是否被接受或处理成功。

每条命令可以带可选的 `id`。

如果带了 `id`，response 会复制同一个 id。

客户端可以用 `id` 找到等待中的请求。

不同命令的 id 应保持唯一。

不要把数组下标作为长期 correlation id。

不要仅凭 response 到达顺序匹配请求。

因为 prompt 接受后会异步产生 events。

event 通常没有原始 command id。

`bash_execution_update` 会带发起 bash 的 id（如果命令提供了 id）。

扩展 UI request 有它自己的唯一 id。

工具事件使用 `toolCallId`。

这些 id 属于不同的命名空间。

客户端应为 command id 建立 pending map。

客户端应为 extension UI id 建立 dialog map。

客户端应为 toolCallId 建立工具显示状态。

response 只解决 command 层的接受结果。

event 解决运行时进度和最终状态。

不能用 `success: true` 推断最终答案成功。

`success: true` 可能只表示消息已经排队。

`success: false` 表示命令在接受前就被拒绝。

接受后的 Provider error 不会再产生第二个 response。

接受后的 Tool error 应从 event/message 流观察。

### 5. `prompt` 命令

最小 prompt 命令如下：

```json
{"id":"req-1","type":"prompt","message":"Hello, world!"}
```

`type` 必须是 `prompt`。

`message` 是用户输入的文本。

`id` 用于关联接受 response。

prompt response 可能在模型完成前到达。

因此 prompt response 不是 final answer。

通常 response 是：

```json
{"id":"req-1","type":"response","command":"prompt","success":true}
```

这表示消息已被接受、排队或立即交给处理器。

如果消息在输入校验阶段失败，success 为 false。

如果模型随后返回 429，原 prompt 不会获得第二个 response。

客户端必须继续读取 events。

客户端必须继续读取 message_end。

客户端应把 `agent_settled` 作为一次完整工作的结束候选。

如果只等待 prompt response，客户端会过早显示 idle。

prompt 可以携带图片。

图片使用 `ImageContent` 格式。

图片的 `data` 是 base64 文本。

图片的 `mimeType` 描述媒体类型。

图像会增加上下文和请求成本。

客户端应限制图片大小。

客户端不应把未经授权的本地文件自动编码上传。

### 6. streamingBehavior、steer 与 follow_up

Agent 正在 streaming 时再次发送 prompt，需要声明 `streamingBehavior`。

`streamingBehavior: "steer"` 把消息放入 steering queue。

steer 在当前 assistant turn 的 Tool batch 完成后交付。

交付发生在下一次 LLM request 之前。

它适合“停止做 X，改做 Y”这类纠偏。

`streamingBehavior: "followUp"` 把消息放入 follow-up queue。

follow-up 要等当前工作自然结束。

它适合“完成后再检查文档”这类追加任务。

不提供 streamingBehavior 时，正在运行的 Agent 会拒绝普通 prompt。

`steer` 命令本身只适用于 active run。

`follow_up` 命令表示完成后追加。

两者都可以带图片。

两者都不允许直接执行 Extension command。

Skill 命令会在发送或排队前展开。

Prompt template 也会在发送或排队前展开。

Extension command 通过 `prompt` 发送时可能立即处理。

Extension command 的 LLM 工作由 Extension 自己管理。

队列不是把文本插进当前正在发送的 HTTP body。

队列消息要在安全的 turn boundary 注入。

这样可以保持 provider message 顺序。

这样也可以避免同时修改正在遍历的数组。

### 7. abort、clear_queue 与 new_session

`abort` 取消当前 Agent operation。

它不是一条新的用户消息。

它也不是强制杀死远端 HTTP server 的保证。

Provider 是否停止远端请求取决于 transport。

已发生的外部副作用不能因为 abort 就自动回滚。

`clear_queue` 移除 steering 和 follow-up。

clear_queue 的 data 会返回被移除的文本。

交互式 Esc 可以先 clear_queue。

客户端可以把返回文本放回编辑器。

然后客户端再发送 abort。

如果直接 abort，已经排队的消息可能继续处理。

这正是 TUI 需要区分“取消当前动作”和“清空待处理输入”的原因。

`new_session` 创建或切换到新 session。

可选 `parentSession` 用于保存父 session 关联。

Extension 可以通过 `session_before_switch` 取消切换。

被取消时 response 仍可能 success 为 true。

此时 `data.cancelled` 为 true。

success 表示 command 被处理。

cancelled 表示业务动作没有发生。

客户端必须同时读取这两个字段。

### 8. state、messages、model 与 thinking

`get_state` 读取当前运行状态。

`model` 是完整 Model 对象或 null。

`thinkingLevel` 是当前 reasoning level。

`isStreaming` 表示是否正在处理 Agent 流。

`isCompacting` 表示是否正在做 context compaction。

`steeringMode` 描述 steering 一次消费一条还是全部。

`followUpMode` 描述 follow-up 的消费策略。

`sessionFile` 是当前 session 文件路径。

`sessionId` 是当前 session 标识。

`sessionName` 是可选显示名。

`autoCompactionEnabled` 表示是否自动压缩。

`messageCount` 是当前消息投影的数量。

`pendingMessageCount` 是队列中待处理消息数量。

`get_messages` 返回当前对话消息。

它不是 append-only session tree 的完整快照。

它可能不包含 abandoned branch。

它也不能替代 `get_entries` 的 durable cursor。

`set_model` 用 provider 和 modelId 切换模型。

成功 response 的 data 是完整 Model。

`cycle_model` 选择下一个可用模型。

只有一个可用模型时 data 可能为 null。

`get_available_models` 返回所有配置模型。

模型信息可能包含 contextWindow 和 cost。

客户端不要只显示 name 而丢掉 provider/id。

因为不同 Provider 可能有同名模型。

`set_thinking_level` 支持 off、minimal、low、medium、high、xhigh、max。

xhigh 和 max 必须由当前模型能力决定。

不支持 reasoning 的模型通常只有 off。

`cycle_thinking_level` 在可用 level 中循环。

### 9. queue modes

`set_steering_mode` 控制 steering 消费方式。

`all` 在当前 turn 完成后一次交付全部 steering。

`one-at-a-time` 每个完成的 assistant turn 交付一条。

默认是 `one-at-a-time`。

`set_follow_up_mode` 控制 follow-up 消费方式。

`all` 在 Agent 完成时交付全部 follow-up。

`one-at-a-time` 每次完成只交付一条。

默认同样是 `one-at-a-time`。

queue mode 不改变消息的含义。

queue mode 也不等于 abort。

客户端应把 mode 持久化在自己的 UI 状态中。

如果用户修改 mode，下一次 get_state 应重新读取。

### 10. compact、retry 与 context overflow

`compact` 手动减少当前 context 的 token 压力。

它可以带 `customInstructions`。

返回值包含 summary。

返回值包含 `firstKeptEntryId`。

返回值包含 tokensBefore。

返回值包含 estimatedTokensAfter。

返回值可能包含生成 summary 的 usage。

estimatedTokensAfter 是 heuristic。

它不是 Provider 精确 tokenizer 的承诺。

不同 Provider 的 token 计数可能不同。

自定义 compaction handler 可能省略 usage。

`set_auto_compaction` 开关控制接近上限时的自动压缩。

overflow compaction 成功后通常会设置 `willRetry: true`。

这意味着 Pi 会有限度地重试原 prompt。

compaction 被 abort 时 result 为 null 且 aborted 为 true。

compaction 失败时 result 为 null 且 errorMessage 提供原因。

`set_auto_retry` 控制 transient error 的自动重试。

常见 transient error 是 overloaded、rate limit 和 5xx。

`abort_retry` 取消等待中的 delay。

它也阻止后续 retry attempt。

retry attempt 不是新的用户输入。

retry 可能产生新的 usage 和成本。

客户端显示 retry 时应显示 attempt/maxAttempts。

### 11. `bash` 与 stdout/stderr

`bash` 是直接 RPC command。

它不是模型返回的 Tool Call。

它立即在当前 cwd 执行 shell command。

请求可以带 command id。

输出通过 `bash_execution_update` events 流出。

最终 response 包含 output。

最终 response 包含 exitCode。

最终 response 包含 cancelled。

最终 response 包含 truncated。

如果输出被截断，可能包含 fullOutputPath。

流式 event 的 chunk 仍可能覆盖整个执行期间的输出。

`bash` 的 stdout/stderr 由 Pi 合并或按实现转换为结果。

外层 RPC 的 stdout 仍只允许 JSONL。

shell 命令产生的文字不能直接写入外层 stdout。

这就是“被执行命令的 stdout”和“RPC server 的 stdout”必须分开的原因。

直接 bash 的结果先形成 `BashExecutionMessage`。

它不会在 bash response 发出时自动成为下一次 LLM 的消息。

下一次 prompt 构建 context 时才会投影它。

投影形式包含 `Ran \`command\`` 和 fenced output。

多个 bash 可以先后执行。

后续 prompt 会一次看到这些 bash 结果。

`abort_bash` 只取消正在运行的直接 bash。

它不等同于 `abort` 当前 Agent operation。

> 译者注：这是最容易踩坑的两个 stdout。协议 stdout 是机器接口，shell stdout 是业务数据。Go/Java client 必须只从 Pi 的 stdout 解析 JSON；如果你自己启动 MCP 或 shell server，也应为其 stdout 建立独立 pipe，不能把两个进程的输出拼在一起。

### 12. session、stats、fork 与 tree

`get_session_stats` 返回 session 级统计。

统计包括 userMessages。

统计包括 assistantMessages。

统计包括 toolCalls 和 toolResults。

统计包括 tokens。

统计包括 cost。

统计包括 contextUsage。

Tool 内部的 LLM 工作可能进入统计。

compaction 和 branch summary 的 usage 也可能进入统计。

刚完成 compaction 时 tokens/percent 可能是 null。

因为新的 assistant usage 还没有产生。

`export_html` 把 session 导出成 HTML。

默认路径由 Pi 决定。

也可以传入 outputPath。

`switch_session` 载入另一个 JSONL session。

它可能被 `session_before_switch` 取消。

`fork` 从 active branch 的 user entry 创建新分支。

它返回被 fork 的原文本。

`clone` 把当前 branch 复制到新 session。

`get_fork_messages` 返回可供 fork 的 user messages。

`get_entries` 按 append 顺序读取 entry。

它不包含 session header。

它包含 compaction 前历史。

它包含 abandoned branch。

`since` 是 entry id cursor。

正确的 cursor 可以跨客户端重启使用。

找不到 since 时 response 为失败。

`leafId` 表示当前活动叶子。

空 session 的 leafId 为 null。

`get_tree` 返回 entry、children、label 和 labelTimestamp。

parent chain 断裂的 entry 也会作为 root 出现。

`get_last_assistant_text` 没有 assistant 时返回 text null。

`set_session_name` 修改当前显示名。

启动时也可以用 `--name` 设置初始名称。

### 13. commands、skills 与 prompt templates

`get_commands` 返回可用的 extension commands。

它也返回 prompt templates。

它还返回 skills。

extension command 的 source 是 `extension`。

prompt template 的 source 是 `prompt`。

skill 的 source 是 `skill`。

skill 名称通常带 `skill:` 前缀。

location 可以是 user。

location 可以是 project。

location 也可以来自显式 path。

path 可能是绝对路径。

客户端应把 path 当作提示信息，不应无条件读取或执行。

`/settings`、`/hotkeys` 等 TUI 内建命令不会出现在列表中。

它们依赖交互式 TUI。

RPC 客户端可以把 get_commands 结果渲染成自己的 palette。

调用时仍应通过 prompt 发送正确的 `/name`。

### 14. events 总体模型

events 是 Agent operation 的观察流。

它们以 JSONL 写入 stdout。

event 通常不带原始 prompt id。

客户端必须用事件字段和本地状态进行关联。

`agent_start` 表示低层 Agent run 开始。

`agent_end` 表示一个低层 run 结束。

`agent_end` 后仍可能发生 retry。

`agent_end` 后仍可能发生 compaction retry。

`agent_end` 后仍可能处理 queued continuation。

`agent_settled` 表示 session 级工作真正稳定。

UI busy 状态更适合等待 agent_settled。

`turn_start` 开始一个 assistant turn。

`turn_end` 结束该 turn。

一个 turn 可能包含多个 Tool result。

`message_start` 和 `message_end` 包围一条消息。

`message_end.message` 是最终权威消息。

### 15. message_update 与流式拼装

`message_update` 提供增量事件。

它不是完整的累计 message 快照。

`usage` 是最新累计 usage。

有些 Provider 直到结束才报告 usage。

因此流中 usage 可能暂时是零。

`text_start` 表示文本 block 开始。

`text_delta` 表示文本片段。

`text_end` 表示文本 block 结束。

`thinking_start` 表示 thinking block 开始。

`thinking_delta` 表示 thinking 片段。

`thinking_end` 表示 thinking block 结束。

`toolcall_start` 提供 id 和 toolName。

`toolcall_delta` 提供参数片段。

`toolcall_end` 提供完整 toolCall。

客户端应按 contentIndex 保存多个 block。

不能把不同 contentIndex 的 delta 拼在一起。

工具参数通常需要把多个字符串片段连接起来。

连接后还要解析 JSON。

解析前不能执行工具。

`message_update` 不再保证旧的 partial 字段存在。

客户端应从 message_start 加 delta 自己构建展示状态。

完成时用 message_end 覆盖本地 partial。

### 16. 工具 events 与队列 events

`bash_execution_update` 关联直接 bash command。

它的 id 复制命令 id。

`tool_execution_start` 表示 LLM Tool 开始。

`tool_execution_update` 表示工具的累计 partial result。

`tool_execution_end` 表示工具完成。

工具 event 使用 `toolCallId` 关联。

`partialResult` 是累计值，不只是本次 delta。

UI 可以直接用最新 partialResult 替换旧显示。

不要把累计结果重复追加，否则界面会重复文本。

`queue_update` 表示 pending steering/follow-up 变化。

它不是 message_end。

它也不是 durable session tree 的完整记录。

`compaction_start` 携带 manual、threshold 或 overflow reason。

`compaction_end` 携带 result、aborted 和 willRetry。

`auto_retry_start` 携带 attempt、delayMs 和错误。

`auto_retry_end` 表示 retry 成功或最终失败。

摘要 retry 有三个独立事件。

`extension_error` 记录 extensionPath、event 和 error。

客户端遇到未知 event type 时应保留原始 JSON。

这样新版本增加 event 时旧客户端仍可诊断。

### 17. Extension UI 子协议

Extension UI 是建立在 RPC 基础流之上的第二层协议。

dialog 方法会暂停 Extension，等待 response。

fire-and-forget 方法只发送 request，不等待 response。

所有 UI request 都有 `type: "extension_ui_request"`。

所有 UI request 都有唯一 id。

所有 UI request 都有 method。

`select` 请求包含 title 和 options。

客户端返回 value 或 cancelled。

`confirm` 请求包含 title 和 message。

客户端返回 confirmed 或 cancelled。

`input` 请求要求自由文本。

客户端返回 value 或 cancelled。

`editor` 请求可以携带 prefill。

返回值是编辑后的多行文本。

`notify` 是无需响应的通知。

`notifyType` 可以是 info、warning 或 error。

`setStatus` 使用 statusKey 更新状态。

省略 statusText 可以清除状态。

`setWidget` 使用 widgetKey 和 widgetLines。

widgetPlacement 可以是 aboveEditor 或 belowEditor。

RPC 只支持字符串数组 widget。

component factory 不会在 RPC 中执行。

`setTitle` 修改 terminal title。

`set_editor_text` 修改输入编辑器文本。

dialog 的 id 必须精确匹配。

错误 id 不应被接受为当前 dialog 的回答。

超时由 Agent 端自动解决。

客户端不需要另起 timer 模拟 Agent timeout。

RPC 中 `ctx.mode` 是 `rpc`。

RPC 中 `ctx.hasUI` 是 true。

这不表示存在真实 TUI。

`custom()` 返回 undefined。

working indicator、footer、header 等 TUI 专属方法是 no-op。

`getEditorText()` 返回空字符串。

`getToolsExpanded()` 返回 false。

`getAllThemes()` 返回空数组。

`getTheme()` 返回 undefined。

`setTheme()` 返回失败结果。

需要真实 TUI 组件时应检查 `ctx.mode === "tui"`。

> 译者注：`hasUI: true` 在这里的意思是“对话框协议可用”，不是“可以安全调用所有 TUI API”。Java 客户端应把 UI request 当成异步 RPC，并用 `CompletableFuture`/Future 按 id 保存等待者；Go 客户端可以用 channel 或 callback 分发 response。fire-and-forget 不应误发送 response。

### 18. 错误、取消和进程退出

命令未被接受时返回 `success: false`。

未知 command 是输入错误。

缺少必填字段是输入错误。

model 不存在是业务校验错误。

JSON 解析失败会返回 parse error。

解析失败不应使客户端继续猜测字段。

接受后的模型错误通过正常 event/message 流发送。

接受后的 tool error 也通过正常流发送。

compaction 失败通过 compaction event 体现。

retry 耗尽通过 auto_retry_end 体现。

abort 是一种终止原因。

客户端必须区分 rejected 和 failed。

rejected 表示没有创建工作。

failed 表示工作已接受但执行失败。

abort 不保证远端计费停止。

abort_bash 不保证已经启动的子进程回滚。

session corrupted 时客户端应保留错误并停止自动写入。

EOF 表示 Pi 进程已离开协议循环。

进程 exit code 需要和最后一个 event 一起判断。

stdout 解析失败时应记录原始行，但注意脱敏。

stderr 不应被当作协议 response。

API key、Authorization 和工具参数不应无条件写日志。

`Model` 是模型能力和计费 metadata 的 JSON 投影。

### 20. Python client 逐行解释

Python 示例使用 `subprocess.Popen` 启动 RPC 子进程。

`stdin=subprocess.PIPE` 让客户端发送命令。

`stdout=subprocess.PIPE` 让客户端读取 JSONL。

`text=True` 让 Python 以文本流处理。

生产代码仍应明确 UTF-8 编码策略。

`send(cmd)` 使用 `json.dumps` 序列化命令。

末尾加真实换行。

调用 flush 让命令及时进入子进程。

`read_events()` 逐行读取 stdout。

每行调用 `json.loads`。

坏行应捕获 JSONDecodeError。

不能让一个坏 event 使整个进程无提示退出。

示例监听 `message_update`。

它取出 `assistantMessageEvent`。

它只输出 text_delta。

thinking 和 toolcall 应由更完整的 UI 另行处理。

示例用 agent_end 结束循环。

严谨客户端应等待 agent_settled。

客户端还应开线程或异步任务读取 stderr。

收到 EOF 时应结束所有 pending promise。

### 21. Node.js client 逐步解释

Node 示例用 `spawn` 启动 Pi。

`StringDecoder("utf8")` 防止多字节字符跨 chunk 被拆坏。

不能对每个 Buffer 直接调用 `toString` 后简单拼接未完成字符。

`buffer` 保存尚未切出的文本。

reader 只寻找 `\n`。

找到后切出一行。

去掉末尾 `\r` 以兼容 CRLF。

`end` 时调用 decoder.end。

最后残留内容也要交给 onLine。

解析出的 JSON 可能是 response 或 event。

二者都必须依据 `type` 分流。

`message_update` 的 text_delta 可以立即渲染。

`SIGINT` 时发送 abort 是友好取消。

直接 `agent.kill()` 可能丢失末尾 event。

kill 仍是超时后的兜底措施。

stdin 写入后应保存 pending command id。

UI request response 要使用另一个 id map。

子进程退出后不能永久等待没有 response 的 request。

> 译者注：Java 的 `ProcessBuilder` 对应 Node `spawn`，`BufferedReader` 对应严格 JSONL reader，Jackson 对应 `JSON.parse`，`ExecutorService`/Future 对应异步读取和取消；Java `HttpClient` 适合模型或远端 RPC 的 HTTP transport，但不能替代本地进程的 stdin/stdout pipe。Go 的 `exec.Cmd`、`StdoutPipe`、`bufio.Reader` 和 `encoding/json` 也能实现同一边界，需要自己定义 id map、EOF 和 context cancellation 语义。

### 22. RPC 与 MCP 的最终辨析

RPC 的 client 是宿主应用。

RPC 的 server 是 Pi coding agent 进程。

RPC 命令控制 prompt、model、session、bash 和 UI。

RPC event 描述 Pi 的运行过程。

MCP 的 client 通常属于 Agent Runtime。

MCP 的 server 提供工具、资源或 prompt。

MCP 的典型方法包括 initialize。

MCP 还包括 tools/list。

MCP 还包括 tools/call。

MCP 可能使用 stdio。

MCP 也可能使用 HTTP transport。

RPC 的 prompt 方向是 client 到 Agent。

MCP 的 tools/call 方向是 Agent 到外部 server。

RPC 的 event 是 Agent 到 client。

MCP server 的 response 是对 MCP request 的回应。

RPC 的 session 是 Pi 对话状态。

MCP 的 session/connection 是协议能力协商状态。

二者的权限主体也不同。

RPC client 可能获得 bash 和 session 控制能力。

MCP server 只应获得明确注册的工具能力。

不要把 RPC stdout 当成 MCP transport。

不要把 `extension_ui_request` 当成 MCP request。

不要把 `tool_execution_start` 当成 JSON-RPC response。

RPC 的最小单位是一行 JSON。

stdin 是命令入口。

stdout 是协议出口。

stderr 是诊断出口。

response 说明命令层是否接受。

message_end 是消息完成边界。

agent_settled 是 session 级稳定边界。

RPC 和 MCP 解决不同的连接问题。

Go 和 Java 都能从标准库实现客户端。

但客户端必须把 framing、取消、错误和安全边界写清楚。

这才是一个可维护的 Agent RPC 集成，而不是“启动进程然后读几行文本”。

````markdown
# RPC Mode

RPC mode enables headless operation of the coding agent via a JSON protocol over stdin/stdout. This is useful for embedding the agent in other applications, IDEs, or custom UIs.

**Note for Node.js/TypeScript users**: If you're building a Node.js application, consider using `AgentSession` directly from `@earendil-works/pi-coding-agent` instead of spawning a subprocess. See [`src/core/agent-session.ts`](../src/core/agent-session.ts) for the API. For a subprocess-based TypeScript client, see [`src/modes/rpc/rpc-client.ts`](../src/modes/rpc/rpc-client.ts).

## Starting RPC Mode

```bash
pi --mode rpc [options]
```

Common options:
- `--provider <name>`: Set the LLM provider (anthropic, openai, google, etc.)
- `--model <pattern>`: Model pattern or ID (supports `provider/id` and optional `:<thinking>`)
- `--name <name>` / `-n <name>`: Set the session display name at startup
- `--no-session`: Disable session persistence
- `--session-dir <path>`: Custom session storage directory

## Protocol Overview

- **Commands**: JSON objects sent to stdin, one per line
- **Responses**: JSON objects with `type: "response"` indicating command success/failure
- **Events**: Agent events streamed to stdout as JSON lines

All commands support an optional `id` field for request/response correlation. If provided, the corresponding response will include the same `id`. `bash_execution_update` events also include the `id` of their originating `bash` command.

### Framing

RPC mode uses strict JSONL semantics with LF (`\n`) as the only record delimiter.

This matters for clients:
- Split records on `\n` only
- Accept optional `\r\n` input by stripping a trailing `\r`
- Do not use generic line readers that treat Unicode separators as newlines

In particular, Node `readline` is not protocol-compliant for RPC mode because it also splits on `U+2028` and `U+2029`, which are valid inside JSON strings.

## Commands

### Prompting

#### prompt

Send a user prompt to the agent. The command response is emitted after the prompt is accepted, queued, or handled. Events continue streaming asynchronously after acceptance.

```json
{"id": "req-1", "type": "prompt", "message": "Hello, world!"}
```

With images:
```json
{"type": "prompt", "message": "What's in this image?", "images": [{"type": "image", "data": "base64-encoded-data", "mimeType": "image/png"}]}
```

**During streaming**: If the agent is already streaming, you must specify `streamingBehavior` to queue the message:

```json
{"type": "prompt", "message": "New instruction", "streamingBehavior": "steer"}
```

- `"steer"`: Queue the message while the agent is running. It is delivered after the current assistant turn finishes executing its tool calls, before the next LLM call.
- `"followUp"`: Wait until the agent finishes. Message is delivered only when agent stops.

If the agent is streaming and no `streamingBehavior` is specified, the command returns an error.

**Extension commands**: If the message is an extension command (e.g., `/mycommand`), it executes immediately even during streaming. Extension commands manage their own LLM interaction via `pi.sendMessage()`.

**Input expansion**: Skill commands (`/skill:name`) and prompt templates (`/template`) are expanded before sending/queueing.

Response:
```json
{"id": "req-1", "type": "response", "command": "prompt", "success": true}
```

`success: true` means the prompt was accepted, queued, or handled immediately. `success: false` means the prompt was rejected before acceptance. Failures after acceptance are reported through the normal event and message stream, not as a second `response` for the same request id.

The `images` field is optional. Each image uses `ImageContent` format: `{"type": "image", "data": "base64-encoded-data", "mimeType": "image/png"}`.

#### steer

Queue a steering message while the agent is running. It is delivered after the current assistant turn finishes executing its tool calls, before the next LLM call. Skill commands and prompt templates are expanded. Extension commands are not allowed (use `prompt` instead).

```json
{"type": "steer", "message": "Stop and do this instead"}
```

With images:
```json
{"type": "steer", "message": "Look at this instead", "images": [{"type": "image", "data": "base64-encoded-data", "mimeType": "image/png"}]}
```

The `images` field is optional. Each image uses `ImageContent` format (same as `prompt`).

Response:
```json
{"type": "response", "command": "steer", "success": true}
```

See [set_steering_mode](#set_steering_mode) for controlling how steering messages are processed.

#### follow_up

Queue a follow-up message to be processed after the agent finishes. Delivered only when agent has no more tool calls or steering messages. Skill commands and prompt templates are expanded. Extension commands are not allowed (use `prompt` instead).

```json
{"type": "follow_up", "message": "After you're done, also do this"}
```

With images:
```json
{"type": "follow_up", "message": "Also check this image", "images": [{"type": "image", "data": "base64-encoded-data", "mimeType": "image/png"}]}
```

The `images` field is optional. Each image uses `ImageContent` format (same as `prompt`).

Response:
```json
{"type": "response", "command": "follow_up", "success": true}
```

See [set_follow_up_mode](#set_follow_up_mode) for controlling how follow-up messages are processed.

#### abort

Abort the current agent operation.

```json
{"type": "abort"}
```

Response:
```json
{"type": "response", "command": "abort", "success": true}
```

#### clear_queue

Remove queued steering and follow-up messages and return their text.

```json
{"type": "clear_queue"}
```

Response:
```json
{
  "type": "response",
  "command": "clear_queue",
  "success": true,
  "data": {
    "steering": ["Change direction"],
    "followUp": ["Summarize when finished"]
  }
}
```

To implement interactive Esc behavior, send `clear_queue` before `abort`, then restore the returned text in the client editor. `abort` continues queued messages when they remain in the session.

#### new_session

Start a fresh session. Can be cancelled by a `session_before_switch` extension event handler.

```json
{"type": "new_session"}
```

With optional parent session tracking:
```json
{"type": "new_session", "parentSession": "/path/to/parent-session.jsonl"}
```

Response:
```json
{"type": "response", "command": "new_session", "success": true, "data": {"cancelled": false}}
```

If an extension cancelled:
```json
{"type": "response", "command": "new_session", "success": true, "data": {"cancelled": true}}
```

#### bash

```json

```json

  "type": "response",
  "command": "bash",
  "success": true,
  "data": {

    "cancelled": false,
    "truncated": false
  }
}
```

If output was truncated, includes `fullOutputPath`:
```json
{
  "type": "response",
  "command": "bash",
  "success": true,
  "data": {
    "output": "truncated output...",
    "exitCode": 0,
    "cancelled": false,
    "truncated": true,
    "fullOutputPath": "/tmp/pi-bash-abc123.log"
  }
}
```

**How bash results reach the LLM:**

The `bash` command executes immediately and returns a `BashResult`. Internally, a `BashExecutionMessage` is created and stored in the agent's message state.

When the next `prompt` command is sent, all messages (including `BashExecutionMessage`) are transformed before being sent to the LLM. The `BashExecutionMessage` is converted to a `UserMessage` with this format:

````
Ran `ls -la`
```
total 48
drwxr-xr-x ...
```
````

This means:
1. Bash output is included in the LLM context on the **next prompt**, not immediately
2. Multiple bash commands can be executed before a prompt; all outputs will be included

## Events

Events are streamed to stdout as JSON lines during agent operation. Events do not generally include an `id` field; `bash_execution_update` includes the `id` of its originating `bash` command when one was provided.

### Event Types

| Event | Description |
|-------|-------------|
| `agent_start` | Agent begins processing |
| `agent_end` | One low-level agent run completes (may still be followed by retry, compaction, or queued continuations) |
| `agent_settled` | Agent run is fully settled; no automatic retry, compaction retry, or queued continuation remains |
| `turn_start` | New turn begins |
| `turn_end` | Turn completes (includes assistant message and tool results) |
| `message_start` | Message begins |
| `message_update` | Streaming update (text/thinking/toolcall deltas) |
| `message_end` | Message completes |
| `bash_execution_update` | Direct RPC bash command output chunk |
| `tool_execution_start` | Tool begins execution |
| `tool_execution_update` | Tool execution progress (streaming output) |
| `tool_execution_end` | Tool completes |
| `queue_update` | Pending steering/follow-up queue changed |
| `compaction_start` | Compaction begins |
| `compaction_end` | Compaction completes |
| `auto_retry_start` | Auto-retry begins (after transient error) |
| `auto_retry_end` | Auto-retry completes (success or final failure) |
| `summarization_retry_scheduled` | Retry scheduled for a transient compaction or branch-summary summarization error |
| `summarization_retry_attempt_start` | Retried summarization request starts |
| `summarization_retry_finished` | Summarization retry loop completes |
| `extension_error` | Extension threw an error |

### agent_start

Emitted when the agent begins processing a prompt.

```json
{"type": "agent_start"}
```

### agent_end

Emitted when one low-level agent run completes. Contains all messages generated during this run. If `willRetry` is true, an automatic retry will follow.

```json
{
  "type": "agent_end",
  "messages": [...],
  "willRetry": false
}
```

### agent_settled

Emitted after the full session-level run settles. At this point Pi will not continue automatically through retry, compaction retry, or queued follow-up messages.

```json
{"type": "agent_settled"}
```

### turn_start / turn_end

A turn consists of one assistant response plus any resulting tool calls and results.

```json
{"type": "turn_start"}
```

```json
{
  "type": "turn_end",
  "message": {...},
  "toolResults": [...]
}
```

### message_start / message_end

Emitted when a message begins and completes. The `message` field contains an `AgentMessage`.

```json
{"type": "message_start", "message": {...}}
{"type": "message_end", "message": {...}}
```

### message_update (Streaming)

Emitted during streaming of assistant messages. Contains a delta event without a cumulative message snapshot.

```json
{
  "type": "message_update",
  "usage": {
    "input": 100,
    "output": 1,
    "cacheRead": 0,
    "cacheWrite": 0,
    "totalTokens": 101,
    "cost": {"input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0, "total": 0}
  },
  "assistantMessageEvent": {
    "type": "text_delta",
    "contentIndex": 0,
    "delta": "Hello "
  }
}
```

The `assistantMessageEvent` field contains one of these delta types:

| Type | Description |
|------|-------------|
| `text_start` | Text content block started |
| `text_delta` | Text content chunk |
| `text_end` | Text content block ended |
| `thinking_start` | Thinking block started |
| `thinking_delta` | Thinking content chunk |
| `thinking_end` | Thinking block ended |
| `toolcall_start` | Tool call started (includes `id` and `toolName`) |
| `toolcall_delta` | Tool call arguments chunk |
| `toolcall_end` | Tool call ended (includes full `toolCall` object) |

Example streaming a text response:
```json
{"type":"message_update","usage":{...},"assistantMessageEvent":{"type":"text_start","contentIndex":0}}
{"type":"message_update","usage":{...},"assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"Hello"}}
{"type":"message_update","usage":{...},"assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":" world"}}
{"type":"message_update","usage":{...},"assistantMessageEvent":{"type":"text_end","contentIndex":0,"content":"Hello world"}}
```

The top-level `usage` field contains the latest cumulative provider-reported usage. It may remain
zero until completion when a provider does not report usage during streaming.

Example starting a tool call:
```json
{"type":"message_update","usage":{...},"assistantMessageEvent":{"type":"toolcall_start","contentIndex":1,"id":"call_abc123","toolName":"write"}}
```

`message_update` intentionally omits the former cumulative `message` field and
`assistantMessageEvent.partial`. Clients that need a live partial message must assemble it
from `message_start` and subsequent events using `contentIndex`. Treat `message_end.message`
as authoritative. For tool calls, `toolcall_start` provides the call `id` and `toolName`;
buffer `toolcall_delta.delta` for arguments. `toolcall_end.toolCall` contains the completed
call.

### bash_execution_update

Emitted once for each output chunk from a direct `bash` command. `id` matches the command's `id`, allowing clients to associate output with the correct command.

Events stream all output while the command runs, even if the final `bash` response's `output` is truncated.

```json
{
  "type": "bash_execution_update",
  "id": "req-1",
  "delta": "total 48\n"
}
```

### tool_execution_start / tool_execution_update / tool_execution_end

Emitted when a tool begins, streams progress, and completes execution.

```json
{
  "type": "tool_execution_start",
  "toolCallId": "call_abc123",
  "toolName": "bash",
  "args": {"command": "ls -la"}
}
```

During execution, `tool_execution_update` events stream partial results (e.g., bash output as it arrives):

```json
{
  "type": "tool_execution_update",
  "toolCallId": "call_abc123",
  "toolName": "bash",
  "args": {"command": "ls -la"},
  "partialResult": {
    "content": [{"type": "text", "text": "partial output so far..."}],
    "details": {"truncation": null, "fullOutputPath": null}
  }
}
```

When complete:

```json
{
  "type": "tool_execution_end",
  "toolCallId": "call_abc123",
  "toolName": "bash",
  "result": {
    "content": [{"type": "text", "text": "total 48\n..."}],
    "details": {...}
  },
  "isError": false
}
```

Use `toolCallId` to correlate events. The `partialResult` in `tool_execution_update` contains the accumulated output so far (not just the delta), allowing clients to simply replace their display on each update.

```json

## Extension UI Protocol

Extensions can request user interaction via `ctx.ui.select()`, `ctx.ui.confirm()`, etc. In RPC mode, these are translated into a request/response sub-protocol on top of the base command/event flow.

There are two categories of extension UI methods:

- **Dialog methods** (`select`, `confirm`, `input`, `editor`): emit an `extension_ui_request` on stdout and block until the client sends back an `extension_ui_response` on stdin with the matching `id`.
- **Fire-and-forget methods** (`notify`, `setStatus`, `setWidget`, `setTitle`, `set_editor_text`): emit an `extension_ui_request` on stdout but do not expect a response. The client can display the information or ignore it.

If a dialog method includes a `timeout` field, the agent-side will auto-resolve with a default value when the timeout expires. The client does not need to track timeouts.

Some `ExtensionUIContext` methods are not supported or degraded in RPC mode because they require direct TUI access:
- `custom()` returns `undefined`
- `setWorkingMessage()`, `setWorkingIndicator()`, `setFooter()`, `setHeader()`, `setEditorComponent()`, `setToolsExpanded()` are no-ops
- `getEditorText()` returns `""`
- `getToolsExpanded()` returns `false`
- `pasteToEditor()` delegates to `setEditorText()` (no paste/collapse handling)
- `getAllThemes()` returns `[]`
- `getTheme()` returns `undefined`
- `setTheme()` returns `{ success: false, error: "..." }`

Note: `ctx.mode` is `"rpc"` and `ctx.hasUI` is `true` in RPC mode because the dialog and fire-and-forget methods are functional via the extension UI sub-protocol. Use `ctx.mode === "tui"` to guard TUI-specific features like `custom()` that require a real terminal.

### Extension UI Requests (stdout)

All requests have `type: "extension_ui_request"`, a unique `id`, and a `method` field.

#### select

Prompt the user to choose from a list. Dialog methods with a `timeout` field include the timeout in milliseconds; the agent auto-resolves with `undefined` if the client doesn't respond in time.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-1",
  "method": "select",
  "title": "Allow dangerous command?",
  "options": ["Allow", "Block"],
  "timeout": 10000
}
```

Expected response: `extension_ui_response` with `value` (the selected option string) or `cancelled: true`.

#### confirm

Prompt the user for yes/no confirmation.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-2",
  "method": "confirm",
  "title": "Clear session?",
  "message": "All messages will be lost.",
  "timeout": 5000
}
```

Expected response: `extension_ui_response` with `confirmed: true/false` or `cancelled: true`.

#### input

Prompt the user for free-form text.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-3",
  "method": "input",
  "title": "Enter a value",
  "placeholder": "type something..."
}
```

Expected response: `extension_ui_response` with `value` (the entered text) or `cancelled: true`.

#### editor

Open a multi-line text editor with optional prefilled content.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-4",
  "method": "editor",
  "title": "Edit some text",
  "prefill": "Line 1\nLine 2\nLine 3"
}
```

Expected response: `extension_ui_response` with `value` (the edited text) or `cancelled: true`.

#### notify

Display a notification. Fire-and-forget, no response expected.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-5",
  "method": "notify",
  "message": "Command blocked by user",
  "notifyType": "warning"
}
```

The `notifyType` field is `"info"`, `"warning"`, or `"error"`. Defaults to `"info"` if omitted.

#### setStatus

Set or clear a status entry in the footer/status bar. Fire-and-forget.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-6",
  "method": "setStatus",
  "statusKey": "my-ext",
  "statusText": "Turn 3 running..."
}
```

Send `statusText: undefined` (or omit it) to clear the status entry for that key.

#### setWidget

Set or clear a widget (block of text lines) displayed above or below the editor. Fire-and-forget.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-7",
  "method": "setWidget",
  "widgetKey": "my-ext",
  "widgetLines": ["--- My Widget ---", "Line 1", "Line 2"],
  "widgetPlacement": "aboveEditor"
}
```

Send `widgetLines: undefined` (or omit it) to clear the widget. The `widgetPlacement` field is `"aboveEditor"` (default) or `"belowEditor"`. Only string arrays are supported in RPC mode; component factories are ignored.

#### setTitle

Set the terminal window/tab title. Fire-and-forget.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-8",
  "method": "setTitle",
  "title": "pi - my project"
}
```

#### set_editor_text

Set the text in the input editor. Fire-and-forget.

```json
{
  "type": "extension_ui_request",
  "id": "uuid-9",
  "method": "set_editor_text",
  "text": "prefilled text for the user"
}
```

### Extension UI Responses (stdin)

Responses are sent for dialog methods only (`select`, `confirm`, `input`, `editor`). The `id` must match the request.

#### Value response (select, input, editor)

```json
{"type": "extension_ui_response", "id": "uuid-1", "value": "Allow"}
```

#### Confirmation response (confirm)

```json
{"type": "extension_ui_response", "id": "uuid-2", "confirmed": true}
```

#### Cancellation response (any dialog)

Dismiss any dialog method. The extension receives `undefined` (for select/input/editor) or `false` (for confirm).

```json
{"type": "extension_ui_response", "id": "uuid-3", "cancelled": true}
```

## Error Handling

Failed commands return a response with `success: false`:

```json
{
  "type": "response",
  "command": "set_model",
  "success": false,
  "error": "Model not found: invalid/model"
}
```

Parse errors:

```json
{
  "type": "response",
  "command": "parse",
  "success": false,
  "error": "Failed to parse command: Unexpected token..."
}
```

## Example: Basic Client (Python)

```python
import subprocess
import json

proc = subprocess.Popen(
    ["pi", "--mode", "rpc", "--no-session"],
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    text=True
)

def send(cmd):
    proc.stdin.write(json.dumps(cmd) + "\n")
    proc.stdin.flush()

def read_events():
    for line in proc.stdout:
        yield json.loads(line)

# Send prompt
send({"type": "prompt", "message": "Hello!"})

# Process events
for event in read_events():
    if event.get("type") == "message_update":
        delta = event.get("assistantMessageEvent", {})
        if delta.get("type") == "text_delta":
            print(delta["delta"], end="", flush=True)
    
    if event.get("type") == "agent_end":
        print()
        break
```

## Example: Interactive Client (Node.js)

See [`test/rpc-example.ts`](../test/rpc-example.ts) for a complete interactive example, or [`src/modes/rpc/rpc-client.ts`](../src/modes/rpc/rpc-client.ts) for a typed client implementation.

For a complete example of handling the extension UI protocol, see [`examples/rpc-extension-ui.ts`](../examples/rpc-extension-ui.ts) which pairs with the [`examples/extensions/rpc-demo.ts`](../examples/extensions/rpc-demo.ts) extension.

```javascript
const { spawn } = require("child_process");
const { StringDecoder } = require("string_decoder");

const agent = spawn("pi", ["--mode", "rpc", "--no-session"]);

function attachJsonlReader(stream, onLine) {
    const decoder = new StringDecoder("utf8");
    let buffer = "";

    stream.on("data", (chunk) => {
        buffer += typeof chunk === "string" ? chunk : decoder.write(chunk);

        while (true) {
            const newlineIndex = buffer.indexOf("\n");
            if (newlineIndex === -1) break;

            let line = buffer.slice(0, newlineIndex);
            buffer = buffer.slice(newlineIndex + 1);
            if (line.endsWith("\r")) line = line.slice(0, -1);
            onLine(line);
        }
    });

    stream.on("end", () => {
        buffer += decoder.end();
        if (buffer.length > 0) {
            onLine(buffer.endsWith("\r") ? buffer.slice(0, -1) : buffer);
        }
    });
}

attachJsonlReader(agent.stdout, (line) => {
    const event = JSON.parse(line);

    if (event.type === "message_update") {
        const { assistantMessageEvent } = event;
        if (assistantMessageEvent.type === "text_delta") {
            process.stdout.write(assistantMessageEvent.delta);
        }
    }
});

// Send prompt
agent.stdin.write(JSON.stringify({ type: "prompt", message: "Hello" }) + "\n");

// Abort on Ctrl+C
process.on("SIGINT", () => {
    agent.stdin.write(JSON.stringify({ type: "abort" }) + "\n");
});
```
````
