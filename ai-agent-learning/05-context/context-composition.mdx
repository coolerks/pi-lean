# Context 是怎么组装的

## 学习目标

读完本页，你应该能够：

1. 区分模型参数、System Prompt、消息历史和 Tool Definition。
2. 从源码定位一次请求的 context 是在哪里组装的。
3. 解释 `AGENTS.md`、`CLAUDE.md`、Skill、Extension 和 Session 如何进入请求。
4. 打印最终发送给 Provider 的内容，而不是凭 Session 文件猜测。

## 先解决一个常见误解

“Context”不是一个字符串，也不是“数据库里所有记忆的总和”。在一次模型调用中，它至少包含几类不同生命周期的数据：

- **System Prompt**：宿主对模型的稳定规则和环境说明。
- **Message history**：当前分支上已经发生的 user、assistant、tool result 消息。
- **Tool definitions**：模型可以请求的工具名称、说明和参数 schema。
- **Request options**：模型、thinking level、token 上限、transport、timeout 和取消信号。

这些内容共同决定模型本轮能看到什么，但 Provider API 可能把它们放在不同字段中。Session 里存在某条记录，也不代表它一定会出现在本轮请求中。

## 从纯聊天到 Coding Agent

纯聊天只有一次投影：

```text
user text
  -> messages
  -> Provider request
  -> assistant text
```

Coding Agent 的投影更像这样：

```text
资源加载
  -> project context + skills + prompt templates + extensions
  -> system prompt 和 tool registry
Session 当前 leaf
  -> branch path
  -> AgentMessage[]
  -> convertToLlm()
一次请求
  -> systemPrompt + messages + tools + model options
```

注意最后一步不是把所有对象 `JSON.stringify`。UI-only custom entry、label、Session metadata 可能需要留在 Session，却不能发送给模型。

## Pi 的真实调用链

研究 commit：`853a80d26c90a14c1886f0ebb8ffaae133ca2185`。

```mermaid
sequenceDiagram
    participant User as 用户输入
    participant Session as AgentSession
    participant Loader as ResourceLoader
    participant Prompt as buildSystemPrompt
    participant Loop as runAgentLoop
    participant Convert as convertToLlm
    participant Model as Provider/Model

    User->>Session: prompt(text)
    Session->>Loader: 读取 context files / skills / prompts
    Session->>Prompt: 组装 base system prompt 和 active tools
    Session->>Loop: 传入 AgentContext
    Loop->>Loop: transformContext（可选）
    Loop->>Convert: AgentMessage[] -> Message[]
    Convert-->>Loop: Provider messages
    Loop->>Model: stream(model, Context, options)
    Model-->>Loop: assistant stream
```

**读图方法**：`ResourceLoader` 负责发现资源，`buildSystemPrompt` 负责把资源文字化，`runAgentLoop` 负责每次请求前的投影。三者不是一个“大 Prompt Builder”。

## 项目指令的作用域

`packages/coding-agent/src/core/resource-loader.ts` 的 `loadProjectContextFiles` 会从 agent 目录和当前工作目录的祖先目录读取候选文件。候选名称包括 `AGENTS.override.md`、`AGENTS.md`、`AGENTS.MD`、`CLAUDE.md` 和 `CLAUDE.MD`。具体加载还受到 project trust 和 `noContextFiles` 等选项影响。

它返回的是：

```ts
Array<{ path: string; content: string }>
```

这个返回值本身不是消息。`AgentSession._rebuildSystemPrompt` 把它放进 `BuildSystemPromptOptions.contextFiles`，随后 `buildSystemPrompt` 生成：

```text
<project_context>
Project-specific instructions and guidelines:
<project_instructions path="/repo/AGENTS.md">
...
</project_instructions>
</project_context>
```

**输入**是路径和文件正文；**输出**是可追溯的 Prompt 区块；**状态变化**是本轮 system prompt 发生变化，而不是 Session 增加一条 user message；**失败点**包括文件不可读、项目不可信或不同资源重复加载。

## Skills 是渐进加载，不是全部注入

`packages/coding-agent/src/core/skills.ts` 的 `formatSkillsForPrompt` 通常只把名称、描述和路径放入 System Prompt。模型看到类似：

```xml
<available_skills>
  <skill>
    <name>review</name>
    <description>Review a change for correctness and tests.</description>
    <location>/repo/.pi/skills/review/SKILL.md</location>
  </skill>
</available_skills>
```

完整 `SKILL.md` 只有在模型决定需要该技能时，才通过 `read` 或显式 `/skill:name` 展开。这样 50 个技能不会在启动时全部消耗上下文。

**不要混淆**：Skill metadata 影响模型的选择，Skill 正文才提供具体方法；Skill 不是 Tool Definition，也不是 Extension 的事件钩子。

## Tools 的两份表示

Tool 至少有两份表示：

```text
registry entry
  ├── executable function
  ├── parameter validator
  └── execution policy

model-visible definition
  ├── name
  ├── description
  └── JSON Schema
```

`AgentSession` 通过 `createAllToolDefinitions`、active tool names、allowlist/denylist 和 Extension 工具构建 active registry。`buildSystemPrompt` 的 guidelines 还可能根据 `read`、`bash`、`grep` 等工具是否存在而变化。

工具定义告诉模型“可以请求什么”，并不授权它执行。真正的顺序仍是：解析参数 → 校验 → `beforeToolCall` → 权限检查 → `AgentTool.execute` → `toolResult`。

## 一次具体投影

假设当前目录是 `/repo`，Session 当前 leaf 上有三条消息：

```text
user: 修复 parser 的测试
assistant: toolCall(read, {path: "parser.ts"})
toolResult: parser.ts 的前 200 行
```

当前可用工具为 `read`、`edit`、`bash`，项目文件要求先运行测试。最终 context 可以抽象为：

```json
{
  "systemPrompt": "coding rules + project instructions + skill metadata + cwd",
  "messages": [
    {"role": "user", "content": "修复 parser 的测试"},
    {"role": "assistant", "content": [], "tool_calls": [{"name": "read", "arguments": {"path": "parser.ts"}}]},
    {"role": "toolResult", "toolCallId": "call-1", "content": "..."}
  ],
  "tools": ["read", "edit", "bash"],
  "options": {"thinking": "medium", "signal": "AbortSignal"}
}
```

**输入**是 Session branch、资源快照和 active tool names；**输出**是 Provider 可以消费的 `Context`；**状态变化**只发生在内存投影，除非之后把新消息持久化；**失败点**是转换器丢失 tool call、工具定义与执行 registry 不一致、或输出超出窗口。

## 代码实验：观察而不是猜

### 目标

证明“Session 中存在”和“本轮请求中存在”是两件事。

### 准备

使用仓库内 faux provider 或 Go/Java 示例的 `ScriptedModel`。准备一个临时目录，不要使用真实凭据。

### 步骤

1. 在临时目录创建 `AGENTS.md`，写入一条明显的规则。
2. 启用一个带短描述的 Skill，再关闭它对应的执行 Tool。
3. 让 Fake Model 记录每次收到的 system prompt、messages 和 tools。
4. 运行一次 `read` tool call，再查看第二次 request。
5. 在 Session 中增加 label 或 UI-only custom entry，观察它是否进入 messages。

### 观察点

- 项目规则通常在 system prompt，而不是 user message。
- tool result 会进入历史，但 tool definition 位于 tools 字段。
- Skill metadata 可以存在，Skill 正文未必存在。
- label 能被 TUI 使用，却不必发送给模型。

### 预期结果

你能画出“资源 → prompt”和“leaf → messages”两条独立路径，并指出每种输入的拥有者。

### 思考题

1. 如果 `AGENTS.md` 要求只读，但用户要求删除文件，冲突应该由哪一层报告？
2. 为什么把所有内容拼成一个 user message 会破坏权限层次和调试能力？
3. 如果 Extension 在 `before_agent_start` 修改 system prompt，下一轮是否应该复用旧 prompt？为什么？

## Go 与 Java 对照

| Context 边界 | Go 示例 | Java 示例 | Pi |
| --- | --- | --- | --- |
| 模型输入 | `Request{Messages, Tools}` | `Request` record | `Context` |
| 取消 | `context.Context` | `CancellationToken` | `AbortSignal` |
| 资源快照 | 显式读取 metadata | 显式读取 `SkillDiscovery` | `ResourceLoader` |
| 消息转换 | provider payload map | Jackson `ObjectNode` | `convertToLlm` |
| 观察方式 | Fake `Model` 记录 request | `ScriptedModel.requests()` | `onPayload`/faux provider |

Go/Java 里的 context manager 可以先是纯函数；真实系统再加入持久化、compaction 和权限。这种逐层增加比在 Loop 里直接读取磁盘更容易测试。

## 小结

Context 是“资源、配置和对话状态在本轮请求中的有边界投影”。System Prompt 不是全部历史，Session 也不是全部 Context；Skill metadata 不是 Skill 正文，Tool Definition 不是 Tool Execution。读源码时沿着 `ResourceLoader → buildSystemPrompt` 和 `Session branch → buildSessionContext → convertToLlm` 两条路径追踪，才能知道模型到底看到了什么。
